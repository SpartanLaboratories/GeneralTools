# The published shape after the module split: core, desktop and the umbrella

- **Issue:** [SpartanLaboratories/GeneralTools#7](https://github.com/SpartanLaboratories/GeneralTools/issues/7); absorbs [#17](https://github.com/SpartanLaboratories/GeneralTools/issues/17) (root artifact usable from plain Maven).
- **Date read:** 2026-11-22. Repo baseline: branch `feat/issue-7-kotlin-multiplatform` at `29dd4ff`, single-module build in `build.gradle.kts`.
- **Method limits:** nothing was built or published. Evidence is plugin source at pinned tags (shallow clones in a scratch directory, read only, deleted afterwards), official Gradle / Maven / Kotlin / Sonatype / JDK documentation, and the published files of comparable artifacts on Maven Central (downloaded and read). Every behaviour that only a build can show is listed in *Gaps* and turned into a rehearsal check in section 6.

## 1. Question

How are `GeneralTools-core` (multiplatform: `jvm`, `js`, `wasmJs`), `GeneralTools-desktop` (JVM-only: `UserActions`, AWT, commons-io) and the source-less umbrella `GeneralTools` built and published at one version, `3.0.0`, under `io.github.spartanlaboratories`, so that:

- 2.x consumers keep the coordinate `GeneralTools`;
- plain-Maven consumers of `GeneralTools` get real classes;
- no consumer build ends up with two copies of the same classes, in particular one that still pulls `GeneralTools:2.2.0` through a published `gametools` 5.x;
- the package `com.spartanlabs.generaltools`, present in the core JVM jar and the desktop jar, is handled for the Java module system;
- the whole set is rehearsed from one file repository and released as one Central deployment by one `publishAndReleaseToMavenCentral` invocation.

Requirements that bind every answer: JVM consumers on Kotlin 2.2.0 and 2.1.20 resolve and compile; web consumers need Kotlin 2.4; bytecode floor 17; `com.vanniktech.maven.publish` 0.37.0; every publication signed; every javadoc jar is Dokka output; package names unchanged.

## 2. Bottom line

1. **Desktop: a Kotlin/JVM module** (`org.jetbrains.kotlin.jvm`), one jar, coordinate `GeneralTools-desktop`. A multiplatform module with only `jvm()` would add an empty root artifact plus `-jvm`, and would make plain Maven consumers of the desktop module hit the same empty-root trap that issue #17 describes.
2. **Umbrella: a JVM-only, source-less Kotlin/JVM module** named `GeneralTools`, with `api(project(":GeneralTools-core"))` and `api(project(":GeneralTools-desktop"))`, publishing an (empty) jar, a POM and a Gradle module file exactly like 2.2.0's shape. Add an Okio-style `pom.withXml` to the **core root** publication so its POM depends on `GeneralTools-core-jvm`; without it plain Maven resolves umbrella -> `GeneralTools-core` -> a jar with no classes. A multiplatform umbrella is only needed if a `commonMain` of a project with a `js`/`wasmJs` target must be able to write the single line `GeneralTools`; it costs three more Central components, empty klibs, and an untested source-less-target publication.
3. **Duplicate protection: dependency constraints**, published from `GeneralTools-core` (its `jvm` variant) and `GeneralTools-desktop`: "`io.github.spartanlaboratories:GeneralTools` requires `<project.version>`". This is the same shape `kotlin-stdlib` ships for its retired `-jdk7`/`-jdk8` artifacts. It works for Gradle consumers only; Maven has no equivalent, so Maven consumers get a migration note. Capabilities are rejected: they fail the build on the normal path (core and umbrella in one graph) or protect nothing. Constraints make the result one copy of 3.0.0 classes; a `gametools` 5.x that was compiled against 2.2.0 then fails with a link error at its first use of a removed type, not with a silent mix of two `Point`s.
4. **Split package: set `Automatic-Module-Name` explicitly on the core JVM jar and on the desktop jar** (distinct names), and state in the docs that core and desktop cannot both be on the module path. Two automatic modules that contain the same package cannot be resolved together, whatever their names; the split is harmless on the class path, which is where 2.x consumers are.
5. **Release: one repository, one invocation.** In the plugin at 0.37.0 every module's upload goes into one shared build service and one zip, hence one Central deployment, from a single root `publishAndReleaseToMavenCentral`. Rehearse with an extra file repository defined in the shared convention plugin and `publishAllPublicationsToRehearsalRepository` from the root. The rehearsal proves the metadata shape and consumer resolution of the exact tree; it does not prove Portal validation, signature acceptance by Central, or byte identity with the upload.

## 3. Findings

Tiers: **Consensus** (spec, official docs or several independent credible sources), **Practice** (what mature libraries visibly do), **Opinion** (one source), **Inference** (derived from the cited sources, not stated by them; checked in the rehearsal).

### F1. A multiplatform root artifact is empty for Maven; a consumer's Maven build gets no classes from it (Consensus; carried from the earlier publishing research)

The root publication of a multiplatform module carries metadata and a `.module` file whose `available-at` entries redirect Gradle to the `-jvm` module; its POM lists only the common dependencies. Maven ignores `.module`. Okio changed `okio` from JVM-only to multiplatform and made the root POM depend on `okio-jvm` for exactly this reason (see section 4). This is why a "depends on both" umbrella is not enough by itself: the POM of an umbrella that depends on `GeneralTools-core` leads Maven to the core **root**, which holds no classes (Inference, from this fact plus the generated-POM rule that a project dependency is written as that project's publication coordinates; confirm in the rehearsal, gap G2). Source for the Okio hack: [`build.gradle.kts` @ `parent-3.18.2`](https://github.com/square/okio/blob/parent-3.18.2/build.gradle.kts), claim 8. Applies to Okio 3.18.2 (built with vanniktech 0.37.0, the version in use here).

### F2. kotlin-stdlib's alignment of retired artifacts is the closest published precedent, and it is a constraint, not a capability (Practice; read 2026-11-22)

- In Kotlin 1.8.0 the contents of `kotlin-stdlib-jdk7`/`-jdk8` were merged into `kotlin-stdlib`; the 1.8.0 `-jdk8` jar on Central holds five entries (manifest and a `module-info` stub) and its POM depends on `kotlin-stdlib` and `-jdk7` at 1.8.0: a retired coordinate kept as an empty pointer. ([Kotlin 1.8.0 notes](https://kotlinlang.org/docs/whatsnew18.html), claim 1; Central listing, claim 2.)
- In 1.8.0 the alignment itself lived in the **Gradle plugin on the consumer's side**: "the Kotlin Gradle Plugin will use that Kotlin version for transitive `kotlin-stdlib-jdk7` and `kotlin-stdlib-jdk8` dependencies" (claim 1). There is no `kotlin-stdlib-1.8.0.module`; the published `.module` files start at 1.9.20 (checked 1.8.0, 1.8.10, 1.8.20, 1.9.0, 1.9.10: HTTP 404; 1.9.20 and later: present).
- From 1.9.20 on, `kotlin-stdlib`'s own `.module` publishes the constraint in its variants. In 2.4.21: `dependencyConstraints` = `kotlin-stdlib-common` requires `2.4.21`, `kotlin-stdlib-jdk7` requires `1.8.0`, `kotlin-stdlib-jdk8` requires `1.8.0` (claim 3). The constraint pins the retired artifacts to **the first version that became the empty pointer** (1.8.0), not to the current stdlib version. The equivalent here: `GeneralTools` requires `3.0.0`, the first version that is an umbrella.
- The correction to the common shorthand "kotlin-stdlib 1.8.0 aligned jdk7/jdk8 with constraints": the version that first did it in published metadata is 1.9.20; 1.8.0 did it in the plugin.

### F3. Gradle dependency constraints do exactly what duplicate protection needs, on the Gradle side only (Consensus; Gradle docs `current` = 9.9.x, read 2026-11-22)

- "A dependency constraint sets version requirements for a module without adding that module as a dependency"; if nothing else brings the module in, the constraint is "a no-op (it doesn't add the module)"; if it is in the graph the constraint "guides the version selection". Constraints are transitive and are published only in Gradle Module Metadata (claim 4).
- The Gradle module-metadata mapping table lists: dependency constraints -> POM `<dependencyManagement>` dependencies, with the note "Gradle dependency constraints are transitive, while Maven's dependency management block isn't" (claim 5). So a Maven consumer gets a POM entry that does not drive its version selection, and `GeneralTools` and `GeneralTools-core` are different artifactIds, which Maven's one-version-per-artifact rule cannot unify anyway (Inference).
- Consequence: a Gradle graph containing `GeneralTools-core:3.0.0` and `GeneralTools:2.2.0` resolves `GeneralTools` to 3.0.0 (the umbrella), which depends on core and desktop. Core is then selected once. There is no cycle: the constraint is not a dependency.
- A constraint of this kind has a cost that must be stated, not hidden. It does not make `gametools` 5.x work with 3.0.0: 5.x names `Square` (renamed `Rectangle`) and assigns `area.dimensions`. It removes the *silent* mix of two jars with the same `com.spartanlabs.geometry.Point` and replaces it with one 3.0.0 copy and a link error at the removed type (Inference from the README's description of 3.0.0 and the gametools POM: `gametools-5.1.0.pom` requires `GeneralTools` `2.2.0`, `gametools-5.1.0.module` carries `"requires": "2.2.0"`).

### F4. Capabilities cannot do this job (Consensus; Gradle docs `current`, read 2026-11-22)

- A component's implicit capability is `group:artifact:version`; "Once you declare any explicit capability, all capabilities must be declared, including the implicit one"; two providers of one capability in a graph fail the build ("it will fail the build with an error, indicating the conflicting modules", and Gradle does not resolve it unless told to); capabilities are published only in Gradle Module Metadata and have no POM equivalent (claim 6; claim 5 table: "Component capabilities are unique to Gradle", "Not published").
- To collide with `GeneralTools:2.2.0`, core and desktop would have to declare the capability `io.github.spartanlaboratories:GeneralTools`. Then core and desktop collide with each other, and core collides with the 3.0.0 umbrella (implicit capability of the same name), on every normal path, unless the umbrella gives up its implicit capability and every variant of every target declares the rest. The one case it would catch (core beside a stale 2.2.0) is already handled by constraints; the cost is a build failure in all cases. It also adds nothing for Maven. Rejected.
- Prior art in the organization: WebTools declares one capability, `…-test-fixtures`, on a JVM variant (`webtools-http/build.gradle.kts`), and carries a comment that Gradle warns because it "cannot be mapped to Maven". No repository in the organization uses a constraint or a capability for alignment (grep of both repos' `*.kts`).

### F5. The retired-artifact precedent in this organization: MyGameTools' `gametools` umbrella (Practice; local files and Central, read 2026-11-22)

- `gametools` 5.1.0 on Central is a JVM-library umbrella: files `gametools-5.1.0.jar`, `-sources.jar`, `-javadoc.jar`, `.module`, `.pom`; POM lists `gametools-core`, `-net`, `-world` (compile scope) plus the shared dependencies; `.module` has `apiElements` with `org.gradle.jvm.environment=standard-jvm`, `org.gradle.jvm.version=23`, `org.jetbrains.kotlin.platform.type=jvm` and the three modules as `requires 5.1.0` dependencies. Build: `gametools/build.gradle.kts` (`api(project(":gametools-core"))` and so on) with its sources jar and Dokka site folded from the modules, guarded by two verify tasks.
- Its own comment names the limit that matters here: `duplicatesStrategy = DuplicatesStrategy.EXCLUDE` "safe today (the modules share no packages), revisit on a module-boundary move". GeneralTools' core and desktop **do** share a package (not a file path), so a path collision would be dropped silently unless a count check is added (Pitfall 6).
- WebTools publishes `webtools-http` / `webtools-http-jvm` / `webtools-feeds` at 1.0.0 as multiplatform modules and left its old `WebTools` coordinate at 2.0.1a. The `webtools-http` 1.0.0 root POM carries no `-jvm` dependency (no Okio hack): its Maven consumers must use `-jvm`. Neither organization repository has solved the "keep the old coordinate for Maven" problem; Okio is the precedent.

### F6. `org.gradle.jvm.version` of a source-less or JVM-only module follows the toolchain unless set (Consensus for the rule; Inference for this repo; observed in 2.2.0's metadata)

- 2.2.0's `GeneralTools-2.2.0.module` carries `"org.gradle.jvm.version": 23` on `apiElements`. A JDK 17 Gradle consumer cannot resolve that variant ("lower is compatible with higher", claim 7). The current multiplatform build sets 17 by hand on the JVM variant (`build.gradle.kts:54`). The umbrella and the desktop module are new JVM variants and need the same floor, or the umbrella would be the only artifact in the set a JDK 17 consumer cannot resolve, even though core accepts it. The mechanism (toolchain versus release flag, and the guard in `check`) is the build-organisation and Java-floor work; this report only records that each published JVM variant, including the empty umbrella's, must show 17.

### F7. The package split across core and desktop is invisible on the class path and fatal for both on the module path (Consensus; JDK 17 documentation)

- A JAR without `module-info.class` is an automatic module named by `Automatic-Module-Name` if present, otherwise derived from the file name: strip `.jar`, cut at the first `-(\d+(\.|$))`, replace non-alphanumerics with dots (claim 9). Without the attribute the new jars would be named `GeneralTools.core.jvm` (from `GeneralTools-core-jvm-3.0.0.jar`) and `GeneralTools.desktop`; the 2.2.0 jar has no `Automatic-Module-Name` (its manifest is `Manifest-Version: 1.0` only), so it was `GeneralTools`. The umbrella jar `GeneralTools-3.0.0.jar` would keep deriving `GeneralTools`.
- "For each enumerated module X that is automatic: X 'reads' every other enumerated module", and resolution fails if "Two or more modules export a package with the same name to a module that 'reads' both. This includes the case where a module M containing package p 'reads' another module that exports p to M" (claim 10). Two automatic modules both holding `com.spartanlabs.generaltools` therefore fail resolution together, under any names (Inference: the rule applied to the package layout; the JDK docs do not name automatic split packages as such). `Automatic-Module-Name` fixes the name instability, not the split.
- Multiplatform libraries set the attribute on `jvmJar`: kotlin-logging 8.0.4 `build.gradle.kts`, `val jvmJar by getting(Jar::class) { manifest { attributes("Automatic-Module-Name" to "io.github.oshai.kotlinlogging") } }` (claim 11; Practice).
- Kotlin side of the same split: the 2.2.0 jar carries `META-INF/GeneralTools.kotlin_module`, named after its module. The 3.0.0 jars carry one `.kotlin_module` each; as long as the two Gradle projects have different names the files differ, so Kotlin consumers see the package's top-level functions from both jars (`MiscKt` in core, `UserActionsKt` in desktop) through two separate module files (Inference; checked in the Kotlin 2.2.0 and 2.1.20 smoke projects, G4).

### F8. One Gradle invocation is one Central deployment (Consensus; plugin source @ 0.37.0)

- `publishToMavenCentral()` in each module registers `prepareMavenCentralPublishing` and the lifecycle tasks `publishToMavenCentral` and `publishAndReleaseToMavenCentral` per module. All modules share one `MavenCentralBuildService`; each module's prepare task calls `registerProject(...)` on it, and at the end of the build the service builds **one** zip from every registered project's local repository (`projectsToPublish.forEach { project -> ... }`), one name (`group-version` when the coordinates share group and version), and uploads it once, logging `Uploaded bundle to Central Portal as $publishingType, deployment id: $deploymentId` (claim 12).
- Gradle's task selector with only a task name, run from the root, runs that task in every subproject that has it (claim 13), so `./gradlew publishAndReleaseToMavenCentral` reaches all three modules. A module that does not apply the plugin, or whose `prepare` task is not reached, is silently absent from the bundle; the plugin does not check the set (Inference from the source: `projectsToPublish` is built only from registrations).
- The upload is at build end, hence the failure semantics: a failed build drops the just-created deployment (`EndOfBuildAction.Drop(runAfterFailure = true)`). Sonatype's API treats the deployment as the unit that is published or dropped (claim 14), and states "the archive can contain more than one component" (claim 15).

### F9. Gradle plugin applicability: a JVM-only umbrella and a JVM desktop are first-class in vanniktech 0.37.0 (Consensus; plugin source @ 0.37.0)

- With `org.jetbrains.kotlin.jvm` applied, `configureBasedOnAppliedPlugins` picks `KotlinJvm(javadocJar, sourcesJar)`, which creates one publication from the `java` component (claim 16); with `java-library` it picks `JavaLibrary`. `JavadocJar.Dokka(taskName)` is the documented way to use Dokka output ("Creates a javadoc jar using Dokka's output. The argument is the name of the dokka task that should be used for that purpose", claim 16). MyGameTools already does this for its umbrella and modules (`gametools.published-library.gradle.kts`: `configure(JavaLibrary(javadocJar = JavadocJar.Dokka("dokkaGeneratePublicationHtml"), sourcesJar = true))`; `sourcesJar = true` is the deprecated Boolean overload, use `SourcesJar.Sources()`).
- For a multiplatform module each target publication receives its own javadoc jar task from the same Dokka task (the earlier publishing research, F2), so root, `-jvm`, `-js` and `-wasm-js` of core each carry Dokka output.
- KGP puts the `jvm` target's published API variant on `jvmApiElements`, which "extends from" the compilation's API dependency scope (`CreateTargetConfigurationsSideEffect` @ v2.4.21, claim 17). A constraint declared on that scope (or on `jvmMainApi`, which feeds it) is therefore expected to land in the `-jvm` module's `apiElements` variant (Inference; confirm in the rehearsal, G3).

### F10. Project and artifact names must agree for a split like this (Consensus; plugin source and Gradle docs)

- vanniktech rewrites each KMP publication's artifactId from the Gradle project name: equal -> replaced by the given `artifactId`; starts with `"$projectName-"` -> prefix replaced; anything else throws (claim 18, claim 8 of the earlier research). So for core, project name `GeneralTools-core` and coordinates `GeneralTools-core` yield `GeneralTools-core`, `GeneralTools-core-jvm`, `-js`, `-wasm-js`. The open issue [vanniktech#1020](https://github.com/vanniktech/gradle-maven-publish-plugin/issues/1020) (reported on 0.33.0) is the failure when the two differ.
- A composite build (`includeBuild`) substitutes `${project.group}:${project.name}` per project, and needs explicit `dependencySubstitution` when "multiple publications are defined for a single project" (claim 19). The root project is currently named `GeneralTools` (`settings.gradle.kts:4`); an umbrella subproject also named `GeneralTools` would give two projects the same `group:name`. MyGameTools avoids this: root `MyGameTools`, subprojects `gametools-core`, `gametools-net`, `gametools-world`, `gametools`.

## 5. Pitfalls and regrets

1. **The umbrella's POM reaches the empty core root.** Gradle writes the umbrella's project dependency as the core root coordinate; Maven then holds a metadata-only jar. Okio's hack on the root POM is the fix; Gradle consumers are unaffected because they read `.module`.
2. **A metadata-only umbrella (a `pom` without a jar) breaks Maven consumers who keep their 2.x dependency declaration.** Maven's dependency `type` defaults to `jar` (claim 20), so a consumer that did not add `<type>pom</type>` asks for `GeneralTools-3.0.0.jar`; with none published the build fails (Inference from claim 20 and Central's rule that non-`pom` packaging supplies a JAR, claim 21; confirm with the Maven smoke project). An empty jar costs nothing and `kotlin-stdlib-jdk8` 1.8.0 is the precedent.
3. **The empty umbrella's `org.gradle.jvm.version` follows the toolchain.** See F6: set 17 on the umbrella and on desktop, or a JDK 17 consumer cannot resolve the umbrella.
4. **A constraint expressed as `project(":GeneralTools")`** inside core would make a project-level cycle (umbrella depends on core, core constrains umbrella). Use the string coordinate `io.github.spartanlaboratories:GeneralTools:$version` with the version read from the one project property, never a literal in two places.
5. **A constraint is not compatibility.** It guarantees one copy; it cannot make a `gametools` 5.x that uses `Square` work. The migration note must say that `gametools` 5.0.0/5.1.0 need a rebuild against 3.0.0.
6. **`duplicatesStrategy = EXCLUDE` in a folded umbrella sources jar hides collisions** (MyGameTools' own comment). Here the packages overlap; add a verify task that the umbrella sources jar holds exactly as many `.kt` entries as core's `commonMain`+`jvmMain` and desktop's `main` together.
7. **Folding a multiplatform module's sources needs the right outgoing configuration.** KGP names it per target (`KotlinTarget.sourcesElementsConfigurationName`; the JVM target's is expected to be `jvmSourcesElements`), unlike MyGameTools' single `sourcesElements`. Confirm the name and that it includes `commonMain` sources in the rehearsal (G5).
8. **Release set completeness is not checked by the plugin.** A module missing from the shared build service is simply absent from the zip; the rehearsal must list the exact expected six components (below) and fail if one is missing.
9. **Project naming.** Root project `GeneralTools` plus subproject `GeneralTools` is ambiguous for composite substitution and breaks the "artifactId equals project name" invariant for one of them; rename the root (it is not published), and name subprojects after their artifacts.
10. **Signing needs keys for the rehearsal too.** For a non-SNAPSHOT version `signAllPublications` is required (earlier publishing research, F3), so the rehearsal runs on the machine that holds the signing key and also exercises the signing path.
11. **`mavenLocal()` shadowing.** Do not rehearse through `~/.m2`; a leftover 3.0.0 outlives the test (earlier publishing research, pitfall 5).

## 6. Recommendation for this repo

The numbered points follow the five design points of the question.

### 6.1 Desktop module: Kotlin/JVM

- `GeneralTools-desktop` applies `org.jetbrains.kotlin.jvm` (and Dokka, vanniktech), coordinates `GeneralTools-desktop`, project name `GeneralTools-desktop`. It publishes one jar, a POM and a `.module`; `KotlinJvm` is auto-detected; javadoc jar = `JavadocJar.Dokka("dokkaGeneratePublicationHtml")`, `SourcesJar.Sources()`.
- Its dependencies are its own: `slf4j-api`/logging and commons-io (`implementation`, runtime scope, as in 2.2.0's POM), no dependency on core unless `UserActions` uses a core type (it currently imports none from `com.spartanlabs`).
- Why not multiplatform with only `jvm()`: it adds `GeneralTools-desktop` (empty root) and `GeneralTools-desktop-jvm`, two publications to sign and validate, and needs the Okio hack again so Maven works; it buys nothing because no other target is planned. A Gradle multiplatform consumer places `GeneralTools-desktop` in `jvmMain`, where a JVM-only dependency is the normal case.

### 6.2 Umbrella: JVM-only, source-less, `api` to both; Okio-style POM rewrite on core's root

- Subproject `GeneralTools` (directory free to name), plugins `org.jetbrains.kotlin.jvm`, Dokka, `com.vanniktech.maven.publish`; no source sets. Dependencies: `api(project(":GeneralTools-core"))`, `api(project(":GeneralTools-desktop"))`. Coordinates `GeneralTools`, same group and version. Sources jar and Dokka HTML aggregated from both modules following `gametools/build.gradle.kts`, with the verify tasks of Pitfall 6.
- Published files, as 2.2.0: `GeneralTools-3.0.0.jar` (empty), `.pom` (compile-scope dependencies on `GeneralTools-core` and `GeneralTools-desktop`), `.module` (`apiElements`/`runtimeElements` with those two as `requires 3.0.0`), sources and javadoc jars.
- On core's `kotlinMultiplatform` publication, the Okio rewrite: the root POM's dependencies become one compile-scope dependency on the `jvm` publication's coordinates. Result: Maven umbrella -> core root -> `GeneralTools-core-jvm` (real classes) -> stdlib, slf4j; and umbrella -> desktop (real classes) -> commons-io. This also gives plain-Maven users of `GeneralTools-core` the JVM classes. The `.module` is not touched. If a pure multiplatform root for core is preferred, apply the same rewrite to the umbrella's POM only, replacing its core dependency with `GeneralTools-core-jvm` (the Gradle metadata still names core root); the cost is the same, the scope is smaller.
- **When to choose the multiplatform umbrella instead.** If a Gradle project with a `js` or `wasmJs` target must be able to declare `GeneralTools` in `commonMain`, a JVM-only umbrella fails there: its variants carry `org.jetbrains.kotlin.platform.type=jvm`, so a `js` resolution finds no candidate ("if at any point no candidates remain, resolution fails", claim 22; the 2.x variants have exactly that attribute). The multiplatform umbrella (`jvm` variant -> core + desktop; `js`/`wasmJs` -> core; the Okio rewrite on its own root) fixes that, at the price of: three more Central components (`GeneralTools-jvm`, `-js`, `-wasm-js`, each with sources, javadoc, signatures), two empty klibs built by Kotlin 2.4 (so the umbrella then also needs Kotlin 2.4 on web), and a source-less multiplatform publication I could not find prior art for and could not build (G1). Under the assumption in section 8 (A1) the JVM-only umbrella is the lower-risk choice: 2.x consumers are all JVM and web consumers depend on `GeneralTools-core` directly.

### 6.3 Duplicate protection: constraints, plus a migration note for Maven

- In core (`jvm` variant) and desktop, add a constraint `io.github.spartanlaboratories:GeneralTools` requiring the project's own version, declared on the `api` scope that feeds the published API variant (for core: `jvmMainApi`; for desktop: `api`). Use the string coordinate (Pitfall 4). Use `require` (a lower bound), so a later 3.x umbrella still wins; do not use `strictly`.
- Alternatives and why not: *capabilities* (F4: fails the normal path, no Maven effect); *a `rejects` range* excluding `[,3.0.0)` (fails resolution with a message even for consumers whose use of 2.2.0 types is unchanged in 3.0.0, which cannot be known, and has no Maven effect); *a note only* (leaves Gradle consumers with two copies on the class path in the one case that can be prevented). 
- Maven consumers: the migration notes say that a build that depends on `GeneralTools:2.2.0` (directly or through `gametools` 5.x) must not also depend on `GeneralTools-core`/`-desktop` 3.0.0 and show an `<exclusion>` on `GeneralTools` for the transitive case. Nothing the library publishes can enforce this in Maven (claim 5).
- Add the Gradle resolution case to the smoke matrix (section 6.6).

### 6.4 Split package: explicit `Automatic-Module-Name` on core JVM and desktop

- Core: `tasks.named<Jar>("jvmJar") { manifest { attributes("Automatic-Module-Name" to "com.spartanlabs.generaltools.core") } }` (the pattern kotlin-logging uses). Desktop: `tasks.jar { manifest { ... "com.spartanlabs.generaltools.desktop" } }`. The names are a commitment: they become the names of the modules if module descriptors are ever added. The umbrella keeps no attribute (empty jar; derived name `GeneralTools`, the same as 2.x).
- Document: on the class path nothing changes. On the module path core and desktop cannot be resolved together (F7); a module-path application takes core alone, or keeps desktop on the class path. Moving `UserActions` to its own package would remove the limit and is a source break outside this release.
- Js/wasm klibs have no module-path concern.

### 6.5 Build naming and publishing set

- Subprojects `GeneralTools-core`, `GeneralTools-desktop`, `GeneralTools`; the root becomes an unpublished aggregator with a different name (for example `GeneralTools-build`) and applies neither the plugin nor any publication. The shared publishing block (`publishToMavenCentral()`, `signAllPublications()`, the POM metadata, the 17 floor on every published JVM variant) lives in the convention plugin; each module only declares `coordinates(...)`, `name`, `description` and its platform.
- The expected component set, to be asserted by a check before the release: `GeneralTools`, `GeneralTools-core`, `GeneralTools-core-jvm`, `GeneralTools-core-js`, `GeneralTools-core-wasm-js`, `GeneralTools-desktop`; each with `.pom`, `.module`, main file, sources jar, javadoc jar, `.asc`, md5 and sha1; the three root-type components that Gradle publishes (core root, umbrella, desktop) each also have a `.module`.

### 6.6 Rehearsal and release

**Rehearsal.** In the convention plugin add one file repository, for example

```kotlin
publishing { repositories { maven { name = "rehearsal"; url = uri(rootProject.layout.buildDirectory.dir("rehearsal-repo")) } } }
```

and run `./gradlew publishAllPublicationsToRehearsalRepository` from the root: the task selector reaches every module, and one directory tree receives all six components with real signatures. Resolve from it in the consumer matrix; every consumer lists the rehearsal repository first, filtered to the group (`content { includeGroup("io.github.spartanlaboratories") }`), then `mavenCentral()`:

1. Kotlin 2.2.0 JVM project (and a Kotlin 2.1.20 one) on `GeneralTools:3.0.0`: compiles calls into core (`MiscKt`), core JVM (`read`), desktop (`cropImage`), all three in the one package; `dependencies` shows the umbrella, core-jvm and desktop; JDK 17 toolchain resolves.
2. The duplicate-protection case: the same project also declares `io.github.spartanlaboratories:GeneralTools-core:3.0.0` and `io.github.spartanlabsgaming:gametools:5.1.0` (from Central, which pulls `GeneralTools:2.2.0`); `dependencyInsight --dependency GeneralTools` shows 3.0.0 selected and the runtime classpath has one `com/spartanlabs/geometry/Point.class`.
3. Kotlin 2.4 multiplatform project with `jvm`, `js`, `wasmJs`: `GeneralTools-core` in `commonMain`, `GeneralTools-desktop` in `jvmMain`; plus, as a documented negative control, `GeneralTools` in `commonMain` (expected to fail on `js` with the JVM-only umbrella).
4. Plain Maven project: `GeneralTools:3.0.0` compiles against `Color`/`Misc` and `UserActions`; `mvn dependency:tree` shows the two jars; a second project with `GeneralTools:2.2.0` plus `GeneralTools-core:3.0.0` documents the duplicate case that the migration note covers.
5. The throwaway MyGameTools migration, against the same repository.

**Release.** Merge the final change; the standing automatic release runs the single root `publishAndReleaseToMavenCentral`. Before landing: confirm all six components are in the rehearsal tree, that every module's `prepareMavenCentralPublishing` is on the task graph (`./gradlew publishAndReleaseToMavenCentral --dry-run`, which writes nothing and does not upload), and that the deployment name the plugin will use is `io.github.spartanlaboratories-3.0.0` (all coordinates share group and version).

**What the rehearsal proves.** The generated `.pom`/`.module` of every component (variants, attributes, `available-at`, constraints, the Okio rewrite, `org.gradle.jvm.version`); that Gradle and Maven resolve the set from a Maven-layout repository and compile against it; the completeness of the set; that signing works with the maintainer's key; that sources and Dokka javadoc jars exist for every component.

**What it does not prove.** (a) Portal validation of each component (namespace for the new artifactIds, POM completeness, javadoc/sources presence under the Portal's rules, the public key on a keyserver); (b) the exact bytes: the Central path rebuilds, and the Central bundle holds only the checksum types the plugin allows (md5 and sha1 by default in 0.37.0) while Gradle's file repository holds all of them; (c) that the Portal serves the root `.module`'s relative `available-at` entries; (d) all-or-nothing behaviour of a failing component in a multi-component deployment, which Sonatype documents only at the deployment level (claim 14); (e) propagation timing. The release is irreversible (Central does not modify published components); the checks above are the only gate, which is why the rehearsal asserts the component set and the constraint presence rather than trusting the build.

## 8. Gaps and assumptions

**Assumptions** (each with what changes if false):

- **A1. "Works as a dependency of a Gradle multiplatform project" means the JVM-consuming source sets (`jvmMain`, or `commonMain` of a project whose only target is `jvm`) of such a project.** If it means `commonMain` of a project that has `js`/`wasmJs` targets, the JVM-only umbrella fails there and the multiplatform umbrella (6.2) is required, with its extra components and the Kotlin 2.4 requirement for the umbrella's klibs.
- **A2. No 2.x consumer puts GeneralTools on the module path.** The 2.2.0 jar has no module descriptor and no `Automatic-Module-Name`; I found no evidence of module-path users either way. - **A3. `UserActions` needs no type from core.** Its imports show none. If it does, desktop gets `api(project(":GeneralTools-core"))` and the constraint plan stays the same.
- **A4. Web consumers depend on `GeneralTools-core` directly.** True by construction (no 2.x web consumers); if a consumer asks for one line for every target, see A1.
