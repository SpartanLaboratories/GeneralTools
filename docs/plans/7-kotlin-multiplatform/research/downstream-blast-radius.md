## 1. Question

What does GeneralTools 3.0.0 break in the repositories that consume it, which classes inside this repository should move onto the new model in this change, and which checks before publishing prove the release before the Central release makes it permanent?

Requirements an answer meets, as plain facts about the work:

- 3.0.0 makes exactly these breaks: `Color`'s primary constructor becomes `internal`; `TwoDoubles` is no longer `sealed`; `Point` and `Dimensions` become immutable; `TwoDoubles.divideBy` returns a `Result`; `evaluateList` takes `(T) -> Boolean`; the `com.spartanlabs.logging` package is removed. Coordinates and package names stay; Maven-only consumers move to `GeneralTools-jvm`.
- MyGameTools stays on Kotlin 2.2.0 and does not compile unchanged against 3.0.0.
- Downstream repositories are read and never changed by this work; nothing is filed against them.
- Every class here built on a replaced mechanism (mutable `Point`/`Dimensions`, the throwing `divideBy`, the slf4j logger fields, `com.spartanlabs.logging`) gets a verdict.
- A Central release cannot be undone; a maintainer publishes by hand.

## 2. Bottom line

- **The blast radius is opt-in and small.** Publishing 3.0.0 changes nothing for a consumer that pins `2.x`. The only consumer with source that fails to compile is MyGameTools (40 in-place mutation sites in 17 files, 2 `Color(` constructor calls, 1 design change: `GameObject.location`). MyGameClient has 19 `Color(...)` calls in 6 files and nothing else; MyGameServer, WebTools, SpartanGraphics and KotlinBottools need no source change. No downstream repository has a Java source file, a `divideBy`/`/=`/`evaluateList`/`com.spartanlabs.logging` use, an exhaustive `when` over `TwoDoubles`, a `Point`-keyed map, or an assertion on `Point.toString()`.
- **The silent breaks are all in MyGameTools, plus one in MyGameClient, and none comes from a compile error.** (1) Making `GameObject.location` a `var` so `+=` compiles detaches it from `VisibleObject.area.location` (the shared `Point`). (2) `Alive` assigns live `Point`s to `destination` in two places (`destination = location`, `destination = attackTarget!!.location`); with immutable points `destination` becomes a snapshot. (3) A published `gametools:5.0.0` jar calls `Point.setTo`/`Point.plusAssign`, so any build that resolves GeneralTools 3.0.0 beside it fails at runtime with `NoSuchMethodError`. (4) MyGameClient's own `Color.lightened` extension is shadowed by the member that GeneralTools has had since 2.1.0, which rounds instead of truncating; its `UiTest` expects `177` and gets `178`. (5) `Actor.isAtDestination = location == destination` changes only for NaN-on-NaN, where equality is now reflexive.
- **Kotlin floors do not change.** GeneralTools 2.2.0 and 2.0.1 already carry class metadata `2.2.0`, and 3.0.0 built with `languageVersion` 2.2 carries `2.2.0` again, so MyGameClient (Kotlin 2.1.20, which reads metadata up to 2.2.0) keeps working and must not be given `languageVersion` 2.3. The issue's "MyGameTools is on 2.0.1" is the published `gametools:5.0.0`; MyGameTools `master` is on `2.2.0`. 3.0.0 also lowers the JVM floor: 2.2.0 and 2.0.1 are Java 23 bytecode and publish `org.gradle.jvm.version: 23`.
- **In this repository:** move `TwoDoubles`, `Point`, `Dimensions`, `Segment`, `Ray`, `Vectors.kt`, `Intersections.kt` and the `evaluateList` part of `Misc.kt` onto the new model (5 logger fields and 12 failure sites go to the helper); `Square` and `AxisAlignedBox` keep their shape with new KDoc; `CenteredBox` keeps its shape and its "treat as immutable" KDoc becomes a guarantee; `UserActions.kt` and the JVM half of `Misc` keep their slf4j logger; `com.spartanlabs.logging` is deleted with no in-repo user.
- **Pre-publish sequence (all on the maintainer's machine, the last four gate the irreversible click):** a throwaway MyGameTools migration against a composite build to settle the API early; publish to a file repository in `build/`; a consumer smoke matrix (Kotlin 2.2.0, Kotlin 2.1.20, Kotlin 2.4.x multiplatform, plain Maven) plus the migrated MyGameTools clone against those artifacts; upload without releasing and repeat the smoke against the Portal's download endpoint; click Publish; check once more from plain `mavenCentral()`. A pre-release version on Central is not recommended: it is permanent, publishes different bytes from the final release, and adds no coverage beyond the staged deployment for three consumers owned by one maintainer.

### 3.2 Kotlin floors through transitive consumers (decoded; source-read)

- **Metadata today.** In `GeneralTools-2.2.0.jar` every class checked (`Color`, `Point`, `TwoDoubles`, `PointKt`, `MiscKt`, `logging.Logger`) has `kotlin.Metadata mv=[2,2,0]`, class-file major 67 (Java 23). The 2.0.1 jar (`Color`, `Point`) is also `mv=[2,2,0]`, major 67. The published `GeneralTools-2.2.0.module` and the 2.0.1 module declare `org.gradle.jvm.version: 23` and `kotlin-stdlib` `requires 2.2.0`. The published `gametools-core:5.0.0` class `Actor` is `mv=[2,2,0]`, major 67.
- **Metadata under 3.0.0.** The metadata a compiler writes is a function of `languageVersion` ([kmp-build-and-kotlin-compat.md](kmp-build-and-kotlin-compat.md) F1), so `languageVersion` 2.2 gives `mv=[2,2,0]` again: the same value every consumer reads today. Not decoded from a 3.0.0 build (none exists); it is the claim the smoke matrix (section 6) proves.
- **MyGameClient, Kotlin 2.1.20.** At `v2.1.20`, `MetadataVersion.INSTANCE` is `(2, 1, 0)`, `INSTANCE_NEXT` is `(2, 2, 0)`, and `isCompatibleWithCurrentCompilerVersion` is true for metadata not newer than `INSTANCE_NEXT` (claim 1). So 2.1.20 reads `2.2.0` and cannot read `2.3.0`. Build evidence: its compiled `SoundPlayer.class` is `mv=[2,1,0]`, major 67, produced against `gametools:5.0.0`. It therefore compiles today and compiles against 3.0.0 only while `languageVersion` stays 2.2: setting 2.3 would break it. The stdlib on its classpath resolves to `2.2.0` (GeneralTools and `gametools` both require it; Gradle takes the highest requested version, claim 2), unchanged by 3.0.0.
- **MyGameServer.** `build.gradle.kts` declares `kotlin("jvm") 1.9.24` together with `` `kotlin-dsl` `` on a Gradle 9.7.1 wrapper. Its own build output (`build/classes/kotlin/main/MainKt.class`, 2026-09-07, after the `gametools:5.0.0` adoption commit `1ec4427`) is `mv=[2,2,0]`, major 67, and its test results exist for the same date. A 1.9.x compiler cannot write or read `2.2.0`, so the effective compiler was 2.2.x, not 1.9.24; the mechanism (most likely `kotlin-dsl` bringing Gradle's embedded Kotlin) was not established. So MyGameServer compiles against today's MyGameTools and GeneralTools, and nothing changes for it under 3.0.0. If the declaration were ever made effective, it could compile against neither today's nor tomorrow's artifacts.
- **JVM floor.** The Java 23 bytecode and `org.gradle.jvm.version: 23` of 2.x are why MyGameClient pins a toolchain of 23 (its comment says so). 3.0.0 targets bytecode 17; no downstream repository gets worse.

**Shared instances (silent when migrated mechanically).**

1. `VisibleObject(val area: Square, ...) : GameObject(area.location)` and `GameObject(val location: Point)`: one `Point` is the game object's location and `area.location`. `Actor` moves it in place. Once `Point` is immutable, `GameObject.location` must be writable for 5 main and 25 test writers, and the mechanical fix (`val` to `var`) gives the game object its own variable while `area.location` stays at the old value. Nothing fails to compile and the drawn box and `collidesWith` (which reads `dimensions`/`location` through different paths) disagree. The fix is one owner of the position: `open var location` in `GameObject`, overridden in `VisibleObject` to read and write `area.location`. Two cautions: the base class keeps an unused backing field, and a `GameObject` initialiser that read `location` before `area` is assigned would fail (none does today). `Alive.updateHealthBar` can avoid the design question for the health bar by writing `healthBar.area.location = ...`.
2. `Alive.attackState` setter: `destination = location` when the swing starts. In the old model `destination` and `location` are the same object, so the actor can never be "not at its destination" even when displaced. With immutable points `destination` is a snapshot, so an actor displaced during a swing walks back to the swing position. Compiles; behaviour differs only on displacement.
3. `Alive.considerAttack`: `destination = attackTarget!!.location` while out of range. In the old model `destination` tracks the target's `Point` live, including target moves later in the same tick; afterwards it is the target's position at assignment. The statement runs every tick in that state, so the effect is at most a one-tick lag, but tests with exact pursuit positions should be re-run, not assumed.
4. `Actor(location = p)`, `Alive(...)`, `Projectile(...)` hand the caller's `Point` into `Square` and `GameObject`; the caller's `p` currently moves with the actor. No site in main or tests reads such a retained point after ticking, and after migration the sharing is harmless.
5. `Actor.destination = Point(location)`, `Alive.respawn = Point(location)`, `Movement.Homing`'s `Point(target.location)`, `Intent.clear`'s `Point(actor.location)` and `VisibleObject.lastIndexedLocation` (an `IndexedPosition` snapshot) are already defensive copies; they remain correct and some become redundant.

**Issue-#8 simplifications MyGameTools gains** (all optional, none required to compile):

- `ZoneGrid.origin = Point(space.bounds.location)` can read the immutable `Point` directly; the "copied at construction because the space's own Point is mutable" KDoc goes.
- `UnzonedPointException.point = Point(point)` needs no copy; `UnzonedPointExceptionTest` (2 tests) loses its mutate-the-original premise and becomes an identity or equality assertion.
- `Zone.bounds`, `Space.bounds` and `TiledMap.bounds` can be typed `AxisAlignedBox` (read-only `min`/`size`). That is a source break for MyGameTools' own consumers and for the 15 test lines in 6 files that write `bounds.location`/`bounds.dimensions`; `ZoneGrid` reads `bounds.location`/`dimensions` in 3 lines. It belongs in the same MyGameTools major as the dependency bump, not a separate one.
- Comments that become false and should be rewritten: `Alive` ("sizing and positioning it never mutates the actor's own geometry (which shares those objects)"), `VisibleObject.lastIndexedLocation`, `Zone` ("shared, mutable GeneralTools geometry").

**Planning estimate, MyGameTools migration:** about 25 files and 150 to 200 changed lines. Roughly 45 are one-line mechanical edits (the 40 mutation sites and 2 `Color(` calls plus the dependency line in `build-logic`); about 20 are the `GameObject`/`VisibleObject` design change; about 80 to 130 are test rewrites whose premise disappears (`UnzonedPointExceptionTest`, the two `MapDefinitionTest` aliasing tests, `ZoneTest` "mutating a zone's bounds", the `SpatialIndexQueryLawsTest` move loop that needs a mutable list of replaced points) and the optional #8 typing. **Silent shadowing (source-read, decoded).** `UI.kt` defines `fun Color.lightened(fraction: Double = 0.35): Color` using `toInt()` (truncation) and its `UiTest` expects `Color(100,100,100,128).lightened(0.5) == Color(177,177,177,128)`. ## 4. How comparable projects do it

- **Staging a breaking major by pre-release.** Okio published `3.0.0-alpha.1` to `3.0.0-alpha.11` on Central before `3.0.0`; Ktor published `3.0.0-beta-1`, `-beta-2`, `-rc-1`, `-rc-2`; kotlinx.coroutines published `1.11.0-rc01` and `-rc02` (Central `maven-metadata.xml`, read 2026-10-18, claim 4). Those libraries have many external consumers who cannot be tested by the maintainer. Okio's own `3.0.0` notes tell most users to change only the version and label the one binary break explicitly ([idiomatic-kotlin-api-mechanics.md](idiomatic-kotlin-api-mechanics.md) F8).
- **Staged upload instead of a pre-release.** Coil's `publish_remote.sh` runs `./gradlew publishToMavenCentral` and finishes with a manual Publish click; the JetBrains multiplatform library template uses the same DSL ([kmp-maven-central-publishing.md](kmp-maven-central-publishing.md) section 4). Sonatype documents referencing a validated bundle as a dependency before release (claim 5).
- **Clean break, no deprecation cycle.** The Kotlin API guidelines advise a deprecation cycle; the Okio and Ktor majors above remove and rename in the major itself. The release's own notes should say the breaks are clean ([idiomatic-kotlin-api-mechanics.md](idiomatic-kotlin-api-mechanics.md) pitfall 10).
- **Idioms for the immutable move.** Kotlin rewrites `a += b` to `a = a + b` when `plusAssign` is absent and errors on ambiguity when both exist on a `var` (claim 6); every comparable geometry library returns new values and offers `copy(x, y)` ([immutable-geometry-model.md](immutable-geometry-model.md) 3.1). A member beats an extension of the same signature (claim 3), which is the shadowing trap in 3.3.

## 5. Pitfalls and regrets

1. **A mechanical `val` to `var` is the dangerous migration.** It compiles and desynchronises the position from the drawn box. The migration notes must name shared `Point` holders and show the single-owner override.
2. **Assignments that used to alias become snapshots.** `destination = target.location` compiles and silently stops tracking. Search for assignments of a `Point` read from another object, not only for mutators.
3. **Binary mixing with an older consumer library.** `api` dependencies on GeneralTools mean `gametools` 5.0.0 and GeneralTools 3.0.0 must never meet in one resolution. State it in the release notes; MyGameTools consumers should not add GeneralTools 3.0.0 directly until a MyGameTools release built on it exists.
4. **Members shadow downstream extensions.** The client's `Color.lightened` is the live example; any future downstream `Point.plus` or `Point.copy` extension would behave the same way after 3.0.0.
5. **Composite-build success is not published-artifact success.** Included builds substitute the project's own variants, not the published `.module`, POM, signatures or stdlib requirements (claim 7; [kmp-maven-central-publishing.md](kmp-maven-central-publishing.md) F9).
6. **`languageVersion` is a contract with the oldest consumer.** Raising the pin to 2.3 would break MyGameClient's Kotlin 2.1.20 and is not caught by any in-repo test.
7. **A pre-release is permanent and is not the release.** The final `3.0.0` bytes differ from an `-rc` build (version string in every file, signatures, checksums); a green pre-release proves the process, not the final artifact. Central never removes or modifies a published component (claim 8).
8. **Tests that prove defensive copies become vacuous.** Deleting them is right; keeping `assertNotSame` on freshly constructed values is harmless but proves nothing.
9. **Stale facts in the issue.** The issue states MyGameTools is on 2.0.1; the published `gametools:5.0.0` is, `master` is on 2.2.0. It also lists `logging/` as common-ready, whereas the package is removed.

## 7. Load-bearing claims

1. **A Kotlin compiler reads metadata up to the next minor.** At tag `v2.1.20`, `MetadataVersion.kt`: "`// * Compiler of deployVersion X (INSTANCE) with LV Y (metadataVersionFromLanguageVersion)` / `//   * can read metadata with version <= max(X+1, Y)`", `val INSTANCE = MetadataVersion(2, 1, 0)`, `val INSTANCE_NEXT = INSTANCE.next()`, `fun next(): MetadataVersion = if (major == 1 && minor == 9) MetadataVersion(2, 0, 0) else MetadataVersion(major, minor + 1, 0)`. Source: <https://github.com/JetBrains/kotlin/blob/v2.1.20/core/metadata/src/org/jetbrains/kotlin/metadata/deserialization/MetadataVersion.kt>, tag `v2.1.20`. (The same rule at `v2.2.0` is claim 2 of [kmp-build-and-kotlin-compat.md](kmp-build-and-kotlin-compat.md).)
2. **Gradle picks the highest requested version.** "Gradle considers all requested versions across the dependency graph and, by default, selects the highest version." Source: <https://docs.gradle.org/9.0.0/userguide/graph_resolution.html>, Gradle 9.0.0 docs, read 2026-10-18 (extracted by a summarising fetch).
3. **A member wins over an extension.** "If a class has a member function and there's an extension function with the same receiver type, the same name, and compatible arguments, the member function takes precedence." Source: <https://kotlinlang.org/docs/extensions.html>, read 2026-10-18 (extracted by a summarising fetch).
4. **Central carries pre-releases of earlier majors.** `maven-metadata.xml` lists `3.0.0-alpha.1` through `3.0.0-alpha.11` then `3.0.0` for `com/squareup/okio/okio`; `3.0.0-beta-1`, `3.0.0-beta-2`, `3.0.0-rc-1`, `3.0.0-rc-2`, `3.0.0` for `io/ktor/ktor-server-core`; `1.11.0-rc01`, `1.11.0-rc02`, `1.11.0` for `org/jetbrains/kotlinx/kotlinx-coroutines-core`. Sources: <https://repo1.maven.org/maven2/com/squareup/okio/okio/maven-metadata.xml>, <https://repo1.maven.org/maven2/io/ktor/ktor-server-core/maven-metadata.xml>, <https://repo1.maven.org/maven2/org/jetbrains/kotlinx/kotlinx-coroutines-core/maven-metadata.xml>, read 2026-10-18.
5. **A validated bundle can be tested before release; publishing types; dropping.** "Once a bundle has been validated it can be referenced as a dependency in your build tool of choice."; "USER_MANAGED: (default) a deployment will go through validation and require the user to manually publish it via the Portal UI"; "If a deployment is in a VALIDATED or FAILED deployment state, it is possible to drop the deployment". 6. **Augmented assignment compiles through `plus`; both operators on a `var` is an error.** "If the corresponding binary function (that means `plus()` for `plusAssign()`) is available too, `a` is a mutable variable, and the return type of `plus` is a subtype of the type of `a`, report an error (ambiguity)." and "Otherwise, try to generate code for `a = a + b` (this includes a type check: the type of `a + b` must be a subtype of `a`)." 7. **Composite builds.** `--include-build` "turns the executed build into a composite, substituting dependencies from the included build into the executed build."; Gradle can "substitute project dependencies for any external dependency matching `${project.group}:${project.name}`"; explicit substitutions are needed when "the publication coordinates don't match `${project.group}:${project.name}`". Source: <https://docs.gradle.org/9.0.0/userguide/composite_builds.html>, read 2026-10-18 (extracted by a summarising fetch).
8. **Central immutability.** "we do not remove or modify components once they are publicly available." and "the best path forward is to publish a new release of the component with a fix for the bug." Source: <https://central.sonatype.org/publish/requirements/immutability/>, read 2026-10-18 (extracted by a summarising fetch).
