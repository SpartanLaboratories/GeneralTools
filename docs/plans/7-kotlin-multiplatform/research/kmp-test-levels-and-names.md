# Test layout, level selection and test names across `jvm`, `js` and `wasmJs`

- **Issue:** [SpartanLaboratories/GeneralTools#7](https://github.com/SpartanLaboratories/GeneralTools/issues/7).
- **Date read:** 2026-10-16. Repo baseline: branch `feat/issue-7-kotlin-multiplatform`, tests as of `master` @ `17d30bc` (185 `@Test` methods, 182 of them backtick-quoted).
- **Pinned sources:** JetBrains/kotlin tag `v2.4.21` (commit `9180ce6a7a7d3627f88b424717583f28ddca052d`, the Kotlin Gradle plugin version in [kmp-build-and-kotlin-compat.md](kmp-build-and-kotlin-compat.md)); `Kotlin/kotlin-web-helpers` tag `v3.5.4`; Gradle docs for 9.8.1 (current at the date read; the wrapper is 9.0.0).
- **Method limits:** nothing was built or run. KGP, compiler and `kotlin-test` behaviour is read from source at the pinned tag. What this means for confidence is in *Gaps*.

## 1. Question

How should the GeneralTools tests be laid out and selected by level across `jvm`, `js` (Node/Mocha) and `wasmJs` (Node, KGP's own runner) in a Kotlin Multiplatform build, and do the 182 existing backtick-quoted test names compile and report correctly on every target?

An answer has to meet these requirements:

- Tests follow a 5-level hierarchy, each level in its own package segment under a `testing` root, mirroring the production package below it: level 1 `testing.gating`, level 2 `testing.component`, level 3 `testing.integration`, level 4a `testing.deterministic`, level 4b `testing.e2e`, level 4c `testing.nonfunctional`, level 5 `testing.uat`. Production packages are `com.spartanlabs.geometry` and `com.spartanlabs.generaltools`, so the level-2 test of `com.spartanlabs.geometry.Point` is `com.spartanlabs.testing.component.geometry.PointTest`. One test class per file.
- Each level can be run, skipped or gated on its own, bound to a test task or a filter, so CI can run levels 1-2 on every commit and keep 4-5 for release gates. Every target's test task (`jvmTest`, `jsNodeTest`, `wasmJsNodeTest`) can select levels by package filter.
- Pure tests go to `commonTest`; file, URL, AWT and slf4j tests go to `jvmTest`. The stray class `Point` (package `geometry`) folds into `PointTest`; the empty `MiscKtTest` is deleted; `logback-test.xml` keeps serving the JVM tests. `src/test/resources/keys.txt` is already deleted on `master`, and moving the test sources leaves it alone.
- The existing component tests carry JUnit `@Tag` and log through slf4j `LoggerFactory`; neither exists in common code.

## 2. Bottom line

- **Select levels with one Gradle property that adds a package filter to every test task:** `tasks.withType<AbstractTestTask>().configureEach { ... filter.includeTestsMatching("com.spartanlabs.testing.$level.*") }`, driven by `-PtestLevel=component` (comma-separated for several). `jvmTest` (a Gradle `Test`), `jsNodeTest` (`KotlinJsTest`, Mocha) and `wasmJsNodeTest` (`KotlinJsTest`, KGP's `KotlinWasmNode`) all pass Gradle's include/exclude patterns to their runner, and a trailing-`*` package pattern matches on both web runners. `./gradlew check` with the property unset still runs every level on every target.
- **Set `filter.isFailOnNoMatchingTests = false` on all of them.** The JS and Wasm tasks already do (KGP's `KotlinTest` base class sets it in `init`); the JVM `Test` default is `true`, so an empty level on `jvmTest` would fail the build without the line. A level with no tests on a target then ends green with zero tests.
- **Per-level, per-target tasks (`testRuns.create("component")`) are rejected:** each created run is wired into `check` and `allTests`, so `check` would execute every test again for every level; `KotlinJsTest` has an `internal` constructor, so web tasks cannot be registered by hand the way MyGameTools registers `Test` tasks. Aggregate tasks that set filters on the three shared tasks are rejected because a filter is per-task state, so two levels in one invocation would collide. Separate compilations per level are rejected as seven compile-and-link chains per target for no gain.
- **Keep all 182 backtick names unchanged.** The only characters present are letters, digits, spaces, hyphens and five apostrophes. Kotlin 2.4.21 (`languageVersion` >= 2.1) accepts arbitrary characters in backticked names on Kotlin/JS and Kotlin/Wasm; both runners carry names as string literals and escape `'` in TeamCity messages; the Gradle report splits class from method at the last `.`, and no name contains a dot. Coil, which runs `commonTest` on `wasmJs`, ships spaced backtick names.
- **Drop `@Tag` and slf4j from the moved tests.** The package already encodes the level, `@Tag` cannot be written in common code, and `kotlin.test` has no tag or assumption API. `jvmTest` classes may keep JUnit `Assumptions` (`UserActionsTest`) because `kotlin-test-junit5` brings `junit-jupiter-api` on the JVM test classpath.
- **Levels for the classes not yet in a level package:** `PointTest`, `SquareTest`, `TwoDoublesTest` and the pure part of `MiscTest` are level 2 (`commonTest`); `UserActionsTest` and the `read` test are level 3 (`jvmTest`); the `asURL` and `Logger.time` tests are level 2 (`jvmTest`); the stray `Point` folds into level-2 `PointTest`. Details in section 6.

## 3. Findings

Tiers: **Consensus** = official doc or several independent credible sources; **Practice** = what mature libraries visibly do; **Source-read** = read from source at the pinned tag, not executed; **Opinion** = one source.

### F1. Source-set directories and resources (Consensus + Source-read, KGP 2.4.21)

- KGP creates every Kotlin source set with `src/<sourceSetName>/kotlin` and `src/<sourceSetName>/resources` as default directories (`KotlinSourceSetFactory.defaultSourceFolder`, `DefaultKotlinSourceSetFactory.setUpSourceSetDefaults`, [KotlinSourceSetFactory.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/tools/kotlin-gradle-plugin/src/common/kotlin/org/jetbrains/kotlin/gradle/plugin/sources/KotlinSourceSetFactory.kt)). So the layout is `src/commonMain/kotlin`, `src/commonTest/kotlin`, `src/jvmMain/kotlin`, `src/jvmTest/kotlin`, and JVM test resources in `src/jvmTest/resources` (`logback-test.xml` goes there).
- The Kotlin docs state "`commonTest` is a counterpart for `commonMain` and compiles to all of the declared targets, allowing you to write common tests. Platform-specific test source sets, such as `jvmTest`, are used to write platform-specific tests" and "To run tests for a particular target, use the `<targetName>Test` task" ([Source set docs](https://kotlinlang.org/docs/multiplatform/multiplatform-discover-project.html), read 2026-10-16). The page does not spell out the directory paths; they come from the KGP source above.
- Package directories need not match packages (the current repo already has `src/test/kotlin/geometry/PointTest.kt` in package `com.spartanlabs.geometry`), but the ten level-2 classes already follow `com/spartanlabs/testing/<level>/<pkg>/`; the moved files should too.
- The same fully qualified class name in `commonTest` and `jvmTest` is a redeclaration error, so a class that splits between common and JVM needs distinct class names (section 6).

### F2. `kotlin-test` in common code (Consensus, Kotlin 2.4.21)

- Dependency: "Add the `kotlin-test` dependency to the `commonTest` source set, so that the Gradle plugin can infer the corresponding test dependencies for each test source set" ([gradle-configure-project](https://github.com/JetBrains/kotlin-web-site/blob/master/docs/topics/gradle/gradle-configure-project.md), read 2026-10-16). In the Kotlin DSL: `commonTest.dependencies { implementation(kotlin("test")) }`.
- JVM variant: "For Kotlin/JVM, Gradle uses JUnit 4 by default. Therefore, the `kotlin("test")` dependency resolves to the variant for JUnit 4"; calling `useJUnitPlatform()` on the test task selects JUnit 5. In a KMP project the docs do this through `jvm { testRuns["test"].executionTask.configure { useJUnitPlatform() } }`. `jvmTest` is a `KotlinJvmTest`, a subclass of Gradle's `Test`, so `tasks.withType<Test>().configureEach { useJUnitPlatform() }` is equivalent ([KotlinJvmTest.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/tools/kotlin-gradle-plugin/src/common/kotlin/org/jetbrains/kotlin/gradle/targets/jvm/tasks/KotlinJvmTest.kt)). The current build already calls `useJUnitPlatform()`; it must be kept, because the existing tests import `org.junit.jupiter.api.*`.
- Common annotations are exactly four: `@Test`, `@Ignore`, `@BeforeTest`, `@AfterTest` (`public expect annotation class ...` in [annotations-common/Annotations.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/kotlin.test/annotations-common/src/main/kotlin/kotlin.test/Annotations.kt)). The suite uses only `@Test` (plus the JUnit `@Tag` in ten files and `Assumptions.assumeFalse` in one); `@BeforeTest`/`@AfterTest`/`@Ignore` are not used anywhere.
- No tag or assumption API exists in `kotlin.test` (no `assume*` in `Assertions.kt` @ v2.4.21). A JUnit `Tag` could only be reached through an `expect annotation` with a JVM `actual typealias`, which duplicates what the package segment already says. `assumeFalse` is only needed by the two screenshot tests, which are `jvmTest`-only.
- `kotlin-test-junit5` 2.4.21 declares `junit-jupiter-api` 5.10.1 with `compile` scope and `junit-jupiter-engine` 5.10.1 at runtime ([POM](https://repo1.maven.org/maven2/org/jetbrains/kotlin/kotlin-test-junit5/2.4.21/kotlin-test-junit5-2.4.21.pom)), so `jvmTest` code can import `org.junit.jupiter.api.Assumptions` without a separate dependency, as `testApi(kotlin("test"))` does today.
- The Kotlin/JS generator turns `@Test` into a suite/test registration only for **classes** (`TestGenerator.createTestContainer` walks `irFile.declarations` for `IrClass`, with a `// TODO top-level functions`); every existing test is in a class, a test class needs a public or internal no-argument constructor, and a test method may not take parameters.

### F3. Level selection reaches the Node runners on both web targets (Source-read, v2.4.21)

How a Gradle filter becomes a runner argument:

1. `KotlinJsTest` extends `KotlinTest`, which extends Gradle's `AbstractTestTask`. `KotlinTest` exposes `includePatterns` = `filterExt.includePatterns + filterExt.commandLineIncludePatterns` and `excludePatterns` = `filterExt.excludePatterns`, both `@Input`. So `filter.includeTestsMatching`, `filter.excludeTestsMatching` and `--tests` all reach the task ([KotlinTest.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/tools/kotlin-gradle-plugin/src/common/kotlin/org/jetbrains/kotlin/gradle/tasks/KotlinTest.kt)).
2. `KotlinMocha.createTestExecutionSpec` (`js`) and `KotlinWasmNode.createTestExecutionSpec` (`wasmJs`) both build `KotlinTestRunnerCliArgs(include = task.includePatterns, exclude = task.excludePatterns)` and append `cliArgs.toList()` to the Node command line. `KotlinTestRunnerCliArgs.toList()` emits `--include <patterns joined by ,>` and `--exclude <patterns joined by ,>` ([KotlinMocha.kt](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/tools/kotlin-gradle-plugin/src/common/kotlin/org/jetbrains/kotlin/gradle/targets/js/testing/mocha/KotlinMocha.kt), [KotlinWasmNode.kt](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/tools/kotlin-gradle-plugin/src/common/kotlin/org/jetbrains/kotlin/gradle/targets/js/testing/KotlinWasmNode.kt), [KotlinTestRunnerCliArgs.kt](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/tools/kotlin-gradle-plugin/src/common/kotlin/org/jetbrains/kotlin/gradle/targets/js/testing/KotlinTestRunnerCliArgs.kt)). Both run a dry run with the same filter first and fail the task if it exits non-zero.
3. The two runners then parse those arguments with **two different implementations**:

| | `js` (Mocha) | `wasmJs` (KGP's own runner, `KotlinWasmNode`) |
|---|---|---|
| Filter code | `kotlin-web-helpers` npm package: `KotlinTestsFilter.ts`, `CliFiltertingConfiguration.ts` ([@ v3.5.4](https://github.com/Kotlin/kotlin-web-helpers/tree/v3.5.4/src)); installed range `^3.3.0` for KGP 2.4.21, and these files are identical from v3.3.0 to v3.6.0 | Kotlin code inside the `kotlin-test` Wasm klib: `FrameworkTestArguments.parse`, `TeamcityAdapter.enterIfIncluded` ([@ v2.4.21](https://github.com/JetBrains/kotlin/tree/v2.4.21/libraries/kotlin.test/wasm/src/main/kotlin/kotlin/test)); no npm tooling |
| `com.spartanlabs.testing.component.*` | Leading text before the first `*` becomes a `StartsWithFilter`; with nothing after the `*` there is no regex, so it is a pure prefix match on `<package>.<Class>.<test>`. A suite whose name cannot lead to a match is skipped entirely | A pattern whose first character is lowercase goes in the "qualifier" list; a test runs if its class path or full path matches by a hand-written `*` wildcard matcher |
| Pattern forms | exact, `prefix*`, `*suffix`, `a*b`, `!negated`, comma lists, `--exclude` | `Class`, `Class.method`, `Class.*` when the first character is uppercase; `qualifier*` when lowercase; comma lists; `--exclude` |
| Suites outside the filter | not reported (never started) | still reported as empty started/finished suites; only the tests are skipped |
| Space in a pattern | handled (argument vector) | **breaks**: `getArguments()` joins `process.argv` with spaces and splits on spaces again |

   Package patterns have no spaces, no commas and start with a lowercase letter, so they sit in the part of the pattern space where both runners behave the same. A pattern that selects one test by name containing spaces would not work on Wasm.
4. A test's identity is `<package>.<Class>.<function name>` on both web runners, and Gradle sees the same. The compiler emits `suite(<package FQN>) { suite(<ClassName>) { test(<function name>) } }`: `JsTestFunctionTransformer` creates the package suite from `JsStringLiteral(pkg)`; `TestGenerator.generateTestCalls` creates the class suite from `irClass.name.asString()` and each test from `testFun.name.asString()`. `kotlin.test` for Wasm declares the same layout in `TestApi.kt` ("`registerRootSuiteBlock("top-level-package1") { suite("TestClass1", ...)`").

**What KGP's own tests cover.** `MppTestFilteringIT` on `master` (commit `ba0cb575d0c2a90af433d65e6038ec28694bf337`, 2026-08-20; not in the `v2.4.21` tree) exercises `--tests` with a simple class, a fully qualified method, `*Class` and `org.example.project.*` package patterns, and the DSL `includeTestsMatching` / `excludeTestsMatching`, all on `:jvmTest`. For `:jsNodeTest` it only asserts the no-match case. **Package-pattern filtering on `jsNodeTest` and `wasmJsNodeTest` is therefore established from source, not from KGP's own tests, and was not run here** (see *Gaps*).

### F4. What Gradle reports for JS and Wasm tests (Source-read, v2.4.21)

`TCServiceMessagesClient` (settings `prependSuiteName = true`, `testNameSuffix = task.targetName`) builds `"<suite path>.<test name>"`, splits it at the **last** `.` into `className` and `methodName`, and sets the display name to `methodName[<targetName>]` ([TCServiceMessagesClient.kt](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/tools/kotlin-gradle-plugin/src/common/kotlin/org/jetbrains/kotlin/gradle/internal/testing/TCServiceMessagesClient.kt), `ParsedTestName`). For `RayTest."pointAt the origin"` that gives:

| target | `className` | `methodName` | display name |
|---|---|---|---|
| `jvm` | `com.spartanlabs.testing.component.geometry.RayTest` | JUnit's name for the function | `... [jvm]` (`KotlinJvmTest.Executor`) |
| `js` | `com.spartanlabs.testing.component.geometry.RayTest` | `pointAt the origin` | `pointAt the origin[js, node]` |
| `wasmJs` | same | same | `pointAt the origin[wasmJs, node]` |

Consequence for names: **a dot inside a test name moves the class/method split into the name.** No existing name contains a dot.

### F5. Backtick names: which characters are legal where (Consensus + Source-read, v2.4.21)

Characters in the 182 names (from `grep` over `src/test/kotlin/**`): ASCII letters, digits (19 names), spaces, hyphens (34 names, e.g. `0-255`, `T-junction`, `round-trips`, `-1`) and apostrophes (5 names: `point's` x2, `square's`, `instance's` x2). Absent: `#`, parentheses, `=`, `<`, `>`, commas, dots, slashes, colons, semicolons, brackets, backslashes, quotes, `| ? * % & !`, underscores, tabs and any non-ASCII character. The longest name is 73 characters; there are no duplicate names.

- **JVM:** the compiler rejects `. ; [ ] / < > : \` in a name (`JvmConstants.INVALID_CHARS`, [JvmConstants.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/compiler/frontend.common.jvm/src/org/jetbrains/kotlin/resolve/jvm/JvmConstants.kt)) and warns on `? * " | %` (`JvmSimpleNameBacktickChecker`). None of these occur. The existing suite already compiles on the JVM.
- **Kotlin/JS and Kotlin/Wasm:**
  - The JS diagnostic `NAME_CONTAINS_ILLEGAL_CHARS` ("Name contains illegal chars that cannot appear in JavaScript identifier.") is reported by `FirJsNameCharsChecker` only for declarations with a *stable* JS name (`external`, `@JsName`, `@JsExport` ones, via `FirJsStableName.createStableNameOrNull`), and not at all when the language feature `JsAllowInvalidCharsIdentifiersEscaping` is enabled. That feature is `JsAllowInvalidCharsIdentifiersEscaping(KOTLIN_2_1, "KT-31799")` in `LanguageFeature`, i.e. on for every `languageVersion` >= 2.1, and the 2.1.0 changelog lists "KT-31799 Allow non-identifier characters in Kotlin/JS (backquoted properties, `@JsName`)". The planned `languageVersion` of 2.2 is therefore past it. Test functions are not exported or external, so the checker would not reach them regardless.
  - Test names are not identifiers at runtime: they reach the runner as string literals (F3 point 4). The identifier the backend generates for the function is mangled separately; Kotlin's own box test `compiler/testData/codegen/box/mangling/parentheses.kt` (class and function both named `` `()` ``, `// LANGUAGE: +JsAllowInvalidCharsIdentifiersEscaping`) carries `// IGNORE_BACKEND: NATIVE` and no ignore for the JS or Wasm backends, so it is expected to run on both.
  - Older reports that "Kotlin/JS does not compile backticked names with spaces" (KT-18771-era threads on kotlinlang Slack, undated) predate 2.1 and the IR backend and do not apply to 2.4.21.
- **Runner escaping:** both runners escape TeamCity message text: Mocha path `tcEscape` in [teamcity-format.js @ v3.5.4](https://github.com/Kotlin/kotlin-web-helpers/blob/v3.5.4/src/teamcity-format.js) escapes `|`, newlines, `[`, `]` and `'`; the Wasm `TeamcityAdapter.tcEscape` does the same set. Spaces, hyphens and digits need no escaping, so the five apostrophe names report correctly.
- **Conventions:** "In tests (and **only** in tests), you can use method names with spaces enclosed in backticks. Note that such method names are only supported by Android runtime from API level 30." ([coding-conventions](https://github.com/JetBrains/kotlin-web-site/blob/master/docs/topics/coding-conventions.md), read 2026-10-16). There is no Android target, so the caveat does not apply.

Verdict: **all 182 names are legal and report correctly on every target.** No rename is needed. Renaming would only help a single-test selection by name on Wasm (space splitting, F3), which package-level selection does not use.

### F6. A level with no tests on a target (Source-read + KGP integration test)

- Gradle's `TestFilter.isFailOnNoMatchingTests` "Returns whether the task should fail if no matching tests where found. The default is true." ([TestFilter](https://docs.gradle.org/current/javadoc/org/gradle/api/tasks/testing/TestFilter.html), Gradle 9.8.1). `KotlinTest.init` sets it to `false` for every `KotlinJsTest`; KGP's own `MppTestFilteringIT.testTargetBehavioralAsymmetryOnNoMatchingTests` asserts `:jvmTest` fails and `:jsNodeTest` succeeds on a filter that matches nothing, and `testDisableFailOnNoMatchingTests` shows `project.tasks.withType(Test::class.java).configureEach { it.filter.isFailOnNoMatchingTests = false }` as the way to switch it off on the JVM.
- Gradle 9 adds a second rule: "When test sources are present and no filters are applied, the test task will now fail with an error if it runs but doesn't discover any tests. ... If filters are applied, the outcome depends on the failOnNoMatchingTests property." ([Upgrading to Gradle 9](https://docs.gradle.org/current/userguide/upgrading_major_version_9.html)). With a level filter applied, `failOnNoMatchingTests = false` therefore governs; with no filter, every target has tests (all of `commonTest`), so the new rule does not trigger.
- A filtered-to-nothing web task is not free: it still compiles and links the test klib, runs the npm/Node setup and starts Node twice (dry run, run). The only mechanism that makes an empty level free is a separate compilation per level, whose test task is skipped when its input file does not exist (`testJs.onlyIf { inputFile exists }` in `KotlinJsIrSubTarget`); that is option (d) in section 4.

### F7. `check`, `allTests` and the limits of `--tests` (Source-read, v2.4.21)

- `KotlinTestsRegistry.registerTestTask` calls `project.tasks.named(CHECK_TASK_NAME).dependsOn(taskHolder)` for every registered target test task and feeds `allTests`, so with `jvm()`, `js { nodejs() }` and `wasmJs { nodejs() }` `./gradlew check` runs `jvmTest`, `jsNodeTest` and `wasmJsNodeTest`, each over all of `commonTest` plus its own source set. This is what remains when no level is selected ([KotlinTestsRegistry.kt](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/tools/kotlin-gradle-plugin/src/common/kotlin/org/jetbrains/kotlin/gradle/testing/internal/KotlinTestsRegistry.kt)).
- `allTests` and the per-target aggregates (`jsTest`, `wasmJsTest`) are `KotlinTestReport`, a subclass of Gradle's `TestReport`, not of `AbstractTestTask` (`abstract class KotlinTestReport : TestReport(), UsesTestReportService`). They have no filter and no `--tests` option; `--tests` attaches to the task named just before it on the command line, so a level cannot be chosen with `--tests` on `check` or `allTests`. A property-driven filter on the leaf tasks avoids this.
- The test tasks' names are `jvmTest`, `jsNodeTest`, `wasmJsNodeTest` (`KotlinJsIrSubTarget.configureTestsRun` composes `target + subtarget + "Test"`).

## 4. How comparable projects do it

|---|---|---|

No public KMP library read for this report splits or filters its *JS/Wasm* test tasks by a package/level scheme; the precedent for that part is KGP's own `MppTestFilteringIT` for the filter DSL and the Kotlin sources for the runners.

### Options compared

| | (a) per-level, per-target tasks via `testRuns.create(level)` | (b) one `-PtestLevel` property adds a package filter to every test task | (c) per-level aggregates configure filters on the three shared tasks | (d) a compilation or source set per level |
|---|---|---|---|---|

## 5. Pitfalls and regrets

- **`--tests` with `check`, `allTests`, `jsTest` or `wasmJsTest` does not work.** Those are lifecycle or `TestReport` tasks without the option (F7). Undated Kotlin Slack threads report `./gradlew jsNodeTest --tests ...` running everything; those predate the IR runner and the source above shows the arguments are passed, but it was not re-run here.
- **A filter matching nothing still costs a full web build and two Node launches.** For a JVM-only level (level 3 here), invoke `jvmTest` rather than `check` in CI.
- **Wasm and JS filter semantics differ in the corners** (F3 table): case of the first character, space splitting, suites reported or not. Package patterns avoid every corner; a pattern starting with an uppercase letter is read as `Class.method` on Wasm and Gradle's simple-name form on the JVM.
- **The JVM `Test` default is `failOnNoMatchingTests = true`:** forgetting `filter.isFailOnNoMatchingTests = false` makes `-PtestLevel=uat` fail `jvmTest` while the web tasks pass.
- **Dots in test names.** A name containing `.` is split into class and method at the dot in the Gradle report for the web targets (F4). Keep dots out of new test names.
- **Same class name in `commonTest` and `jvmTest`** is a redeclaration; a class that must split needs two names.
- **Test classes in `commonTest` must have a public or internal no-arg constructor and no top-level `@Test` functions** on Kotlin/JS (F2).
- **Typos in a level name would silently select nothing** with `failOnNoMatchingTests = false`; validate the property value against the known level list and fail the build on an unknown level.
- **Dead `@Tag` imports** in the moved files break `commonTest` compilation on JS and Wasm.
- **Mocha's per-test timeout is 2 s by default** (`KotlinMocha.DEFAULT_TIMEOUT = "2s"`); pure tests do not approach it, but any future slow test on `js` needs `useMocha { timeout = ... }`.

**Selection.** Add this to `build.gradle.kts` (reading the property through a provider keeps it a configuration-cache input; the level list lives in one place):

```kotlin
import org.gradle.api.tasks.testing.AbstractTestTask

val testLevels = listOf("gating", "component", "integration", "deterministic", "e2e", "nonfunctional", "uat")

// -PtestLevel=component or -PtestLevel=gating,component ; unset runs every level.
val selectedTestLevels = providers.gradleProperty("testLevel")
    .map { value -> value.split(',').map(String::trim).filter(String::isNotEmpty) }
    .orElse(emptyList())

tasks.withType<AbstractTestTask>().configureEach {
    // A level with no tests on a target is a green no-op, not an error (jvmTest defaults to failing).
    filter.isFailOnNoMatchingTests = false
    selectedTestLevels.get().forEach { level ->
        require(level in testLevels) { "Unknown test level '$level'; expected one of $testLevels" }
        filter.includeTestsMatching("com.spartanlabs.testing.$level.*")
    }
}
```

`AbstractTestTask` covers `jvmTest`, `jsNodeTest` and `wasmJsNodeTest` and nothing else, so no KGP-internal type is referenced. CI recipes:

- every commit: `./gradlew check -PtestLevel=gating,component` (all three targets, levels 1-2);
- a JVM-only level: `./gradlew jvmTest -PtestLevel=integration`;
- release gate: `./gradlew check` (every level, every target), or name the gate levels.

**Why this and not the alternatives.** The filter is the only selector that spans `commonTest` (tags need JUnit) and the only one that all three leaf tasks already understand. Per-level tasks (a) cannot be created for the web targets except through `testRuns`, which re-adds every test to `check` for each level; aggregates that set the filter (c) fight over per-task state; compilation-per-level (d) multiplies web link time by seven. The cost accepted: no named `componentTest` task, and a filtered-to-nothing web task still builds and launches Node, which the JVM-only-level recipe avoids.

**Names.** Keep all 182 backtick names. Add no rename step. For new tests, avoid `.` in names, and keep spaces out of any *pattern* meant for `wasmJsNodeTest`.

**Tests that move.** Remove `@Tag` and the slf4j `LoggerFactory` field from the files going to `commonTest` (logging is covered in [kotlin-logging-adoption.md](kotlin-logging-adoption.md); the 173 `log.` calls in the tests moving to `commonTest` go with it, of 183 in the test tree); behaviour of the moved assertions on each target is in [cross-platform-behaviour-parity.md](cross-platform-behaviour-parity.md). Keep the file KDoc line "Level 2 (Isolated Component Behaviour)" on each class.
