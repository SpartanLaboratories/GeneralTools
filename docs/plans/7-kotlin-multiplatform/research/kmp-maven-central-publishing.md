# R2 - Publishing GeneralTools 3.0.0 (KMP) to Maven Central with vanniktech, and testing it before the irreversible release

- **Researcher:** R2, for [SpartanLaboratories/GeneralTools#7](https://github.com/SpartanLaboratories/GeneralTools/issues/7). Informs decision **D2**.
- **Date read:** 2026-10-15. Repo baseline: `master` @ `6926069`, Gradle wrapper 9.0.0.
- **Method limits:** nothing was built, published or run (brief boundary). Evidence is plugin source at tag `0.37.0` (shallow clone, read only, deleted afterwards), KGP/Gradle source at pinned tags, official Sonatype / Kotlin / Gradle docs, and the published Maven Central artifacts of comparable libraries (downloaded and listed read-only). Secret values were not read; only Gradle property names appear below.

## 1. Question

How should GeneralTools 3.0.0 be published to Maven Central as a KMP library (jvm 17 + js + wasmJs, same coordinates `io.github.spartanlaboratories:GeneralTools`) with the vanniktech plugin, which plugin version should it use, and what is the cheapest sequence of steps that lets the maintainer verify the real published artifacts (all variants, and a downstream build) before the irreversible release click.

## 2. Bottom line

- **Use vanniktech `0.37.0` (latest release, 2026-06-21).** Minimum Gradle 9.0.0 (this repo's wrapper), minimum KGP 2.2.0, "tested up to" KGP 2.4.0. `0.36.0` also works with KGP 2.4.x in practice (JetBrains' own `multiplatform-library-template` pairs 0.36.0 with KGP 2.4.10; Coil 3.6.3 pairs 0.37.0 with 2.4.10), so this is a low-risk bump, and 0.37.0 adds the one thing the staged flow wants: it logs the Central deployment id after upload. The only 0.36 -> 0.37 behaviour change is slimmer checksums (md5+sha1 only, no `.asc.*` checksums), which Central does not require.
- **The existing DSL carries over almost unchanged.** `publishToMavenCentral()`, `signAllPublications()`, `coordinates(...)` and the `pom { }` block stay; the plugin auto-detects `org.jetbrains.kotlin.multiplatform` and, with no Dokka applied, publishes an **empty javadoc jar plus a sources jar on every publication**. Signing with `signing.keyId` / `signing.password` / `signing.secretKeyRingFile` is documented and tested by the plugin (including under `--configuration-cache`; config-cache support for publishing arrived in 0.34.0). An explicit `configure(KotlinMultiplatform(javadocJar = JavadocJar.Empty(), sourcesJar = SourcesJar.Sources()))` is optional; I recommend it only to pin the empty-javadoc policy against a future Dokka plugin silently switching it.
- **Exact coordinates** (project `rootProject.name = "GeneralTools"`, which is already so): `GeneralTools` (root `kotlinMultiplatform` publication, a metadata jar with no classes plus a `.module` that redirects), `GeneralTools-jvm`, `GeneralTools-js`, `GeneralTools-wasm-js`, all `io.github.spartanlaboratories:...:3.0.0`. Target suffixes are lower-cased and dash-separated; the project-name part keeps its case (`GeneralTools-jvm` is the same pattern as `CanvasLib-jvm` on Central). Keep `coordinates` artifactId identical to `rootProject.name`, and keep the default target names `js()` and `wasmJs()`.
- **Central accepts what KMP produces.** Empty (manifest-only) javadoc jars are accepted in practice on every publication (Okio 3.18.2 ships 261-byte javadoc jars for root, jvm, js and wasm-js, published through this same plugin) and Sonatype states placeholder jars are allowed. `klib` POM packaging, `.module` files and the extra `-kotlin-tooling-metadata.json` all pass.
- **Staged flow for 3.0.0 only: upload without release, then test the validated deployment, then click Publish.** Run `./gradlew publishToMavenCentral` (not `publishAndReleaseToMavenCentral`): it uploads one bundle as `USER_MANAGED`, so nothing reaches Central. Once the Portal shows it as VALIDATED, point a throwaway consumer at `https://central.sonatype.com/api/v1/publisher/deployments/download/` with a Bearer header (Sonatype's "Manually Testing a Deployment Bundle"); vanniktech has no support for that, it is repository config in the consumer. A bad bundle is dropped (`./gradlew dropMavenCentralDeployment --deployment-id=<id>`, or in the Portal). Releasing is one click in the Portal. Cost versus today: one extra command, one UI click, and a consumer-side repository stanza. Before that, a free local rehearsal to a **file repository inside `build/`** (not `~/.m2`) catches almost everything else.
- **Plain-Maven consumers get an empty artifact from `GeneralTools:3.0.0`** (root jar has no `.class` files, root POM has only runtime-scope stdlib/logging deps and no pointer to `-jvm`). They must switch to `GeneralTools-jvm`, as B9 already states. Okio solved the same migration (JVM-only to KMP under the same coordinates) with a ~15-line `pom.withXml` hack that makes the root POM depend on `-jvm`; that is an available opt-in that does not touch B9's coordinates, flagged for the planner, not recommended by default.

## 3. Findings

Tiers: **Consensus** = spec, official docs, or several independent credible sources. **Practice** = what mature libraries visibly do. **Opinion** = one source.

### F1. vanniktech versions: what differs between 0.36.0, 0.37.0 and latest (Consensus; changelog + source)

- Releases (GitHub, read 2026-10-15): `0.37.0` 2026-06-21 is the latest; `0.36.0` 2026-01-18 (changelog date 2026-01-13); `0.35.0` 2025-11-11. No newer tag exists; `main` has unreleased commits (CHANGELOG `UNRELEASED` lists the same minimums and tested-up-to as 0.37.0). ([releases](https://github.com/vanniktech/gradle-maven-publish-plugin/releases), [CHANGELOG @ 0.37.0](https://github.com/vanniktech/gradle-maven-publish-plugin/blob/0.37.0/CHANGELOG.md); claim 1.)
- Minimums in both 0.36.0 and 0.37.0: JDK 17, Gradle 9.0.0, AGP 8.13.0, KGP 2.2.0. Tested up to: 0.36.0 -> Gradle 9.3.0, KGP 2.3.0 / 2.3.20-Beta1; 0.37.0 -> Gradle 9.6.0, KGP 2.4.0, JDK 26. So Gradle 9.0.0 sits exactly on the minimum for both; KGP 2.4.21 is inside the tested range for neither as an exact version, but 2.4.0 is tested for 0.37.0 only (claim 1).
- 0.37.0 changes (the whole list): redundant checksums are excluded by default (checksums of `.asc` files and `sha256`/`sha512`; default published checksums `md5,sha1`, configurable via `checksums(...)` / `mavenCentralChecksums`), and "Maven Central deployment id is being logged after upload" (claim 1). Our 2.2.0 on Central (built with 0.36.0) carries all checksum types, including `.asc.md5/.sha1/.sha256/.sha512`; Okio 3.18.2 (built with 0.37.0) carries none of the `sha256`, `sha512` or `.asc.*` ones (listing read 2026-10-15).
- 0.36.0 changes that matter and that a boolean-era snippet would trip over: `configure(KotlinMultiplatform(...))` now takes `JavadocJar` and `SourcesJar` types, the `Boolean` forms are `@Deprecated`; "When calling `configure(...)` manually ... and not passing `javadocJar` explicity, the plugin now defaults to publishing an empty javadoc jar"; `validateDeployment` became an enum (`VALIDATED` default; `PUBLISHED`, `NONE`); Dokka v1 support removed (claim 3). The brief's `sourcesJar = true` spelling is the deprecated overload; use `SourcesJar.Sources()`.
- **Pairings in the wild with KGP 2.3/2.4** (Practice): JetBrains `Kotlin/multiplatform-library-template` @ `2260964` (2026-08-07): `kotlin = "2.4.10"`, `vanniktech-maven-publish = "0.36.0"`, DSL `publishToMavenCentral(); signAllPublications(); coordinates(group.toString(), "library", version.toString())`. Coil 3.6.3 (2026-09-18): KGP 2.4.10 + 0.37.0. Kermit 2.2.0 (2026-09-08): KGP 2.3.21 + 0.36.0. Okio `parent-3.18.2`: KGP 2.2.21 + 0.37.0. (claim 18.) I found no open vanniktech issue about KGP 2.4 (searched "Kotlin 2.4", "wasm"). Absence of evidence, not a test.
- **Verdict on version:** 0.37.0. The "tested up to 2.4.0" statement is the only documented 2.4 coverage and 0.36.0's real-world 2.4.x use (JetBrains template, Turbine on 2.4.20) shows the risk is small either way; 0.37.0 gives the deployment-id log line the staged flow benefits from.

### F2. KMP support: automatic detection versus `configure(KotlinMultiplatform(...))` (Consensus; source @ 0.37.0)

- `com.vanniktech.maven.publish` runs `configureBasedOnAppliedPlugins()` in `afterEvaluate`; for `org.jetbrains.kotlin.multiplatform` it calls `configure(KotlinMultiplatform(javadocJar, sourcesJar, variants))` with defaults `JavadocJar` = Dokka if a Dokka plugin is applied, else for KMP `JavadocJar.Empty()`, and `SourcesJar.Sources()` (`MavenPublishBaseExtension.configureBasedOnAppliedPlugins` and `defaultJavaDocOption`; claim 2). A manual `configure(KotlinMultiplatform(...))` is therefore only needed to choose Dokka, or to pin Empty.
- `KotlinMultiplatform(javadocJar: JavadocJar = JavadocJar.Empty(), sourcesJar: SourcesJar = SourcesJar.Sources(), androidVariantsToPublish: List<String> = listOf("release"))`. It "Uses the default publications that gets created by that plugin, including the automatically created `-sources` jars"; it adds an empty or Dokka javadoc jar to **each** publication (`project.mavenPublications { it.withJavadocJar(javadocJar, project, multipleTasks = true) }`) and calls `KotlinMultiplatformExtension.withSourcesJar(...)`. `androidVariantsToPublish` is irrelevant without an Android target ([Platform.kt @ 0.37.0](https://github.com/vanniktech/gradle-maven-publish-plugin/blob/0.37.0/plugin/src/main/kotlin/com/vanniktech/maven/publish/Platform.kt), symbol `KotlinMultiplatform`; claim 2).
- The plugin applies the `signing` plugin itself and signs every `MavenPublication`; for KMP it additionally wraps each `Sign` task's signature type in a `DirectorySignatureType` as a workaround for KT-61313 / gradle#26132 ([MavenPublishBaseExtension.signAllPublications @ 0.37.0](https://github.com/vanniktech/gradle-maven-publish-plugin/blob/0.37.0/plugin/src/main/kotlin/com/vanniktech/maven/publish/MavenPublishBaseExtension.kt); claim 4).

### F3. Signing with `signing.keyId` / `signing.password` / `signing.secretKeyRingFile`, and configuration cache (Consensus for support; the combination with this repo is untested here)

- The `signAllPublications()` KDoc documents exactly this mode: "Signing can be done using a local `secring.gpg` by setting these Gradle properties: signing.keyId=... signing.password=... signing.secretKeyRingFile=..." (claim 4). It requires signing to be configured unless the version ends in `-SNAPSHOT` (`setRequired(version ... !endsWith("-SNAPSHOT"))`), so local `publishToMavenLocal` of `3.0.0` needs the maintainer's keyring too.
- The plugin's own integration tests run with `--configuration-cache` and a `signing.secretKeyRingFile` test keyring, across Gradle/KGP matrices, and the KMP project test asserts that the root, jvm, linuxx64 and nodejs publications each have a signed jar/klib, pom, module, sources jar and javadoc jar ([ProjectSpecRunner.kt](https://github.com/vanniktech/gradle-maven-publish-plugin/blob/0.37.0/plugin/src/integrationTest/kotlin/com/vanniktech/maven/publish/util/ProjectSpecRunner.kt), [KotlinPluginTest.kt](https://github.com/vanniktech/gradle-maven-publish-plugin/blob/0.37.0/plugin/src/integrationTest/kotlin/com/vanniktech/maven/publish/KotlinPluginTest.kt), symbol `kotlinMultiplatformProject`; claim 5). No `wasmJs` fixture exists in the plugin's tests; Okio's `okio-wasm-js` 3.18.2 and Kermit prove it works in the field.
- Configuration cache: 0.34.0 "Added configuration cache support for publishing." Up to 0.32.0 the changelog said releases to Central were excluded ("blocked by Gradle issue #22779"); that caveat does not appear from 0.33.0 on (claim 6). The repo published 2.2.0 with 0.36.0 and `org.gradle.configuration-cache` defined in the maintainer's `~/.gradle/gradle.properties` (I did not read its value), consistent with this.
- Known signing pitfall (Opinion, open issue [#1334](https://github.com/vanniktech/gradle-maven-publish-plugin/issues/1334), 2026-07): "Unable to read secret key from file ... (it may not be a PGP secret key ring)" can be a red herring for a `ClassNotFoundException` on `BcPGPSecretKeyRingCollection`; the reporter's thread resolves it with in-memory keys and notes `--no-configuration-cache` in the failing run. Not reproduced for this repo (2.2.0 signed fine); keep in mind if signing fails after the KMP switch. The first diagnostic is `./gradlew checkSigningConfiguration`, mentioned in that thread.

### F4. Naming of every KMP publication (Consensus; KGP and plugin source, confirmed on Central)

- KGP names target publications `dashSeparatedName(target.project.name, artifactTargetName.toLowerCaseAsciiOnly(), suffix)` (`KotlinVariant.defaultArtifactId` in [kotlinVariants.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/tools/kotlin-gradle-plugin/src/common/kotlin/org/jetbrains/kotlin/gradle/plugin/mpp/kotlinVariants.kt)); for js/wasm targets `artifactTargetName = wasmDecamelizedDefaultNameOrNull() ?: componentName` (`KotlinJsIrTarget.createKotlinVariant` in [KotlinJsIrTarget.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/tools/kotlin-gradle-plugin/src/common/kotlin/org/jetbrains/kotlin/gradle/targets/js/ir/KotlinJsIrTarget.kt)). The root publication is named `kotlinMultiplatform` and keeps the project name ([Publishing.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/tools/kotlin-gradle-plugin/src/common/kotlin/org/jetbrains/kotlin/gradle/plugin/mpp/publishing/Publishing.kt), `createRootPublication`; claim 7).
- vanniktech `coordinates(group, artifactId, version)` then rewrites each KMP artifactId in `afterEvaluate`: if the publication's artifactId equals the project name it becomes `artifactId`; if it starts with `"$projectName-"` the prefix is replaced and "the suffix needs to be preserved"; anything else throws `IllegalStateException` (`forMultiplatform` in `MavenPublishBaseExtension`; claim 8). KDoc: "resulting in artifactIds like `[artifactId]-jvm`."
- **Resulting coordinates for this repo** (`rootProject.name = "GeneralTools"`, artifactId `"GeneralTools"`, group `io.github.spartanlaboratories`, version `3.0.0`):

| Gradle publication | artifactId | main artifact | POM packaging |
|---|---|---|---|
| `kotlinMultiplatform` (root) | `GeneralTools` | `GeneralTools-3.0.0.jar` (common metadata only), `.module`, `-kotlin-tooling-metadata.json`, `-sources.jar`, `-javadoc.jar` | `jar` (default; no element) |
| `jvm` | `GeneralTools-jvm` | `GeneralTools-jvm-3.0.0.jar` | `jar` |
| `js` | `GeneralTools-js` | `GeneralTools-js-3.0.0.klib` | `klib` |
| `wasmJs` | `GeneralTools-wasm-js` | `GeneralTools-wasm-js-3.0.0.klib` | `klib` |

  Evidence for the shape: Okio 3.18.2 root/`-jvm`/`-js`/`-wasm-js` directory listings (same file kinds; wasm target is `wasm-js`, not `wasmjs`), and `io.github.palex65:CanvasLib`, `CanvasLib-js`, `CanvasLib-jvm` on Central for the capitalised-name-plus-lowercase-suffix combination (listing read 2026-10-15). The target names must be the defaults: a `js("browser")` would publish `GeneralTools-browser`.
- **Pitfall tied to naming:** [vanniktech #1020](https://github.com/vanniktech/gradle-maven-publish-plugin/issues/1020) (open, 0.33.0): when `coordinates` artifactId differs from the Gradle project name, the KMP `.module` files contained references derived from the project name and consumers failed to resolve target POMs; the reporter's workaround was to rename the project. Here both are `GeneralTools` (exact case), which avoids the class of problem; do not rename either independently.
- Namespace: all four artifactIds sit under the already-verified `io.github.spartanlaboratories` groupId; every KMP library on Central does the same (Okio), so no new Portal registration is expected. Sonatype's namespace page says control of a namespace permits "any groupId starting with the reverse domain name"; it does not spell out artifactIds (see Gaps).

### F5. Central Portal requirements as they apply to KMP (Consensus; official docs + Practice)

- Sonatype requirements: "Projects with packaging other than `pom` have to supply JAR files that contain Javadoc and sources." and "If you cannot provide sources or documentation, we allow uploading placeholder `.jar` files in order to pass validation." The rule is per component (artifactId), so root, `-jvm`, `-js` and `-wasm-js` each need a `-javadoc.jar` and `-sources.jar`. The plugin does that by default (F2). Okio 3.18.2's four javadoc jars are 261 bytes each, manifest only (inspected), and were accepted by Central; so was our own 2.2.0 empty javadoc jar. ([requirements](https://central.sonatype.org/publish/requirements/); claim 9.)
- Checksums: "`.md5` and `.sha1` are required"; `sha256`/`sha512` supported but optional; `.asc` per file; ".asc files don't need checksum files" (claim 9), which is why 0.37.0's default is safe.
- POM: `name`, `description`, `url`, license(s), developer(s), SCM are required, as is the `-SNAPSHOT`-free version (claim 9). The plugin's `pom { }` block is applied to every `MavenPublication` including the root and each target, so the existing block already satisfies all four.
- Root publication: the Kotlin docs state "Some repositories, such as Maven Central, require the root module to contain a JAR artifact without a classifier ... The Kotlin Multiplatform plugin automatically produces the required artifact with the embedded metadata artifacts." Its POM has no `packaging` element (jar) and, from the libraries inspected (kotlin-logging 8.0.4, kotlinx-datetime 0.8.0, Ktor 3.6.0), only runtime-scope dependencies (stdlib and commonMain deps), no dependency on `-jvm` (claim 10). Okio's root jar contains zero `.class` files (inspected: 195 entries, `META-INF/kotlin-project-structure-metadata.json` and `commonMain/**` metadata).
- Validation rules KMP projects commonly trip over (Practice): (1) a publication missing its javadoc or sources jar; (2) signing with a public key not distributed to a keyserver ([#859](https://github.com/vanniktech/gradle-maven-publish-plugin/issues/859): "Fixed, I need to publish my public key to pgp key server"; already done for this maintainer since 2.2.0 was accepted); (3) duplicate publications when several hosts upload the same artifact: the Kotlin docs state "Maven Central explicitly forbids duplicate publications and fails the process if they are created", irrelevant here because jvm/js/wasmJs all publish from one Windows host and there are no native targets (the Kotlin docs: publications are created "for each target that can be built on the current host"). A failing deployment shows a per-component failure count in the Portal ([#915](https://github.com/vanniktech/gradle-maven-publish-plugin/issues/915) shows "53 failed Component Validations" for a many-target library; its cause was local to that project).
- Central is immutable: "we do not remove or modify components once they are publicly available" and a bug means a new release (claim 11). That is the reason for the staged flow below.

### F6. What `publishToMavenCentral` / `publishAndReleaseToMavenCentral` actually do (Consensus; plugin source @ 0.37.0)

- The DSL call `publishToMavenCentral(automaticRelease = project.automaticRelease(), validateDeployment = project.validateDeployment())` defaults `automaticRelease` to `false` (Gradle property `mavenCentralAutomaticPublishing`) and `validateDeployment` to `DeploymentValidation.VALIDATED` (`mavenCentralDeploymentValidation`). It registers two lifecycle tasks: `publishToMavenCentral` ("Publishes to Maven Central") and `publishAndReleaseToMavenCentral` ("Publishes to Maven Central and automatically triggers release"); the latter additionally depends on `enableAutomaticMavenCentralPublishing` (claim 12).
- For a non-SNAPSHOT version, `publishAllPublicationsToMavenCentralRepository` does **not** talk to the network by itself: it writes a Maven-layout repository to `build/publishing/mavenCentral`; the upload happens at the **end of the build** in `MavenCentralBuildService.close()`, which zips that directory into `<settings dir>/build/publish/<group>-<artifactId>-<version>-<epoch>.zip`, uploads it to `https://central.sonatype.com` with `publishingType` `USER_MANAGED` (default) or `AUTOMATIC` (release task), and logs "Uploaded bundle to Central Portal as $publishingType, deployment id: $deploymentId". If a validate action is enabled it then polls; for `USER_MANAGED` the build ends with "Skipping deployment validation!" (claim 12). `prepareMavenCentralPublishing` hard-requires `mavenCentralUsername` and `mavenCentralPassword`, so even a "dry run" of that repository task fails without credentials and, with them, uploads. There is no dry-run mode.
- A failed build after registration drops the just-created deployment (`EndOfBuildAction.Drop(runAfterFailure = true)`), and `dropMavenCentralDeployment --deployment-id=<id>` drops one on demand (claim 12).
- Docs: "Uploading with manual publishing: run `./gradlew publishToMavenCentral`. Afterward go to Deployments on the Central Portal website and click "Publish" on the deployment."; the automatic path is `./gradlew publishAndReleaseToMavenCentral`; "Step 4 can take 10 to 30 minutes and only after it completed the published artifacts will be available for download." ([docs/central.md @ 0.37.0](https://github.com/vanniktech/gradle-maven-publish-plugin/blob/0.37.0/docs/central.md); claim 13.) A separate "release an already-uploaded deployment" Gradle task does not exist ([#1130](https://github.com/vanniktech/gradle-maven-publish-plugin/issues/1130), open; the maintainer-side answer is the Portal's Publish button).
- Sonatype semantics: `USER_MANAGED` (default) = "a deployment will go through validation and require the user to manually publish it via the Portal UI"; `AUTOMATIC` = "go through validation and, if it passes, automatically proceed to publish"; a VALIDATED or FAILED deployment can be dropped with `DELETE /api/v1/publisher/deployment/<deploymentId>`; a VALIDATED one is published with `POST` to the same path (claim 14).
- Comparable practice: Coil's `publish_remote.sh` runs `./gradlew publishToMavenCentral` (manual click); Okio sets `publishToMavenCentral(automaticRelease = true)`; Kermit sets `publishToMavenCentral(true, DeploymentValidation.NONE)` (claim 18).

### F7. The Portal's "Manually Testing a Deployment Bundle" (Consensus; Sonatype docs; not run)

- "Once a bundle has been validated it can be referenced as a dependency in your build tool of choice. The usecase for this would be building a release in a CI environment but performing manual testing in your local environment before releasing the deployment to Central." Two endpoints: `/api/v1/publisher/deployment/<deploymentId>/download/<relativePath>` (one deployment) and `/api/v1/publisher/deployments/download/<relativePath>` ("any validated deployment containing the requested file"). Host `https://central.sonatype.com`.
- Gradle form, as documented: a `maven { url "https://central.sonatype.com/api/v1/publisher/deployments/download/"; credentials(HttpHeaderCredentials); authentication { header(HttpHeaderAuthentication) } }` repository, with `centralManualTestingAuthHeaderName=Authorization` and `centralManualTestingAuthHeaderValue=Bearer <base64 of username:password>` in `gradle.properties`; `mavenCentral()` is listed after it so transitive dependencies (stdlib, kotlin-logging) resolve normally. The credential is the same Portal **user token** pair that is `mavenCentralUsername` / `mavenCentralPassword` (the plugin base64-encodes `username:password` for its own API calls; docs example header `Bearer ZXhhbXBsZV91c2VybmFtZTpleGFtcGxlX3Bhc3N3b3Jk`). (claim 15.)
- vanniktech does not expose this (no mention in docs or source of 0.37.0). It is configuration in the **consumer** build, not in GeneralTools. Required state: VALIDATED (the doc ties it to "once a bundle has been validated"; I did not find a list of states it accepts).
- Not documented by Sonatype and therefore untested here: whether Gradle follows the root `.module`'s relative `available-at` URL (`../../GeneralTools-jvm/3.0.0/GeneralTools-jvm-3.0.0.module`) through this endpoint. Gradle treats `available-at` as a module coordinate lookup against the declared repositories (spec: "`url` ... must be a path relative to the module"), and the "any validated deployment" endpoint serves any file path, so it should work; confirm on the first run (see Gaps).

### F8. Local rehearsal: `publishToMavenLocal` versus a file repository in `build/` (Practice)

- `publishToMavenLocal` publishes the four publications (`publishKotlinMultiplatformPublicationToMavenLocal`, `publishJvmPublicationToMavenLocal`, `publishJsPublicationToMavenLocal`, `publishWasmJsPublicationToMavenLocal`) into `~/.m2`; Coil's `publish_local.sh` does exactly that. The Kotlin docs list `publishToMavenLocal` and per-publication tasks (claim 16).
- Downsides: it writes into a shared cache that outlives the test (a later `mavenLocal()`-first consumer keeps seeing a `3.0.0` that Central may never get), and it does not produce the `.md5/.sha1` checksums files in the shape Central sees. A **custom file repository** under `build/` (a `publishing { repositories { maven { name = "smoke"; url = uri(layout.buildDirectory.dir("smoke-repo")) } } }` block, then `publishAllPublicationsToSmokeRepository`) produces the full Maven layout with checksums and signatures, does not touch `~/.m2`, needs no credentials and no network upload. This is precisely how the plugin tests itself (`publishAllPublicationsToTestFolderRepository`) and how Okio offers an `internalUrl` repository for rehearsals (claim 5, claim 18). Combine with `-PmavenCentralChecksums=...` only if you want to rehearse the 0.37 checksum set.
- What a local repository cannot prove: namespace verification, public-key distribution, Portal POM/javadoc/source validation, and relative `available-at` redirects under the Portal's URL scheme. Only the Portal can.

### F9. How consumers resolve `io.github.spartanlaboratories:GeneralTools:3.0.0` (Consensus for mechanism; Practice from published KMP modules)

- **Gradle `kotlin("jvm")` project (MyGameTools):** Gradle prefers the `.module` file over the POM (the POM carries the `do_not_remove: published-with-gradle-metadata` marker, Gradle docs: the marker "explains to Gradle that a *better* module metadata file exists and that it should use it instead"). The root `.module` lists `jvmApiElements-published` / `jvmRuntimeElements-published` / `jvmSourcesElements-published` as `available-at` redirects to the `-jvm` module with attributes `org.gradle.usage=java-api|java-runtime`, `org.gradle.jvm.environment=standard-jvm`, `org.jetbrains.kotlin.platform.type=jvm` (Okio 3.18.2 root module, inspected). A `kotlin("jvm")` consumer therefore lands on `GeneralTools-jvm`'s jar with no coordinate change, exactly like MyGameTools already consumes the KMP `kotlinx-serialization-json` (R1 F3). stdlib and kotlin-logging requirements follow R1/R3.
- **Gradle KMP project:** requests the `common` metadata variant for shared source sets and per-target variants (`platform.type` = `jvm`, `js` + `js.compiler=ir`, `wasm` + `wasm.target=js`) from the root module's redirects. js/wasm consumers must satisfy R1's ABI floor (compiler >= 2.4 for klibs built by 2.4.21).
- **Plain Maven:** Maven does not read `.module`. The root POM has no `<packaging>` (jar) and only the root's runtime-scope dependencies; the root jar is the metadata jar with no classes. `GeneralTools:3.0.0` resolves and compiles to nothing; `GeneralTools-jvm:3.0.0` is the real jar (its POM lists `kotlin-stdlib` as `compile` and kotlin-logging as `runtime` if R3's `implementation` shape holds). Okio's changelog: 3.2.0 "Configure the multiplatform artifact ... to depend on the JVM artifact ... for Maven builds. This should work-around an issue where Maven doesn't interpret Gradle metadata", implemented as a `pom.withXml` replacing the root POM's dependencies with one compile-scope dependency on `okio-jvm` and with the comment "This hack allows Maven users to continue using our original Okio artifact names ... Note that module.json doesn't need this hack." (claim 17.) That is a precedent for keeping Maven consumers on the old artifactId; B9 chose the other path (Maven consumers move to `-jvm`), which is the Kotlin-default and costs them one line.
- **`org.gradle.jvm.version`:** per R1, KMP jvm publications carry none unless set. Gradle's rule: "lower is compatible with higher, prefers highest compatible" (claim 19). If you set 17 (kotlinx-datetime 0.8.0 does this with 8, and the attribute appears on **both** the root redirect variants and the `-jvm` module variants, inspected), a JVM 11 consumer gets a resolution-time "incompatible" error instead of a class-version error at runtime; MyGameTools (JVM 23) is unaffected. If you leave it unset, every consumer resolves and old JVMs fail at class load.
- **Old Gradle:** Gradle Module Metadata has been published by default since Gradle 6.0 and any Gradle that KGP 2.2+ runs on (>= 7.6.3, R1 claim 15) reads it; the failure mode of an environment that ignores `.module` (Maven, or tooling that reads only the POM) is the empty-root problem above. A Gradle consumer that resolves from a repository **without** the `.module` file (for example a hand-copied `~/.m2` tree) fails because Gradle then falls back to the POM and the empty root jar.
- **Composite-build substitution:** `includeBuild("../GeneralTools")` in MyGameTools substitutes dependencies "matching `${project.group}:${project.name}`" (Gradle docs). Here `group = "io.github.spartanlaboratories"` and `project.name == "GeneralTools"`, so `io.github.spartanlaboratories:GeneralTools` is substituted for the KMP project, and KGP resolves the correct variant through the project dependency. Gradle lists the cases that require an explicit `dependencySubstitution`: published coordinates that do not equal `${project.group}:${project.name}`. Because vanniktech's `coordinates()` only changes the publication (not `project.group`/`project.name`), keep `group` set at project level and the artifactId equal to the project name; do not rename either, or add `dependencySubstitution { substitute(module("io.github.spartanlaboratories:GeneralTools")).using(project(":")) }` (claim 20). The substituted dependency uses the project's own variants, not the published `.module`, so a composite build does not prove publication correctness.

## 5. Pitfalls and regrets

1. **`publishAndReleaseToMavenCentral` is a one-shot, irreversible command.** `AUTOMATIC` means validation success = publication; there is no pause to test the real bundle. Central never deletes or modifies (claim 11). For a major release that changes the artifact shape, use the upload-only flow once.
2. **The root `GeneralTools:3.0.0` is an empty artifact for Maven.** Any README, changelog or release note that still shows `<artifactId>GeneralTools</artifactId>` for Maven must change to `GeneralTools-jvm` (B9), including the repo README's dependency snippets.
3. **Artifact id / project name drift** (vanniktech #1020; `forMultiplatform` throws on unexpected names): keep `rootProject.name = "GeneralTools"` (exact case), the same string in `coordinates`, and default target names `js()` / `wasmJs()`.
4. **No dry run for the Central upload** (F6): even the "prepare" task needs credentials. Do not try to test by running `publishAllPublicationsToMavenCentralRepository` "just to see".
5. **`mavenLocal()` shadowing:** an `~/.m2` copy of 3.0.0 survives the test and is preferred by any `mavenLocal()`-first build. Prefer a repository under `build/` for rehearsal, or delete `~/.m2/repository/io/github/spartanlaboratories` afterwards.
6. **Signing is required for non-SNAPSHOT** (F3): any CI job or contributor that runs `publishToMavenLocal`/`publish*` on `3.0.0` without keys fails. Rehearse on the maintainer's machine; CI should not call publish tasks (there is no CI publish today, and the README's "Releasing" section is wrong about in-memory keys, which is the task of whoever updates the README).
7. **Local file names show `unspecified` if `project.version` is unset.** The plugin sets the publication version but not `project.version`; KGP names local jars from `project.version`. The `.module` `files[].name` is cosmetic (`url` is the repo path), but set `version`/`group` on the project and derive `coordinates(group.toString(), "GeneralTools", version.toString())` as the JetBrains template does, so the version lives in one place. (The exact local file names are inferred from Okio's module, whose `name` fields differ from the `url` fields; verify in the rehearsal.)
8. **Dokka / javadoc:** the default stays empty. If a Dokka plugin is applied later, `configureBasedOnAppliedPlugins` silently switches to Dokka javadoc jars on all four publications (`defaultJavaDocOption`); pin `JavadocJar.Empty()` explicitly to keep the current behaviour.
9. **0.37.0's smaller checksum set** changes the file inventory relative to 2.2.0. This is deliberate and Central-compliant; do not "fix" it back.
10. **`mavenCentralUsername`/`Password` double as the testing-repository credential.** Putting the Bearer value in `gradle.properties` of a consumer project would leak it into a repo; keep `centralManualTestingAuthHeader*` in `~/.gradle/gradle.properties` only, and scope the repository with `content { includeGroup("io.github.spartanlaboratories") }` so only these coordinates are looked up there.
11. **Wasm/JS klibs need Kotlin >= 2.4 consumers** (R1); that is a consumer-resolution fact to state in the 3.0.0 notes, not a publishing defect.

## 6. Recommendation for this repo

**Plugin and DSL.** Use `id("com.vanniktech.maven.publish") version "0.37.0"` next to `kotlin("multiplatform") version "2.4.21"` (R1). Drop `kotlin("jvm")` and `java-library` (R1). Keep the `mavenPublishing { publishToMavenCentral(); signAllPublications(); coordinates(...); pom { ... } }` block as is, with two edits: set `group` and `version = "3.0.0"` on the project and pass `coordinates(group.toString(), "GeneralTools", version.toString())` (one source of truth for the version, JetBrains' shape); and add `configure(KotlinMultiplatform(javadocJar = JavadocJar.Empty(), sourcesJar = SourcesJar.Sources()))` as a documented, explicit policy (empty javadoc, as 2.2.0 shipped), so applying Dokka later is a conscious change. Do not pass `automaticRelease = true` in the DSL: the existing split of `publishToMavenCentral` (upload) versus `publishAndReleaseToMavenCentral` (upload + release) already gives both modes without config changes. Leave `rootProject.name = "GeneralTools"` and the default `js()` / `wasmJs()` target names alone. Whether the explicit `org.gradle.jvm.version` = 17 attribute is declared is R1's policy decision (recommended there); from the publishing side it appears on both the root redirect variants and `GeneralTools-jvm`.

**Rehearsal (free, reversible) before any upload.**
1. `./gradlew check` (R1/R5 scope) then publish to a file repository inside `build/` (extra `publishing { repositories { maven { name = "smoke"; url = ... } } }` in the build script; run `publishAllPublicationsToSmokeRepository`). Inspect: four artifact directories (`GeneralTools`, `-jvm`, `-js`, `-wasm-js`) each with `.pom`, `.module`, main file, `-sources.jar`, `-javadoc.jar`, `.asc` and md5/sha1 for each; root has `-kotlin-tooling-metadata.json`; root jar has no classes; `-jvm` POM stdlib/logging scopes; `-jvm` `.module` attribute `org.gradle.jvm.version`; signatures verify against the maintainer's key.
2. Consume that repository from three throwaway builds: a **Kotlin 2.2.0 `kotlin("jvm")` project** (MyGameTools' case; the only real proof of B1, as R1 notes), a **Kotlin 2.4.x KMP project** with jvm + js + wasmJs, and a **plain Maven project** depending on `GeneralTools-jvm` (and, as a negative control, on `GeneralTools` to see the empty root). Delete `~/.m2` contents of the group if `publishToMavenLocal` was used instead.

**Staged release (irreversible step last).**
3. `./gradlew publishToMavenCentral` -> note the logged deployment id and keep `build/publish/*.zip` (the exact bundle). In the Portal wait for VALIDATED; if FAILED, read the per-component errors and fix; do not drop a FAILED deployment before reading it (Sonatype asks that, for support cases). A bad VALIDATED deployment is dropped (`./gradlew dropMavenCentralDeployment --deployment-id=<id>` or Portal).
4. Point the three consumers at `https://central.sonatype.com/api/v1/publisher/deployments/download/` (header credentials kept in `~/.gradle/gradle.properties`, repository content-filtered to the group), re-run them. This is the only test of the bytes Central will serve, including the root `.module` -> `-jvm` redirect through the Portal URL scheme.
5. Publish in the Portal (or `POST` to `/api/v1/publisher/deployment/<id>`), wait the documented 10-30 minutes, then run the Kotlin 2.2.0 consumer once more against plain `mavenCentral()` before tagging `3.0.0` and creating the GitHub release (tag/release conventions are settled and not part of this report).

**Why not the alternatives.** `publishAndReleaseToMavenCentral` first: nothing is testable between validation and publication, and the artifact shape changes (new artifactIds, empty root), which is the case most likely to hide a mistake. A published `3.0.0-rc1`/`-SNAPSHOT`: a release candidate is permanent clutter on Central; a SNAPSHOT is not validated like a release (signing optional, no Portal validation of javadoc/POM) and needs "Enable SNAPSHOTs" on the namespace. `publishToMavenLocal` as the only rehearsal: pollutes `~/.m2` and cannot validate anything Portal-side. The Okio-style root-POM hack: valid, but B9 already fixes the Maven-user story; adding it is an additive opt-in the planner may take later without a coordinate change.
