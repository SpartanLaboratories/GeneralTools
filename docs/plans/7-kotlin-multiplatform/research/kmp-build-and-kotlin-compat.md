# R1 - KMP build configuration and Kotlin 2.2.0 consumer compatibility

- **Researcher:** R1, for [SpartanLaboratories/GeneralTools#7](https://github.com/SpartanLaboratories/GeneralTools/issues/7). Informs decision **D1**.
- **Date read:** 2026-10-15. Repo baseline: `master` @ `6926069`.
- **Versions this report is pinned to** (from `gh release list` / GitHub tags, 2026-10-15): Kotlin 2.4.21 (2026-10-08) is the latest stable; 2.4.20 (2026-09-07); 2.4.0 (2026-06-03); 2.5.0-Beta1 (2026-09-23). Gradle docs state KGP 2.4.20-2.4.21 supports Gradle 7.6.3-9.7.0.
- **Method limits:** nothing was built or run (brief boundary). Everything below comes from compiler/KGP source at pinned tags, official docs, published Maven Central artifacts of comparable libraries (opened and decoded read-only), and GitHub/YouTrack. What this means for confidence is in *Gaps*.

## 1. Question

Which Kotlin Gradle plugin version and which compatibility settings should GeneralTools 3.0.0 use as a KMP library with `jvm` (bytecode 17) + `js` + `wasmJs`, so that MyGameTools (Kotlin **2.2.0**, JVM only, `api` dependency) keeps compiling without changing its Kotlin version, plus the JVM-17, JS/Wasm-test, Gradle, CI and version-catalog choices that go with it. It informs D1 (plugin version and pins, targets and source sets, JVM 17 enforcement, JS/Wasm test runtime, Gradle and CI).

## 2. Bottom line

- **Use KGP 2.4.21 (not 2.2.0) with pins; leave Gradle at 9.0.0.** KGP 2.2.x is documented only up to Gradle 8.14, and `wasmJs` only became Beta in 2.2.20 (and `webMain` arrived then). KGP 2.4.20-2.4.21 is documented for Gradle 7.6.3-9.7.0, so the wrapper needs no change. `java-library` must be dropped (KGP errors on it in a KMP project on Gradle >= 8.7).
- **What keeps a Kotlin 2.2.0 JVM consumer compiling is two numbers, not one.** (1) Metadata: a compiler X reads class metadata up to X+1; the metadata written equals `languageVersion`. Set `languageVersion = apiVersion = 2.2` at the `kotlin {}` extension level. (2) The `kotlin-stdlib` that the published JVM variant declares: the KMP plugin adds stdlib as an `api` dependency at `coreLibrariesVersion` (default = KGP version), and Gradle resolves the highest requested version, so an unpinned 2.4.21 build would put stdlib 2.4.21 (metadata 2.4.0, which a 2.2.0 compiler cannot read) on MyGameTools' compile classpath. Declare `kotlin-stdlib:2.2.0` for JVM/common.
- **Do not lower `coreLibrariesVersion` globally; split by target.** The JS and Wasm compilers reject a stdlib/kotlin-test klib older than themselves (ABI and version check), and no `languageVersion` setting changes that (KT-66755, open in Backlog). So JVM/common get `kotlin-stdlib:2.2.0` and the web targets keep the KGP-matching stdlib. This is exactly the shape Okio 3.18.2 publishes (and what the `tapmoc` plugin automates).
- **The `js`/`wasmJs` klibs will require Kotlin >= 2.4 on the consumer side.** A klib carries `abi_version` = compiler's (2.4.0 for KGP 2.4.21); compilers older than that cannot read it, and the only "export to an older ABI" switch in 2.4.21 is an unreleased, pre-release-binary feature that cannot go below 2.3. That is acceptable for SpartanGraphics/SpartanUI (current Kotlin), and it is the one trade-off to state in the 3.0.0 notes. The only dial that widens it is the KGP version itself (KGP 2.3.21 is the alternative, section 6).
- **JVM 17:** `kotlin { jvmToolchain(17) }` is sufficient for bytecode 61 plus JDK-17-only API visibility (documented: sets `jvmTarget` convention and `-jdk-home`), and it runs `jvmTest` on a real 17. Set `jvmTarget` explicitly too. Under *either* approach the KMP jvm publication writes **no** `org.gradle.jvm.version` (the old `kotlin("jvm")` + `java-library` build wrote 23 only because `java-library` does); declare it explicitly if you want it.
- **JS/Wasm tests:** `nodejs()` only, for both targets; `./gradlew check` runs every registered target test task. KGP downloads Node (24.16.0 for js, 26.2.0 for wasm) from `nodejs.org/dist` and Yarn from GitHub into `~/.gradle`. Commit `kotlin-js-store/yarn.lock` (js only). `nodejs()` does not limit browser consumers: published variants carry no browser/node attribute. CI needs no Node step. No version catalog.

## 3. Findings

Tiers: **Consensus** = official doc/spec or several independent credible sources; **Practice** = what mature libraries visibly do; **Opinion** = one source.

### F1. The exact rule for a Kotlin 2.2.0 JVM compiler reading a newer-compiled library (Consensus)

- Official statement: language version decides which compilers can use your library; "On the JVM, consumers can use any compiler version from the previous language version onwards"; the API version decides the minimum stdlib; "Your consumers also need to provide a Kotlin standard library version that is at least as new as your library's configured API version." ([API guidelines](https://kotlinlang.org/docs/api-guidelines-backward-compatibility.html), read 2026-10-15; see Load-bearing claim 1.)
- Mechanism in the compiler: `MetadataVersion.isCompatibleWithCurrentCompilerVersion` accepts metadata `<= INSTANCE.next()` (non-strict mode), where `INSTANCE` is the compiler's own version (`MetadataVersion(2, 2, 0)` at tag `v2.2.0`; `MetadataVersion(2, 4, 0)` at `v2.4.21`). So a 2.2.0 compiler reads **metadata <= 2.3.0**. ([MetadataVersion.kt @ v2.2.0](https://github.com/JetBrains/kotlin/blob/v2.2.0/core/metadata/src/org/jetbrains/kotlin/metadata/deserialization/MetadataVersion.kt); claim 2.)
- The metadata a compiler writes is a pure function of `languageVersion`: `LANGUAGE_TO_METADATA_VERSION` maps `KOTLIN_2_2 -> 2.2.0`, `KOTLIN_2_3 -> 2.3.0`, `KOTLIN_2_4 -> 2.4.0`. ([metadataHelpers.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/compiler/frontend.common/src/org/jetbrains/kotlin/util/metadataHelpers.kt); claim 3.) Per-class `mv` is stored in `@Metadata`; error text on violation: "was compiled with an incompatible version of Kotlin. The actual metadata version is X, but the compiler version Y can read versions up to Z" ([wrongAbiVersion.out](https://github.com/JetBrains/kotlin/blob/master/compiler/testData/cli/jvm/wrongAbiVersion.out), read 2026-10-15 via code search on master).
- So `languageVersion` of 2.2 or 2.3 is readable by 2.2.0; 2.4 is not. The 2.4.21 compiler still supports and does not deprecate `-language-version 2.2` (`FIRST_SUPPORTED = KOTLIN_2_0`, `FIRST_NON_DEPRECATED = KOTLIN_2_2`); in 2.5.0-Beta1 `FIRST_NON_DEPRECATED = KOTLIN_2_3`, so a 2.2 pin starts warning in 2.5. ([LanguageVersionSettings.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/core/language.version-settings/src/org/jetbrains/kotlin/config/LanguageVersionSettings.kt), [@ v2.5.0-Beta1](https://github.com/JetBrains/kotlin/blob/v2.5.0-Beta1/core/language.version-settings/src/org/jetbrains/kotlin/config/LanguageVersionSettings.kt); claim 4.)

### F2. The stdlib on the consumer's compile classpath comes from the library's own pins (Consensus on mechanism; Practice on effect)

- KGP adds `kotlin-stdlib` to each compilation; "The version of the standard library used is the same as the version of the Kotlin Gradle plugin" ([gradle-configure-project](https://kotlinlang.org/docs/gradle-configure-project.html), source `docs/topics/gradle/gradle-configure-project.md` @ kotlin-web-site `0b10373`; claim 16).
- `coreLibrariesVersion` is documented as "the version of the core Kotlin libraries that are added to the Kotlin compile classpath, unless there is already a dependency added to this project" (kotlin-stdlib, kotlin-test, kotlin-dom-api-compat, kotlin-reflect), default "the same version as the version used in the Kotlin Gradle plugin" ([kotlinTopLevelExtensionConfig.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/tools/kotlin-gradle-plugin-api/src/common/kotlin/org/jetbrains/kotlin/gradle/dsl/kotlinTopLevelExtensionConfig.kt); claim 5).
- In a KMP project the default stdlib goes to the `api` scope of the root (no-`dependsOn`) source set, and is skipped for a source set where the user declared a stdlib ([stdlibDependencyManagement.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/tools/kotlin-gradle-plugin/src/common/kotlin/org/jetbrains/kotlin/gradle/internal/stdlibDependencyManagement.kt), `addStdlibDependency`; claim 6). `api` means it is **published** as a dependency of the variant.
- What the publication declares: the Gradle module of the `-jvm` variant lists `kotlin-stdlib` with `"requires": "<that version>"` in both `jvmApiElements-published` and `jvmRuntimeElements-published`; the `-jvm` POM lists it with `<scope>compile</scope>`. Seen in Ktor 3.6.0 (`2.3.21`), Okio 3.18.2 (`2.1.21`), kotlinx-datetime 0.8.0 (`2.1.20`), kotlinx-coroutines 1.11.0 (`2.2.20`), kotlinx-serialization 1.11.0 (`2.3.20`) (claim 8).
- Gradle then takes the highest requested version ("Gradle considers all requested versions across the dependency graph and, by default, selects the highest version", claim 7). MyGameTools adds stdlib 2.2.0 itself, so an unpinned GeneralTools built by 2.4.21 would win with `kotlin-stdlib:2.4.21`.
- I decoded the `@Metadata` `mv` in the published jars (read-only): `kotlin-stdlib-2.2.0.jar` classes have `mv = [2,2,0]`, `2.3.21` has `[2,3,0]`, `2.4.21` has `[2,4,0]` (`kotlin/Unit.class`, `kotlin/collections/CollectionsKt.class`). By F1, a 2.2.0 compiler reads 2.2/2.3 stdlib and rejects 2.4.21. (Local inspection of Maven Central jars; not a quoted claim.)

### F3. What exactly keeps MyGameTools compiling (synthesis of F1 + F2; Practice)

For the JVM variant MyGameTools resolves (`kotlin("jvm")` consumers pick `jvmApiElements-published` through the root module's `available-at` redirect to `GeneralTools-jvm`, the same way MyGameTools already consumes the KMP `kotlinx-serialization-json:1.7.3`):

1. every class's metadata <= 2.3.0: set `languageVersion` (2.2, or 2.3 at most);
2. the published `kotlin-stdlib` requirement <= 2.3.x (set to 2.2.0, the API version);
3. no JDK-newer-than-consumer problem: bytecode 61 <= MyGameTools' JDK 23 toolchain.

`apiVersion = 2.2` additionally stops the library from calling stdlib APIs newer than 2.2.0, which is the documented guard for "consumer's stdlib at least the API version".

### F4. js/wasmJs klibs: "same or later compiler" is enforced by ABI version, and cannot be lowered with `languageVersion` (Consensus; source-verified)

- Official: "On other platforms, consumers can use a compiler version the same as the library's configured language version or any later version." (claim 1.)
- The enforcement is the klib manifest `abi_version`: `KotlinAbiVersion.CURRENT = KotlinAbiVersion(2, 4, 0)` at `v2.4.21` (2, 2, 0 at `v2.2.0`) and `isCompatibleTo` requires the klib's ABI `<=` the loading compiler's `CURRENT` ([KotlinAbiVersion.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/compiler/util-klib/src/org/jetbrains/kotlin/library/KotlinAbiVersion.kt); claim 10). The JS/Wasm loader calls `maxPermittedAbiVersion(KotlinAbiVersion.CURRENT)` ([loadWebKlibs.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/compiler/ir/serialization.js/src/org/jetbrains/kotlin/ir/backend/js/loadWebKlibs.kt)).
- Empirical confirmation from published klibs' `default/manifest` (decoded read-only): Okio 3.18.2 `okio-js`/`okio-wasm-js`: `compiler_version=2.2.21`, `abi_version=2.2.0`; kotlinx-datetime 0.8.0 `-js`: `compiler_version=2.1.20`, `abi_version=1.201.0`; kotlin-logging 8.0.4 `-js` and `-wasm-js`: `compiler_version=2.1.21`, `abi_version=1.201.0`. The ABI follows the compiler, not the `languageVersion` Okio sets for the JVM.
- In 2.4.21 there is a newer knob: `KlibAbiCompatibilityLevel` (`ABI_LEVEL_2_3`, `ABI_LEVEL_2_4`) selected from `languageVersion`, **but only when the language feature `ExportKlibToOlderAbiVersion` is enabled**; it is declared `ExportKlibToOlderAbiVersion(sinceVersion = null, forcesPreReleaseBinaries = true, issue = "KT-76131")`, and "Exporting KLIBs in older ABI format is only supported for the following language versions" (2.3 and 2.4). With it off (default) the level is `LATEST_STABLE` (2.4) ([klibArguments.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/compiler/cli/src/org/jetbrains/kotlin/cli/common/klibArguments.kt), [KlibAbiCompatibilityLevel.kt](https://github.com/JetBrains/kotlin/blob/v2.4.21/compiler/config/src/org/jetbrains/kotlin/config/KlibAbiCompatibilityLevel.kt); claims 10, 11). It forces pre-release binaries and cannot reach 2.2, so it is not usable here.
- The long-standing request is [KT-66755](https://youtrack.jetbrains.com/issue/KT-66755) "Native & non-JVM targets: add support for `languageVersion`", State **Backlog**, unresolved on 2026-10-15; its text: "library authors need to use low versions of their compiler and Kotlin Gradle Plugin" and "I understand this works for the JVM but not for native or other non-JVM targets" (claim 12).
- Consequence for consumers: a JS/Wasm consumer of GeneralTools 3.0.0 built by KGP 2.4.21 needs Kotlin >= 2.4.0. (Kotlin 2.2/2.3 web consumers would need KGP 2.2.x/2.3.x on our side; the choice is in section 6.) Newer compilers read older ABIs (the check is `<=`).

### F5. Why `coreLibrariesVersion` must not be lowered for js/wasmJs (Consensus on mechanism; source-verified)

- `LibrarySpecialCompatibilityChecker` (used by `loadWebKlibs` for both JS and Wasm, checking the stdlib and kotlin-test klibs) reports `KLIB_LOADING_ERROR` when a stdlib/kotlin-test klib's ABI version is not at the compiler's ABI compatibility level, or when the library "has an older version (...) than the compiler (...). Such a configuration is not supported." ([source @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/compiler/ir/serialization.common/src/org/jetbrains/kotlin/backend/common/diagnostics/LibrarySpecialCompatibilityChecker.kt); claim 9.) So a global `coreLibrariesVersion = "2.2.0"` would make `compileKotlinJs`/`compileKotlinWasmJs` (and kotlin-test, which follows `coreLibrariesVersion` too) fail under compiler 2.4.21.
- Independent confirmation: tapmoc's KGP integration for KMP pins `kotlin-stdlib:<floor>` for `jvm`/`androidJvm`/`common` compilations and `kotlin-stdlib:<KGP version>` for others, with the comment "Non-JVM targets do not support compatibility flags and require the latest version of kotlin-stdlib" ([KgpImpl.kt @ tapmoc v0.5.0](https://github.com/GradleUp/tapmoc/blob/v0.5.0/tapmoc-gradle-plugin/src/kgp/kotlin/com/gradleup/tapmoc/internal/KgpImpl.kt); claim 13). Its author's write-up (Opinion, but consistent with the source): "One case where you don't want to downgrade your stdlib is KMP ... because Kotlin/JS and Kotlin/Native require the stdlib to match your compiler version." ([mbonnin.net, 2026-02-22](https://mbonnin.net/2026-02-22-kotlin-versions/)).
- The published result is visible in Okio 3.18.2: `okio-jvm` requires `kotlin-stdlib 2.1.21`; `okio-js` and `okio-wasm-js` list **both** `kotlin-stdlib 2.2.21` and `kotlin-stdlib 2.1.21` (claim 8). Duplicated requirements are therefore normal and harmless: Gradle resolves the highest.

### F6. Choosing the KGP version (Practice + docs)

- KGP/Gradle matrix (docs, claim 15): `2.2.0-2.2.10` and `2.2.20-2.2.21` -> Gradle `7.6.3-8.14`; `2.3.0` and `2.3.10` -> `7.6.3-9.0.0`; `2.3.20-2.3.21` -> `7.6.3-9.3.0`; `2.4.0-2.4.10` -> `7.6.3-9.5.0`; `2.4.20-2.4.21` -> `7.6.3-9.7.0` (the last row is `%minGradleVersion%-%maxGradleVersion%` in the markdown, resolved from `docs/v.list`: `minGradleVersion=7.6.3`, `maxGradleVersion=9.7.0`). Gradle 9.0.0 (this repo) is therefore officially supported by KGP >= 2.3.0, and not by 2.2.x ("You can also use Gradle ... versions up to the latest releases, but ... you might encounter deprecation warnings or some new features might not work"). The repo's `kotlin("jvm") 2.2.0` on Gradle 9.0.0 builds today (185 tests, per the planner), but KMP + JS/Wasm Node tasks on that pairing are untested territory.
- `wasmJs` stability: "Kotlin/Wasm | Beta | 2.2.20" ([components-stability](https://kotlinlang.org/docs/components-stability.html); claim 17). Before 2.2.20 it was pre-Beta, and `webMain`/`webTest` appear only from 2.2.20 ([What's new 2.2.20](https://kotlinlang.org/docs/whatsnew2220.html); claim 18).
- What the comparable libraries chose: Ktor 3.6.0 builds with KGP 2.3.21; kotlinx-datetime 0.8.0 with 2.1.20; Okio 3.18.2 with 2.2.21; kotlin-logging 8.0.4 with 2.1.21; androidx-main uses 2.4.21. The tapmoc authors' guideline is "Target `KGP - 3` for Kotlin" for the language/API floor while keeping KGP modern (Opinion, from the maintainers of the plugin Okio uses; [guidelines](https://github.com/GradleUp/tapmoc/blob/v0.5.0/docs/src/content/docs/guidelines.mdx)).
- Net: libraries do not build with the oldest KGP; they run a recent KGP and pin the floor (Okio: KGP 2.2.21 / floor 2.1; Ktor: KGP 2.3.21 / LV 2.3 / API 2.2). That favours KGP 2.4.21 + floor 2.2 here.

### F7. Wasm Beta changes between 2.2.x and 2.4.x that matter to a no-interop library (Practice)

Most Wasm release-note items concern JS interop (`@JsFun` `require()` error in 2.4.20, `@nativeInvoke` in 2.3.20, Component Model in 2.4.0) and do not touch a library with none. Those that touch it:

- **2.2.20:** Wasm becomes Beta; Kotlin tooling npm packages for `wasmJs` move out of the project (`<kotlin-user-home>/kotlin-npm-tooling/...`), and the project-level `yarn.lock` is no longer generated "unless the project has npm dependencies" ([What's new 2.2.20](https://kotlinlang.org/docs/whatsnew2220.html); claim 24). The same note says the change is not yet done for `js`; KGP 2.4.21 still says "only WasmJS targets use a shared location" (claim 24).
- **2.3.0:** `KClass.qualifiedName` works on Wasm by default (FQNs on) ([What's new 2.3.0](https://kotlinlang.org/docs/whatsnew23.html)). Irrelevant unless code reads `qualifiedName`; the repo's `this::class` in `equals` is fine.
- **2.4.0:** Wasm incremental compilation is Stable and on by default; partial library linkage is always on for JS/Wasm/Native ([What's new 2.4](https://kotlinlang.org/docs/whatsnew24.html)). The latter means linkage problems appear at runtime on first use ("SILENT" default per the planner's earlier note) - a reason to keep a consumer smoke test.
- **2.4.20:** companion-object initialisation order on Wasm now matches the JVM (super before sub) ([What's new 2.4.20](https://kotlinlang.org/docs/whatsnew2420.html); claim 32). `Color` and `CenteredBox` have companions; behaviour only differs for companion-in-hierarchy cases, which R4 may care about.
- **2.4.20 plan:** "Starting with Kotlin 2.5.0, we plan to enable BTA in Kotlin/JS, Kotlin/Wasm, and Kotlin metadata by default" - expect build-tooling churn at the 2.5 bump.
- `wasmJs()` is still `@ExperimentalWasmDsl` in KGP 2.4.21 (`KotlinTargetContainerWithWasmPresetFunctions`), so the build script needs `@OptIn(ExperimentalWasmDsl::class)` (claim 31).

### F8. `webMain` and the default hierarchy (Consensus)

- Not needed for common-only code. The default hierarchy template (on by default) creates `webMain`/`webTest` as a parent of `js` and `wasmJs` only when you put code there; the stated purpose is code that needs JS/Wasm-specific APIs "without duplicating code" (claim 18, [multiplatform-hierarchy](https://kotlinlang.org/docs/multiplatform/multiplatform-hierarchy.html)). With everything in `commonMain`/`commonTest`, declare nothing and do not set `kotlin.mpp.applyDefaultHierarchyTemplate=false` (kotlinx-datetime does, only because it has a bespoke hierarchy).
- Known issues: none material for this repo. Two to remember: you cannot share a source set between several JS targets (only `js` + `wasmJs`), and `KotlinHierarchyBuilder.withWasm()` was removed in 2.4.0 (only matters for custom templates) ([compatibility guide 2.4](https://kotlinlang.org/docs/compatibility-guide-24.html)). If R4 finds a JS-vs-Wasm numeric difference that needs `expect`/`actual`, `webMain` is where a shared JS/Wasm `actual` would live; shared `external` declarations are not needed here.
- Move `java-library` out: in a KMP project the plugin raises `KMPJavaPluginsIncompatibilityDiagnostic` with `ERROR` severity on Gradle >= 8.7 for `java-library`/`java`/`application` (claim 20).

### F9. Enforcing JVM 17 (Consensus on mechanism; Opinion on preference)

| | guarantees bytecode 61? | guarantees no JDK > 17 API? | tests run on 17? |
|---|---|---|---|
| `kotlin { jvmToolchain(17) }` | yes: "Sets the `compilerOptions.jvmTarget` to the toolchain's JDK version if the user doesn't set the `jvmTarget` option explicitly" | yes: "Sets the `-jdk-home` option available for JVM targets"; the compile classpath is JDK 17's class library | yes: "Sets the toolchain to be used by any Java compile, test, and javadoc tasks" |
| `jvmTarget = JVM_17` + `-Xjdk-release=17` (no toolchain) | yes | yes (like `javac --release`); needs the Gradle JVM to be >= 9 | no, `jvmTest` runs on the Gradle JVM (23 locally) |

(quotes: claim 16.) Notes:

- Bytecode level and API surface are independent: "the Java bytecode version is independent from the set of JDK APIs that you can reference" - Jake Wharton's argument for `-Xjdk-release` ([post](https://jakewharton.com/kotlins-jdk-release-compatibility-flag/); claim 29, Opinion; the same post says "Gradle toolchains are rarely a good idea", which is the dissent: it argues toolchains force an old JDK for tooling. KGP's own docs contradict the premise for Kotlin: "The Kotlin compiler always runs on the JDK the Gradle daemon is running on"). The disagreement turns on whether you want tests on the minimum JDK; here you do (B5).
- There is still no typed DSL for the flag: [KT-49746](https://youtrack.jetbrains.com/issue/KT-49746) "Support -Xjdk-release in gradle toolchain" is in Backlog (claim 28); it is `freeCompilerArgs.add("-Xjdk-release=17")`, and `jvmTarget` must be set to the same value or the compiler reports a conflict (as tapmoc's source comments).
- Both machines work: CI has JDK 17 (the toolchain resolves it from the environment); the maintainer's machine already has Temurin 17 in `~/.gradle/jdks`; the foojay resolver (`1.0.0`, the version the Kotlin docs show) provisions it elsewhere. Gradle 9.0 itself needs a JVM 17-24 to run (claim 30), so CI's JDK 17 is the minimum that works.
- I would write a single `val jvmFloor = 17` used by `jvmToolchain(...)` and `jvmTarget`, and keep `-Xjdk-release` out unless the toolchain line is ever removed.

### F10. What `org.gradle.jvm.version` the KMP jvm publication declares (Practice; read from source and from published artifacts, not run)

- Today's build (`kotlin("jvm")` + `java-library`) publishes 23 because `kotlin("jvm")` applies `JavaPlugin` (`project.plugins.apply(JavaPlugin::class.java)` in `AbstractKotlinPlugin`), whose `apiElements`/`runtimeElements` carry the attribute from the compile target. The KMP jvm target applies only `JavaBasePlugin` and builds its own `jvmApiElements`/`jvmRuntimeElements`; KGP source at `v2.4.21` never sets `TargetJvmVersion` (claim 17b).
- Evidence: KMP libraries built with toolchains/targets publish **no** `org.gradle.jvm.version` on the jvm variants: Ktor 3.6.0 (Gradle 9.7.1; build uses `jvmToolchain(...)`, `apiVersion = KOTLIN_2_2`, `languageVersion = KOTLIN_2_3`), Coil 3.6.3 (Gradle 9.7.1), kotlinx-io 0.9.1, Okio 3.18.2, kotlinx-coroutines 1.11.0, kotlin-logging 8.0.4. kotlinx-datetime 0.8.0 declares it **explicitly** (`attributes { attribute(TargetJvmVersion.TARGET_JVM_VERSION_ATTRIBUTE, 8) }` in `jvm {}`) and its module shows `org.gradle.jvm.version: 8` (claim 19).
- Under the toolchain approach and under the `jvmTarget`+release approach the answer is therefore the same: absent unless set explicitly. The KGP docs warn about the other direction (a `kotlin("jvm")` library with no `jvmTarget` publishes the Gradle JDK version, "which is wrong"). Setting it to 17 gives non-17 consumers a resolution-time error instead of an `UnsupportedClassVersionError`; MyGameTools (toolchain 23) is unaffected. It is a policy choice; R2 owns publication, I recommend setting it.

### F11. Gradle 9.0.0, configuration cache, vanniktech 0.36.0 (version conflicts only)

- **KGP vs Gradle:** KGP 2.4.21 + Gradle 9.0.0: inside the documented range (F6). KGP 2.2.x + Gradle 9.0.0: outside it.
- **vanniktech `com.vanniktech.maven.publish`:** 0.36.0 (2026-01-13/18) lists minimum Gradle 9.0.0 and KGP 2.2.0, and "Compatibility tested up to ... Kotlin Gradle Plugin 2.3.0, 2.3.20-Beta1". 0.37.0 (2026-06-21) is "tested up to ... ### F12. JS/Wasm test runtime for a library (Consensus from docs + KGP source; not run)

- **Which tasks `check` runs:** KGP's `KotlinTestsRegistry.registerTestTask` does `project.tasks.named(CHECK_TASK_NAME).dependsOn(taskHolder)` for every registered target test task and also feeds the aggregate `allTests` (claim 23). So with `jvm()`, `js { nodejs() }`, `wasmJs { nodejs() }`: `./gradlew check`/`build` runs `jvmTest`, `jsNodeTest`, `wasmJsNodeTest`. Adding `browser()` would add `jsBrowserTest`/`wasmJsBrowserTest` (Karma + headless Chrome by default, "No browsers are bundled with the plugin"; or a Playwright-based opt-in DSL that installs browsers on first run) - not needed for a pure library.
- **Test frameworks:** `js` Node tests use Mocha (npm packages); `wasmJs` Node tests use KGP's own `KotlinWasmNode` framework (`KotlinNodeJsIr.configureDefaultTestFramework`).
- **What is downloaded, from where, cached where** (KGP 2.4.21 source):
  - Node.js: `https://nodejs.org/dist` as an Ivy artifact `org.nodejs:node:<version>`, default `24.16.0` for `js` (docs say "The default Node.js version is currently 24.16.0") and `26.2.0` for `wasmJs` (`WasmNodeJsRootPlugin`: `nodeJsRoot.version = "26.2.0"`), unpacked to `<GRADLE_USER_HOME>/nodejs`.
  - Yarn (classic) from `https://github.com/yarnpkg/yarn/releases/download`, to `<GRADLE_USER_HOME>/yarn` (`com.yarnpkg:yarn`).
  - npm packages (Mocha and its transitive deps for `js`; tooling for `wasmJs`) from the configured npm/Yarn registry. `wasmJs` tooling goes to `<kotlin-user-home>/kotlin-npm-tooling/...` (outside the project; `hasSharedNpmToolingDir()` is `true` only for WasmJS); `js` tooling goes to the project's `build/js`.
- **Lock files:** `js` writes `kotlin-js-store/yarn.lock` and it contains the Mocha tooling closure (kotlinx-datetime's committed lock lists `ansi-colors`, `browser-stdout`, ... alongside `@js-joda/*`). Kotlin docs: "commit `kotlin-js-store` and its contents" ([js-project-setup](https://kotlinlang.org/docs/js-project-setup.html); claim 22). `yarnLockMismatchReport` defaults to `FAIL`, `reportNewYarnLock` to off. For `wasmJs` with no npm dependencies, no project-level lock is generated (2.2.20 note, F7). Three of five libraries checked commit `kotlin-js-store/yarn.lock` (kotlinx-datetime v0.8.0, Okio parent-3.18.2, kotlinx-serialization v1.11.0); kotlin-logging 8.0.4 and kotlinx-coroutines 1.11.0 do not.
- **Maintenance consequence:** a committed `js` lock goes stale with each KGP bump (tooling ranges change) and then `kotlinNpmInstall` fails on mismatch until `kotlinUpgradeYarnLock` is run and committed. An uncommitted lock has no churn but is not reproducible across runs.
- **Offline:** after a first run the Node/Yarn archives are in `~/.gradle`, but a full offline `--offline` run was not verified (see *Gaps*). The first run needs network access to nodejs.org, GitHub and the npm registry; so does every clean CI run unless the Gradle user home is cached.
- **Does `nodejs()`-only limit browser consumers? No** (Practice). The published variants carry only `org.jetbrains.kotlin.platform.type` (`js`, or `wasm` + `org.jetbrains.kotlin.wasm.target=js`), `org.jetbrains.kotlin.js.compiler=ir` (js), usage and category. In `kotlin-logging-8.0.4.module`, `jsApiElements-published` has no browser/node attribute, and `wasmJsApiElements-published` has `"org.jetbrains.kotlin.platform.type": "wasm"` and `"org.jetbrains.kotlin.wasm.target": "js"` only (claim 25). `browser()`/`nodejs()` configure test and run tasks, not the published klib.

### F13. CI (Consensus; versions read 2026-10-15)

- Needs: a JDK 17 for Gradle (and as the toolchain), the Gradle wrapper, network. It does **not** need `actions/setup-node`: KGP downloads Node itself (F12).
- Current actions: `actions/checkout` v7.0.1 (2026-07-20), `actions/setup-java` v6.1.0 (2026-10-14), `gradle/actions` v6.4.0 (2026-09-28), `actions/cache` v6.1.0. The current workflow uses `checkout@v2` and `setup-java@v2` with `distribution: adopt`; `setup-java` v6 removed the AdoptOpenJDK distributions ("Use `temurin` instead of `adopt`") and says v1-v4 are deprecated (claim 27). `gradle/actions/setup-gradle@v6` caches `caches`, `notifications` and wrapper distributions by default; Node/Yarn in `~/.gradle/nodejs`, `~/.gradle/yarn` are not in that default set (add via `gradle-home-cache-includes`, or accept a re-download of ~tens of MB per run). v6's default caching provider is its "Enhanced Caching" (free for public repos); `cache-provider: basic` is the MIT thin wrapper over `actions/cache`.
- The `chmod +x ./gradlew` step is unnecessary if the executable bit is committed; keep it if not sure.

### F14. Version catalog (Opinion, with docs)

Not worth introducing for this single module (about six coordinates, one plugin block). Gradle's own pitch is "Centralized Version Management: Each catalog is visible to all projects in a build" (claim 34), which is a multi-project benefit; MyGameTools' own build-logic comment records the same call for a four-module repo ("this repo has no version catalog"). The two values that deserve a single source of truth here (`kotlinFloor = "2.2.0"`, `jvmFloor = 17`) belong as two local `val`s at the top of `build.gradle.kts` (or `gradle.properties`). Revisit if the repo grows modules.

## 5. Pitfalls and regrets

1. **Global `coreLibrariesVersion` downgrade breaks js/wasmJs compilation** (F5). The obvious reading of option (b) is wrong for this reason; split by target.
2. **jvmTest does not prove the 2.2.0 floor.** `kotlin-test` and the test compilations stay at the KGP version, and Gradle's highest-wins means `jvmTest` runs on stdlib 2.4.21 even when the main variant declares 2.2.0. The pins are only proven by compiling a Kotlin 2.2.0 JVM consumer against the published artifact (overlaps R8/D8). tapmoc's `checkDependencies()` additionally fails the build if an `api` dependency leaks incompatible metadata/stdlib/class files.
3. **`languageVersion` does not constrain the web klibs** (F4); neither does `apiVersion`. State in the 3.0.0 notes that web consumers need Kotlin >= 2.4.
4. **The 2.2 pin has an expiry.** 2.5.0-Beta1 makes 2.2 deprecated (`FIRST_NON_DEPRECATED = KOTLIN_2_3`); it will later become unsupported. Plan the bump together with MyGameTools' own Kotlin upgrade (or move the floor to 2.3, which the N+1 rule still allows for 2.2.0 consumers).
5. **`java-library` + KMP is a hard error** (Gradle >= 8.7). The `api(...)`/`implementation(...)` blocks become source-set dependencies.
6. **Silent `org.gradle.jvm.version` regression:** KMP publishes none, so Java 11 consumers get a runtime class-version error instead of a resolution error unless set.
7. **Committed `kotlin-js-store/yarn.lock` churns on each KGP bump** and the default `yarnLockMismatchReport = FAIL` turns that into a red CI until `kotlinUpgradeYarnLock` is committed. Not committing it removes the churn but loses reproducibility; either is defensible, pick one deliberately.
8. **CI network dependency:** Node (nodejs.org), Yarn (GitHub releases) and npm are fetched on a clean runner; outages fail the build. Caching `~/.gradle` partly helps.
9. **Wasm is Beta and changes behaviour in minors** (2.4.20 companion init order, top-level `require()` error). Pin KGP exactly, bump deliberately, and expect `wasmJsNodeTest` to be the first thing a bump breaks. `wasmJs()` still needs `@OptIn(ExperimentalWasmDsl::class)`.
10. **Two Node installs** (24.16.0 for js, 26.2.0 for wasm) is normal in 2.4.21, not a misconfiguration.
11. **vanniktech 0.36.0 is not documented as tested against KGP 2.4.x** (F11).
12. **tapmoc is 0.x and renamed its package in 0.5.0** (published 2026-10-13); a hand-written pin has no dependency and is about ten lines.

## 6. Recommendation for this repo

**Plugin and Gradle.** `kotlin("multiplatform") version "2.4.21"`; remove `kotlin("jvm")` and `java-library`; keep Gradle 9.0.0, `foojay-resolver-convention 1.0.0`. (vanniktech version: R2 decides; note 0.37.0 is the first documented against 2.4.) Reject option (a): on 2.2.0 `wasmJs` is pre-Beta, there is no `webMain`, and Gradle 9.0.0 is outside KGP 2.2.x's documented range. Reject the literal option (b) of a global `coreLibrariesVersion` pin: it breaks the web compilations.

**Compatibility pins (one constant, `kotlinFloor = 2.2`).**
- At `kotlin { compilerOptions { ... } }` (extension level, applies to all targets and shared source sets): `languageVersion` and `apiVersion` = `KotlinVersion.KOTLIN_2_2`. This makes JVM class metadata 2.2.0 and API-checks against stdlib 2.2.
- Stdlib: leave `coreLibrariesVersion` alone. Add `api("org.jetbrains.kotlin:kotlin-stdlib:2.2.0")` to `commonMain` (the JVM and the common-metadata variants then publish `requires 2.2.0`). Add `api("org.jetbrains.kotlin:kotlin-stdlib:<KGP version>")` to `webMain` (or `jsMain` and `wasmJsMain`) so the JS/Wasm compilations use the compiler-matching stdlib; the duplicate requirement in the web variants is harmless (Okio publishes it). The alternative is `com.gradleup.tapmoc` 0.5.0 with `tapmoc { kotlin("2.2.0"); java(17) }`, which does the same and adds `checkDependencies()`; I prefer the hand-written version because it avoids a young 0.x plugin dependency and the logic is tiny, but tapmoc is a reasonable swap if the spike shows the manual version fiddly.
- If compiling `js`/`wasmJs` with `languageVersion = 2.2` under 2.4.21 turns out to misbehave in the spike, fall back to setting `languageVersion`/`apiVersion` only in `jvm { compilerOptions { ... } }` (the JVM compile is then still the gate for what commonMain may use).
- Guard: a small consumer check (Kotlin 2.2.0 `kotlin("jvm")` project resolving the locally published `GeneralTools-jvm`, compiling one line using `Color` and `Point`) is the only real proof of B1; fold it into R8/D8's pre-publish verification.

**Targets and source sets.** `jvm()`, `js { nodejs() }`, and `@OptIn(ExperimentalWasmDsl::class) wasmJs { nodejs() }`. Everything in `commonMain`/`commonTest` plus `jvmMain`/`jvmTest` per B6; create no `webMain` unless R4 needs a shared JS/Wasm `actual`. Keep the default hierarchy template. No `browser()`.

**JVM 17.** One constant `jvmFloor = 17`: `kotlin { jvmToolchain(jvmFloor) }` and `jvm { compilerOptions { jvmTarget.set(JvmTarget.JVM_17) } }`. Optionally `jvm { attributes { attribute(TargetJvmVersion.TARGET_JVM_VERSION_ATTRIBUTE, 17) } }` so the Gradle metadata declares 17 (recommended, mirrors kotlinx-datetime). Do not add `-Xjdk-release` while the toolchain pins 17.

**Tests/runtime.** `./gradlew check` runs `jvmTest`, `jsNodeTest`, `wasmJsNodeTest`; R5 attaches package filters to those three. Commit `kotlin-js-store/yarn.lock` after the first run (js only; recommended by the Kotlin docs and by three of five comparables), and record in the contributor notes that a KGP bump needs `./gradlew kotlinUpgradeYarnLock`. If the maintainer prefers zero churn, ignore the directory instead; this is a policy call for the user, not a technical one.

**CI.** `actions/checkout@v7`, `actions/setup-java@v6` with `distribution: temurin`, `java-version: 17`, then `gradle/actions/setup-gradle@v6` (or keep the plain `./gradlew build` and only upgrade the two actions), no Node step, no `chmod` if the exec bit is committed. Trigger and OS unchanged (`ubuntu-latest`).

**Catalog.** None (F14).

**The reasoning in two sentences.** The Kotlin JVM compatibility window is one minor wide and is set by two independent artifacts (class metadata and the declared stdlib), so the stable fix is to pin both explicitly on the JVM and let everything else follow a modern KGP. The web klibs cannot be pinned (KT-66755), so the web floor is "Kotlin >= the KGP minor you build with", which is why the web side deliberately follows KGP 2.4.21.

**Alternative worth the user's attention (not my first choice).** KGP **2.3.21** (Ktor 3.6.0's choice): web klibs at ABI 2.3.0 (readable by Kotlin >= 2.3), Gradle 9.0.0 officially supported, vanniktech 0.36.0 tested against 2.3.x, and by the N+1 rule JVM 2.2.0 consumers compile with no stdlib pin at all (stdlib 2.3.21 has `mv = [2,3,0]`). The price: it only works while the build sits exactly one minor above the consumer; the first KGP bump re-introduces the stdlib and metadata problem, and 2.3 is the older line. If SpartanGraphics/SpartanUI end up pinned to Kotlin 2.3, this is the option that serves them.

## 8. Gaps

- **Nothing was built or run.** The following are inferred from source, docs and published artifacts, and each needs one spike run before the plan relies on it: (1) that `languageVersion = apiVersion = 2.2` at the extension level compiles `js`/`wasmJs` and the common-metadata task under KGP 2.4.21 (analogues: Okio sets LV/API 2.1 on 2.2.21 for all targets via tapmoc; Ktor sets API 2.2/LV 2.3 on 2.3.21; I found no check that rejects it, and `setupKlibAbiCompatibilityLevel` simply keeps `LATEST_STABLE` when the older-ABI feature is off); (2) that the explicit `commonMain` stdlib 2.2.0 plus `webMain` stdlib at KGP version resolves as intended, with the expected `requires` in the published `.module` (Okio's published module shows the shape, not our build); (3) `check` end-to-end including `kotlinNpmInstall`/Yarn on Windows and `ubuntu-latest`, and under the maintainer's enabled configuration cache (no incompatibility found; absence of evidence only); (4) whether a `kotlin-js-store/yarn.lock` appears for `js` with no npm dependencies other than Mocha tooling (kotlinx-datetime's and Okio's committed locks suggest yes); (5) whether `--offline` works after a warm cache (Node/Yarn archives are cached under `~/.gradle`, the npm cache location for `kotlinNpmInstall` was not traced).
- **B1 proof is derived, not tested.** The claim "a Kotlin 2.2.0 JVM consumer compiles against a KGP 2.4.21 build with LV/API 2.2 and stdlib 2.2.0" follows from the compiler's metadata rule (F1), the stdlib `mv` decode (F2) and precedent (Okio, Ktor, kotlinx.* libraries consumed on older Kotlin), but I did not compile a 2.2.0 consumer. Recommend the consumer smoke test (R8/D8).
- **`org.gradle.jvm.version` under the toolchain** is concluded from KGP source (no `TargetJvmVersion` set) and from Ktor 3.6.0, Coil 3.6.3, kotlinx-io, Okio, coroutines modules, not from running `generateMetadataFileForKotlinMultiplatformPublication` here. Ktor's build was read for `jvmToolchain`; the others' build files were not.
- **KGP 2.2.0's wasm Node/canary behaviour** and the exact failure of KGP 2.2.0 on Gradle 9.0.0 for KMP were not established (the `v2.2.0` source path for the wasm Node plugin was not found; the matrix says "outside range", which is all I rely on).
- **Kotlin release dates:** the kotlin-web-site headers and `gh release list` disagree for 2.4.0 (header says July 14, 2026; tag says 2026-06-03). I used the GitHub tag dates; nothing here depends on it.
- **Fetcher-extracted quotes** (claims 7, 29, 30, 34) came from a summarising fetch, not a raw read; the verifier should re-open them. All source-code and markdown quotes were read raw.
- **Not looked at:** the kotlinx-coroutines and kotlinx-serialization build files (only their published modules), Karma/Playwright browser test behaviour on CI, `kotlin-test` variant inference per target (R5), Dokka/javadoc and signing for KMP (R2), `explicitApi()` and ABI validation (R7), numeric parity on JS/Wasm (R4).
- **Open user decisions this exposes:** (a) KGP 2.4.21 + pins versus KGP 2.3.21 with no stdlib pin (section 6); (b) commit or ignore `kotlin-js-store/yarn.lock`; (c) set `org.gradle.jvm.version = 17` explicitly or not. None blocks design, but (a) fixes the Kotlin floor that web consumers see.
