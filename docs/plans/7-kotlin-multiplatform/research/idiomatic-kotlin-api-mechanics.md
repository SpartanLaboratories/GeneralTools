# Kotlin language mechanics for the 3.0.0 API breaks, and proving the API changes by exactly the intended set

- **Issue:** [SpartanLaboratories/GeneralTools#7](https://github.com/SpartanLaboratories/GeneralTools/issues/7) (Kotlin Multiplatform; the same change resolves #8).
- **Date read:** 2026-10-17. Repo baseline: branch `feat/issue-7-kotlin-multiplatform`; `git diff 2.2.0 master -- src/main` is empty, so tag `2.2.0` and `master` (`17d30bc`) have identical main sources.
- **Pinned outside sources:** Kotlin `v2.2.0`, `v2.3.0`, `v2.4.21`; binary-compatibility-validator (BCV) `0.18.2`; Okio `parent-3.18.2`; kotlinx.coroutines `1.11.0`; kotlinx.serialization `v1.11.0`; Ktor 3 migration guide (read 2026-10-17).
- **Method limits:** nothing was compiled or run. Language behaviour comes from compiler source and compiler test data at the pinned tags, the Kotlin documentation, and published API dumps of other libraries. Every prediction about what a dump will contain is derived by hand from the source plus those references, and is marked as a prediction. *Gaps* lists what a short spike settles.
- Sibling reports: [`kmp-build-and-kotlin-compat.md`](kmp-build-and-kotlin-compat.md), [`immutable-geometry-model.md`](immutable-geometry-model.md), [`cross-platform-behaviour-parity.md`](cross-platform-behaviour-parity.md), [`kotlin-logging-adoption.md`](kotlin-logging-adoption.md).

## 1. Question

Which Kotlin language mechanics express the 3.0.0 breaks other than the geometry model (`Color`'s constructor, the `Result` return of `divideBy`, `evaluateList`'s signature, the removal of `com.spartanlabs.logging`, the JVM facade of the split `Misc` functions, the opt-in marker for subclassing `TwoDoubles`), and how is it proven that the public API changes by exactly the intended set?

Requirements an answer meets, as plain facts about the work:

- 3.0.0 makes exactly these breaks: `Color`'s primary constructor becomes `internal`; `TwoDoubles` is no longer `sealed`; `Point` and `Dimensions` become immutable; `TwoDoubles.divideBy` returns a `Result`; `evaluateList` takes `(T) -> Boolean` and lives in common code; the `com.spartanlabs.logging` package is removed. Breaks are clean, with no deprecation cycle. Everything else stays source-compatible.
- `read`, `asURL`, `Logger.time` and `UserActions` stay JVM-only.
- Consumers include a JVM-only Kotlin 2.2.0 build and future Kotlin Multiplatform consumers; the build pins `languageVersion`/`apiVersion` 2.2 ([kmp-build-and-kotlin-compat.md](kmp-build-and-kotlin-compat.md)).
- Migration notes go in the README and the GitHub release; the repository has no `CHANGELOG.md`.
- Anything reachable by a consumer is public API with KDoc contracts; an Experimental seam is gated by a `@RequiresOptIn` marker and says in its KDoc that it may change in a minor.

## 2. Bottom line

- **`Color`: keep the `data class`, make the constructor `internal`, and annotate the class `@ExposedCopyVisibility`.** That leaves exactly two JVM-dump lines gone (`<init>(IIII)V` and its synthetic default-argument twin). `copy`, `component1..4`, `equals`, `hashCode` and `toString` stay public and unchanged. With no annotation the build compiles at `languageVersion` 2.2 but warns on the declaration and the warning becomes an error at language version 2.5 (or in progressive mode); `@ConsistentCopyVisibility`, a plain final class and a value class each remove or change more than the listed set. Even with `@ExposedCopyVisibility`, consumers that call `copy` get a compiler warning, so the notes must name `copy`.
- **Keep the plain name `divideBy` for the `Result`-returning function, and accept that no compile-time guard against a dropped `Result` is usable.** The Kotlin guidelines reserve the `Catching` suffix for a paired throwing/wrapping overload (none remains after 3.0.0) and the repo already returns `Result` from seven plain-named functions. `@MustUseReturnValues` is `@SinceKotlin("2.3")`, Experimental and off by default, so a library at `apiVersion` 2.2 cannot apply it. KDoc and the migration notes are the only guards.
- **`evaluateList` becomes a non-`inline` `fun <T> evaluateList(list: Iterable<T>, validator: (T) -> Boolean): Boolean`.** Trailing-lambda callers (including this repo's tests) compile unchanged; callers holding a `Predicate` variable or writing `Predicate { }` break; the JVM descriptor changes from `Predicate` to `Function1`. `inline` would force a `@PublishedApi` logger into the ABI.
- **One JVM facade `MiscKt`:** put `@file:JvmMultifileClass` and `@file:JvmName("MiscKt")` on the common `Misc.kt` and on a differently named JVM file (for example `MiscJvm.kt`), as Okio does for `Okio`. Both annotations are optional-expectation annotations usable in common code. Keep every other moved file's name and package, because the facade class is derived from them.
- **Opt-in marker:** a new `@RequiresOptIn(level = ERROR)` annotation with `@Retention(BINARY)` and an empty `@Target()` (the `SealedSerializationApi` shape), applied through `@SubclassOptInRequired`. The marker class appears in the JVM and klib dumps; the gating annotations do not, so a dump cannot prove the gate.
- **Proof:** enable the Kotlin Gradle plugin's experimental `abiValidation()` (dumps `api/GeneralTools.api` and `api/GeneralTools.klib.api`; `check` runs `checkKotlinAbi`), take the baseline from tag `2.2.0`, commit a build-migration checkpoint whose JVM dump must be unchanged, then review each break commit's dump diff against a break ledger. `explicitApi()` strict mode costs about 100 added `public` modifiers and about 35 added return types, changes no API, and should land in its own commit before the breaks. Breaks the dump cannot show (`sealed` to open, opt-in gating, behaviour) need compile or unit checks of their own.

## 3. Findings

Tiers: **consensus** = spec, official documentation or several independent credible sources; **practice** = what mature libraries visibly do; **source-read** = read from compiler or library source at the pinned version, not executed; **opinion** = one source.

### F1. `Color` with an `internal` primary constructor

**F1.1 What the compiler does to `copy` at language version 2.2 (source-read, consensus).**

- KT-11914 changes the generated `copy` of a data class with a non-public primary constructor in three phases. The language features in the compiler show the schedule: at `v2.2.0` `ErrorAboutDataClassCopyVisibilityChange(KOTLIN_2_3, ...)` ("Deprecation phase 2"); at `v2.3.0` and `v2.4.21` it moved to `KOTLIN_2_5, enabledInProgressiveMode = true`; `DataClassCopyRespectsConstructorVisibility` ("Deprecation phase 3", the default change) is `sinceVersion = null` at all three tags ([LanguageVersionSettings.kt @ v2.2.0](https://github.com/JetBrains/kotlin/blob/v2.2.0/compiler/util/src/org/jetbrains/kotlin/config/LanguageVersionSettings.kt), [@ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/core/language.version-settings/src/org/jetbrains/kotlin/config/LanguageVersionSettings.kt)).
- So with `languageVersion` 2.2, on compiler 2.2.0 or 2.4.21, the build is in phase 1: `copy` is still generated public; there is a **warning** on the constructor declaration (`DATA_CLASS_COPY_VISIBILITY_WILL_BE_CHANGED_WARNING`) unless the class carries `@ConsistentCopyVisibility` or `@ExposedCopyVisibility` ([compiler test data `deprecationPhase1_warning.kt` @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/compiler/testData/diagnostics/tests/dataClassNonPublicConstructor/deprecationPhase1_warning.kt); the checker `FirDataClassNonPublicConstructorChecker` @ [v2.2.0](https://github.com/JetBrains/kotlin/blob/v2.2.0/compiler/fir/checkers/src/org/jetbrains/kotlin/fir/analysis/checkers/declaration/FirDataClassNonPublicConstructorChecker.kt) returns early only when the class is annotated or the phase-3 feature is on).
- The declaration warning turns into an error at language version 2.5 or in progressive mode. The 2.2 pin in [kmp-build-and-kotlin-compat.md](kmp-build-and-kotlin-compat.md) expires on that horizon, so an unannotated class is a latent build failure.
- Both annotations are `@SinceKotlin("2.0")`, `@Target(CLASS)`, `@Retention(BINARY)` in the common stdlib, so they are usable at `apiVersion` 2.2 in common code ([ConsistentCopyVisibility.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/stdlib/src/kotlin/annotations/ConsistentCopyVisibility.kt)).

**F1.2 What each choice does to members (source-read: compiler ABI test data on the JVM).**

| Choice | constructor | `copy` / `copy$default` | `componentN`, `equals`, `hashCode`, `toString` |
|---|---|---|---|
| `internal constructor`, no annotation | Kotlin-internal | public, unchanged; declaration warning (error from language version 2.5) | public, unchanged |
| plus `@ExposedCopyVisibility` | Kotlin-internal | public, unchanged binary signature | public, unchanged |
| plus `@ConsistentCopyVisibility` | Kotlin-internal | `copy` becomes `internal` and is mangled with the module name (`copy$main` in the test; `copy$<module>` here) | public, unchanged |

([jvm-abi-gen test data, ExposedCopy](https://github.com/JetBrains/kotlin/blob/v2.4.21/plugins/jvm-abi-gen/testData/content/dataClassNonPublicConstructorExposedCopy/signatures.txt) and [ConsistentCopy](https://github.com/JetBrains/kotlin/blob/v2.4.21/plugins/jvm-abi-gen/testData/content/dataClassNonPublicConstructorConsistentCopy/signatures.txt) at `v2.4.21`.)

- **Call sites of `copy` in consumers are flagged either way.** The checker `FirDataClassCopyUsageWillBecomeInaccessibleChecker` reports `DATA_CLASS_INVISIBLE_COPY_USAGE` when the constructor is not visible at the call site and says: "We don't check the presence of @ExposedCopyVisibility annotations on purpose. Even if the 'copy' is exposed, call-sites need to migrate." It is a warning at language versions below 2.5 and an error from phase 2 ([checker @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/compiler/fir/checkers/src/org/jetbrains/kotlin/fir/analysis/checkers/expression/FirDataClassCopyUsageWillBecomeInaccessibleChecker.kt)). `@ExposedCopyVisibility` therefore preserves binary compatibility, not long-term source compatibility, for `copy`. The downstream repositories read for this report (MyGameTools, GameGraphics, MyGameServer) contain no `copy` call on a `Color`; they call the constructor and destructure only the `FloatArray` from `normalized()`.
- **`internal` is a Kotlin-level rule, not a JVM one.** In the same test data the internal constructor is `public method <init>(p0: int): void` in the class file, and constructors are not name-mangled. Java callers, and already-compiled Kotlin callers, can still link to `Color.<init>(IIII)V` at runtime; recompiled Kotlin callers cannot compile against it. The API dump follows the Kotlin metadata and hides it ([BCV README, "What constitutes the public API"](https://github.com/Kotlin/binary-compatibility-validator/blob/0.18.2/README.md)).
- **What leaves the dump.** BCV's own test for a public class with `internal constructor(name: String, flags: Int = 0)` dumps an empty class (`public final class cases/default/ClassConstructors {\n}`), so for `Color` both `<init>(IIII)V` and `<init>(IIIIILkotlin/jvm/internal/DefaultConstructorMarker;)V` disappear ([BCV test case `default/constructors.kt` and `default.txt` @ 0.18.2](https://github.com/Kotlin/binary-compatibility-validator/tree/0.18.2/src/test/kotlin/cases/default)). The KGP built-in tool is a port of the same code with the same `isPublishedApi` and Kotlin-visibility rules ([`AsmMetadataLoading.kt`, `KotlinMetadataSignature.kt` @ v2.4.21](https://github.com/JetBrains/kotlin/tree/v2.4.21/libraries/tools/abi-validation/abi-tools/src/main/kotlin/org/jetbrains/kotlin/abi/tools/impl/jvm)).

**F1.3 Alternatives (reasoned; consensus on the Kotlin rules).**

- **Plain final class with hand-written members.** Removes `copy` and `component1..4` (source and binary), and `equals`/`hashCode`/`toString` must be rewritten to the same output (`toString` is `Color(red=.., green=.., blue=.., alpha=..)` today). That is five further breaks. The Kotlin API guidelines do advise against data classes in public APIs because the generated `copy` and `componentN` freeze the property list ([API guidelines, backward compatibility](https://kotlinlang.org/docs/api-guidelines-backward-compatibility.html), "Avoid using data classes in your API"), so this is the end state worth considering at a later major, not in this one.
- **`@JvmInline value class Color internal constructor(val packed: Int)`.** Every function with a `Color` parameter is name-mangled with a hash on the JVM ([Kotlin docs, inline value classes, "Mangling"](https://kotlinlang.org/docs/inline-classes.html)), `Color?` and generic uses box, there is no `copy` or `componentN`, and a packed `Int` cannot represent the channel values `0..255` outside the range that the current constructor documents as "not validated". This changes the signature of every `Color`-typed member in both dumps and is far outside the set.
- **`@ConsistentCopyVisibility`.** The idiomatic end state of the Kotlin migration (the stdlib KDoc recommends it over `@ExposedCopyVisibility` for code that does not need binary compatibility), but it removes `copy` and `copy$default` from the dump: one break beyond the listed set. Moving from Exposed to Consistent later is itself a break, so this is a one-way door.

### F2. Naming for functions that return `Result`, and the discarded-result hazard

**F2.1 Convention (consensus for the suffix; opinion-level disagreement on whether to return `Result` at all).**

- The Kotlin API guidelines: "Consider providing overloads of functions, where one throws an exception, while the other wraps it in a result type instead. In these cases, use the `Catching` suffix to indicate that exceptions are caught in the function." Examples named there: `run`/`runCatching`, `receive`/`receiveCatching` ([API guidelines, consistency](https://kotlinlang.org/docs/api-guidelines-consistency.html)). KEEP-0127 states the same convention: "Functions that capture thrown exception and encapsulate it into `Result` instance are named with explicit `Catching` suffix like `runCatching` and `mapCatching`" ([KEEP-0127](https://github.com/Kotlin/KEEP/blob/main/proposals/stdlib/KEEP-0127-result.md)). `OrNull` is the pairing for a `null` result (`first`/`firstOrNull`; kotlinx-datetime 0.8.0 adds `orNull` and `parseOrNull` for non-throwing construction, [CHANGELOG](https://github.com/Kotlin/kotlinx-datetime/blob/v0.8.0/CHANGELOG.md)).
- Both rules name a *pair*. After 3.0.0 `divideBy` has no throwing sibling, so there is nothing to disambiguate. The repo's seven existing `Result`-returning functions (`distanceFrom`, `normalized()`, `asRay()`, `unit()`, `segmentIntersectsSegment`, `segmentIntersectsBox`, `rayIntersectsBox`) all use plain names; renaming `divideBy` would also be a source break outside the set.
- **Disagreement to record.** KEEP-0127 says the `Result` class "is not designed to represent domain-specific error conditions" and shows `fun findUserByName(name: String): Result<User> // ERROR` as the discouraged shape, preferring nullable types or a sealed result type for failures a caller handles locally. The repo's paradigm (expected failures as `Result`) is the opposite choice, and the guidelines page itself permits it ("In other cases, throw an exception or return a `Result` type"). The disagreement turns on whether a degenerate geometric input is a "programming error" (exception), "missing data" (null) or an "expected, locally handled outcome" (the repo's view). It is a settled requirement here, not an open call; the notes should not describe `Result` as the Kotlin-recommended style.
- **JVM naming consequence (source-read).** Member functions returning an inline class are name-mangled on the JVM since Kotlin 1.4 (`MangleClassMembersReturningInlineClasses(KOTLIN_1_4, ...)`), and top-level functions are not (`hasMangledReturnType = returnType.isInlineClassType() && parentClassOrNull?.isFileClass != true`) ([InlineClassAbi.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/compiler/ir/backend.jvm/src/org/jetbrains/kotlin/backend/jvm/InlineClassAbi.kt)). So `divideBy` appears in the dump as `divideBy-<hash> (D)Ljava/lang/Object;`, like the existing member `Point.distanceFrom`, and Java callers see a mangled name. The hash was not computed.

**F2.2 Warning consumers who drop a `Result` (source-read, consensus; none is usable).**

- Kotlin 2.3.0 introduced an unused return value checker; its status is Experimental, and "`disable` disables the unused return value checker (default)" ([What's new in Kotlin 2.3.0](https://kotlinlang.org/docs/whatsnew23.html); [unused return value checker](https://kotlinlang.org/docs/unused-return-value-checker.html)). A library marks APIs with `@MustUseReturnValues` on a file or class (not a function); a consumer sees reports only when the consumer enables `-Xreturn-value-checker=check` or `full`.
- The annotation is `@Target(FILE, CLASS) @SinceKotlin("2.3") public annotation class MustUseReturnValues` at `v2.3.0` and `v2.4.21`. At `v2.2.0` the file held a differently spelled `MustUseReturnValue` (singular, `@SinceKotlin("2.2")`) which was renamed ([ReturnValue.kt @ v2.2.0](https://github.com/JetBrains/kotlin/blob/v2.2.0/libraries/stdlib/src/kotlin/annotations/ReturnValue.kt), [@ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/stdlib/src/kotlin/annotations/ReturnValue.kt)). With `apiVersion` 2.2 the 2.3-only name is not available to the library, and a Kotlin 2.2.0 consumer would not know it. The docs also list Java annotations (`com.google.errorprone.annotations.CheckReturnValue` and others) as equivalents, but Java annotations cannot be referenced from common code.
- Consequence: the discarded `p divideBy 2.0` statement ([immutable-geometry-model.md](immutable-geometry-model.md) section 3.4) compiles and does nothing, and no mechanism usable at `languageVersion`/`apiVersion` 2.2 warns about it. Mitigations are documentation: the KDoc of `divideBy` states that the result must be used, and the migration notes name `divideBy` as the one break that does not fail to compile. A consumer on Kotlin 2.3 or later can wrap its own calls in `val _ = ...` or enable the checker for its own code, but the library cannot make that happen.

### F3. `evaluateList(list: Iterable<T>, validator: (T) -> Boolean)`

- **Not `inline` (reasoned from the repo and the logging report).** The body logs through a private logger. A public `inline` function cannot reference a private member; it would need `@PublishedApi internal val log`, which BCV and the built-in tool treat as public API (`@PublishedApi internal` members are dumped; BCV test `inline/inlineExposed.kt` dumps `exposedForInline`), putting a kotlin-logging type into the ABI. [kotlin-logging-adoption.md](kotlin-logging-adoption.md) pitfall 3 already rules that out ("Do not expose kotlin-logging in public signatures or public `inline` functions"). The benefit of `inline` (no `Function1` allocation, non-local `return`) is negligible for a function that logs at TRACE, and changing inline-ness later is a binary break. The existing `onException` is `inline` for the opposite reason and carries a comment saying so.
- **Java callers.** The parameter becomes `kotlin.jvm.functions.Function1<T, Boolean>`; a Java lambda `x -> x > 0` fits, and the dump descriptor changes from `(Ljava/lang/Iterable;Ljava/util/function/Predicate;)Z` to `(Ljava/lang/Iterable;Lkotlin/jvm/functions/Function1;)Z` (prediction, derived from the signature). It is a binary break for compiled callers.
- **Kotlin callers.** `evaluateList(list) { it == 2 }` compiles unchanged (this repo's `MiscTest` uses exactly that). Breaking shapes: a `Predicate<T>` variable (`evaluateList(list, predicate)`: write `predicate::test` or `{ predicate.test(it) }`), and the explicit `Predicate { ... }` SAM constructor (write a plain lambda). Named-argument calls (`validator = ...`) keep working. Functionally `evaluateList(list, f)` equals `list.any(f)` apart from the TRACE logging.

### F4. One JVM facade for the split `Misc` functions

- **The mechanism (consensus, source-read).** `JvmName` (`@Target(FILE, FUNCTION, PROPERTY_GETTER, PROPERTY_SETTER)`) and `JvmMultifileClass` (`@Target(FILE)`) are both `@OptionalExpectation public expect annotation class` in the common stdlib, so common code may carry them and non-JVM targets ignore them ([JvmAnnotationsH.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/stdlib/common/src/kotlin/JvmAnnotationsH.kt)). In common code `kotlin.jvm.*` is not default-imported, so the file needs `import kotlin.jvm.JvmMultifileClass` and `import kotlin.jvm.JvmName`.
- **A working precedent with the exact shape (practice).** Okio `parent-3.18.2` has `okio/src/commonMain/kotlin/okio/Okio.kt` and `okio/src/jvmMain/kotlin/okio/JvmOkio.kt`, both starting `@file:JvmMultifileClass` and `@file:JvmName("Okio")`. Its published JVM dump `okio/api/okio.api` lists class `okio/Okio` with both the common function `buffer` and the JVM-only function `appendingSink` ([Okio.kt](https://github.com/square/okio/blob/parent-3.18.2/okio/src/commonMain/kotlin/okio/Okio.kt), [JvmOkio.kt](https://github.com/square/okio/blob/parent-3.18.2/okio/src/jvmMain/kotlin/okio/JvmOkio.kt), [okio.api](https://github.com/square/okio/blob/parent-3.18.2/okio/api/okio.api)). That is one JVM compilation of `commonMain` plus `jvmMain` producing one facade.
- **For this repo.** The facade is derived from the file name (`Misc.kt` gives `MiscKt`), so the JVM file needs a different name (a second `Misc.kt` in the same package would produce a duplicate JVM class `MiscKt`). Use `Misc.kt` in `commonMain` and for example `MiscJvm.kt` in `jvmMain`, both with the two annotations and `@file:JvmName("MiscKt")`. `read`, `asURL`, `Logger.time` then stay on `MiscKt` and the dump lines for them do not move. `JvmMultifileClass` needs `JvmName` on every part.
- **Dump treatment (source-read).** BCV drops a multifile facade only if it has no effectively public member ("it contains at least one effectively public member, in case if the class corresponds to a kotlin *file* with top-level members or a *multifile facade*"); the part classes are not dumped. The test pair `internalMultifile1.kt`/`internalMultifile2.kt` (`@file:JvmName("MultifileKt") @file:JvmMultifileClass`, internal members only) produces no class in the dump.
- **The other moved files.** `Vectors.kt` (`VectorsKt`: `EPSILON`, `dot`, `cross`, `length`, `lengthSquared`, `normalized`, `projectedOnto`), `Intersections.kt` (`IntersectionsKt`), `CenteredBox.kt` (`CenteredBoxKt`: `toCenteredBox`, `toSquare`) have public top-level members; their facade names stay as long as the file names and packages stay. `Point.kt`, `TwoDoubles.kt` and `Segment.kt` hold only a `private val log`, which compiles to a facade class (`PointKt`, `TwoDoublesKt`, `SegmentKt`) with a private static field. The tools do not list a facade without effectively public members, and they filter synthetic accessors for private fields, so these classes never reach a dump. They remain on the classpath; renaming a file renames its facade. After the kotlin-logging change the field type is a `KLogger` instead of an slf4j `Logger`; the class stays absent from the dump.
- **A file that moves whole** (`UserActions.kt` into `jvmMain`) keeps `UserActionsKt` because the name derives from the file name, not the directory.

### F5. The opt-in marker for subclassing `TwoDoubles`

**F5.1 Declaration (consensus on the rules, practice on the shape).**

- The Kotlin rules for a marker: it must have `BINARY` or `RUNTIME` retention, no `EXPRESSION`, `FILE`, `TYPE` or `TYPE_PARAMETER` target, and no parameters; `RequiresOptIn.Level.ERROR` is the default level and means "the code that uses marked API won't compile" ([opt-in requirements](https://kotlinlang.org/docs/opt-in-requirements.html)).
- `@SubclassOptInRequired(vararg markerClass)` is `@SinceKotlin("2.1")` with `@WasExperimental(ExperimentalSubclassOptIn::class)`, `@Target(CLASS)`, `@Retention(BINARY)` in the common stdlib ([OptIn.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/stdlib/src/kotlin/annotations/OptIn.kt)). At `apiVersion` 2.2 it is usable without the `ExperimentalSubclassOptIn` opt-in that kotlinx.coroutines 1.11.0 still writes. It gates subclassing of open and abstract classes only; using the type needs no opt-in. The requirement is not propagated to nested classes of the annotated class.
- A subclass opts in with `@OptIn(Marker::class)`, or propagates with `@SubclassOptInRequired(Marker::class)`, or, if the marker allows `CLASS` as a target, by annotating the subclass with the marker itself.
- Comparable markers at pinned tags:

| Marker | Level | Target | Use | Source |
|---|---|---|---|---|
| `ExperimentalStdlibApi` | ERROR | many | experimental use | [@ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/stdlib/src/kotlin/annotations/ExperimentalStdlibApi.kt) |
| `ExperimentalCoroutinesApi` | WARNING | many | experimental use | [@ 1.11.0](https://github.com/Kotlin/kotlinx.coroutines/blob/1.11.0/kotlinx-coroutines-core/common/src/Annotations.kt) |
| `ExperimentalForInheritanceCoroutinesApi` | WARNING | `CLASS` | `@SubclassOptInRequired` on `SharedFlow`, `MutableSharedFlow`, `StateFlow`, `Job`, ... | same file |
| `ExperimentalSerializationApi` | WARNING | `CLASS, PROPERTY, FUNCTION, TYPEALIAS` | experimental use | [@ v1.11.0](https://github.com/Kotlin/kotlinx.serialization/blob/v1.11.0/core/commonMain/src/kotlinx/serialization/ApiLevels.kt) |
| `SealedSerializationApi` | ERROR | none (`@Target()`, "no direct targets, only argument to @SubclassOptInRequired") | `@SubclassOptInRequired(SealedSerializationApi::class)` on `SerialDescriptor` | same file |

- Naming: the `Experimental<Area>Api` family is the convention; coroutines separates the inheritance marker from the use marker by name (`ExperimentalForInheritanceCoroutinesApi`). GeneralTools has no marker today, and a separate subclass-only marker leaves the name `ExperimentalGeneralToolsApi` free for later Experimental seams that gate use rather than subclassing. The name and package are the maintainer's call.
- **Level.** Raising a level later (`WARNING` to `ERROR`) breaks consumers who did not opt in; lowering it never does. `ERROR` is the conservative start and matches "use is a deliberate opt-in"; coroutines uses `WARNING` for its Experimental markers and states "This will be an error in a future release" for an inheritance marker, which is the pattern to avoid when starting from a clean slate.

**F5.2 What the dumps show (practice, from published dumps).**

- The marker class is dumped like any public annotation. JVM: `public abstract interface annotation class kotlinx/coroutines/ExperimentalForInheritanceCoroutinesApi : java/lang/annotation/Annotation {\n}`. klib: `open annotation class kotlinx.coroutines/ExperimentalForInheritanceCoroutinesApi : kotlin/Annotation { ... constructor <init>() ... }` ([kotlinx-coroutines-core.api](https://github.com/Kotlin/kotlinx.coroutines/blob/1.11.0/kotlinx-coroutines-core/api/kotlinx-coroutines-core.api), [kotlinx-coroutines-core.klib.api](https://github.com/Kotlin/kotlinx.coroutines/blob/1.11.0/kotlinx-coroutines-core/api/kotlinx-coroutines-core.klib.api)).

So the dump records that a marker exists, not that `TwoDoubles` is gated.
- **Consequence for proof.** The gate needs its own check: a throwaway source that subclasses `TwoDoubles` without opt-in must fail to compile (an error at level `ERROR`), and one with `@OptIn` must compile. The library's own subclasses `Point` and `Dimensions` need `@OptIn` or a module-wide `-opt-in` ([immutable-geometry-model.md](immutable-geometry-model.md) *Gaps* item 2).

Pinning KGP exactly bounds the exposure.

**F6.3 How the comparison proves "exactly the intended set" (reasoned).**

1. Commit the baseline `api/GeneralTools.api` (from tag `2.2.0`) before any source or build change.

3. Land each break as a separate commit with its dump diff. Review the combined diff of `api/GeneralTools.api` from the checkpoint to the release against the break ledger (section 6). Every added or removed line has to map to a ledger row; every ledger row that the dump can show must have its line.
4. Rows the dump cannot show get their own check: `sealed` to open (no sealed-ness in a JVM dump; the sealed class constructors are `protected` per the [sealed classes docs](https://kotlinlang.org/docs/sealed-classes.html), so constructor lines may change, which was not established), the opt-in gate (F5.2), `equals`/`hashCode` contract changes, and the WARN log level of `divideBy`. They are covered by unit tests and by the consumer smoke build planned in question 8 of [README.md](README.md).
5. From then on `check` runs `checkKotlinAbi`; a later pull request that changes the API fails until its author runs `updateKotlinAbi` and commits the diff.

### F7. `explicitApi()`

- **What strict mode requires (source-read).** On every public API declaration an explicit visibility modifier and, for public properties and expression-bodied functions, an explicit return type. Exclusions listed in the checker: primary constructors of public classes, properties of data or value classes and of annotations, overrides ("effectively, ... no report on overrides at all"), getters/setters, value parameters, anonymous and local functions; enum entries are exempt ([FirExplicitApiDeclarationChecker.kt @ v2.4.21](https://github.com/JetBrains/kotlin/blob/v2.4.21/compiler/fir/checkers/src/org/jetbrains/kotlin/fir/analysis/checkers/syntax/FirExplicitApiDeclarationChecker.kt)).
- **KMP behaviour.** "Configures default explicit API mode for all non-test compilations in the project" ([`KotlinTopLevelExtension.explicitApi`](https://kotlinlang.org/api/kotlin-gradle-plugin/kotlin-gradle-plugin-api/org.jetbrains.kotlin.gradle.dsl/-kotlin-top-level-extension-config/explicit-api.html)): set once on the `kotlin {}` extension it covers `commonMain` and `jvmMain`; test source sets are exempt. `explicitApiWarning()` reports the same issues as warnings.
- **Count in this codebase (my count of `src/main/kotlin` by reading each file; the removed `logging` package excluded).** About 100 public declarations lack a visibility modifier and about 35 lack an explicit type: `Color.kt` 30 and 14 (class, 10 members, `companion`, 14 constants `val WHITE = Color(...)`, 4 factories; the 14 constants and none of the functions lack types), `Misc.kt` 10 and 7, `UserActions.kt` 7 and 1, `AxisAlignedBox.kt` 6 (interface plus five members), `CenteredBox.kt` 5, `Intersections.kt` 7, `Point.kt` 7 and 4, `Ray.kt` 3, `Segment.kt` 6, `Square.kt` 1, `TwoDoubles.kt` 12 and 10, `Vectors.kt` 7. Roughly half of the `Point.kt` and `TwoDoubles.kt` counts disappear because those files are rewritten for the immutable model.
- **Effect.** No API change: public stays public and an explicit type only names the inferred one. The Kotlin API guidelines recommend it ("We recommend using the explicit API mode ..."). It keeps a new `commonMain` declaration from being exported to three targets by accident, which matters in the release that opens `TwoDoubles` and adds a marker. The SpartanGraphics plan already turns on `explicitApi()` together with `abiValidation()`.
- **Cost.** Review noise: about 135 mechanical edits in the same diff as the breaks hides the break edits. Landing it first, in its own commit with an unchanged dump, removes the noise and doubles as a second neutral checkpoint.

### F8. Migration notes for a major release (practice)

- **Ktor 2 to 3 migration guide** ([ktor.io](https://ktor.io/docs/migrating-3.html)): sections by area; the server section opens with a linked list of its breaking changes; each change is a short prose explanation followed by a rename table (old name, new name, package), an old/new code pair, or numbered steps.
- **Okio 3.0.0** ([CHANGELOG](https://github.com/square/okio/blob/parent-3.18.2/CHANGELOG.md), "Version 3.0.0"): opens with who is affected ("Most users should be able to upgrade from 2.x by just changing the version. If you're using Okio in a Kotlin Multiplatform project, you'll need to drop the `-multiplatform` suffix"), then one bullet per change, and labels the binary break explicitly ("This is a binary-incompatible change. We expect that this public API is very rarely used outside of Okio itself.").
- **kotlinx-datetime 0.8.0** ([CHANGELOG](https://github.com/Kotlin/kotlinx-datetime/blob/v0.8.0/CHANGELOG.md)): groups "Breaking changes:", "Additions:", "Tweaks and fixes:" with issue links.
- **Pattern to copy.** A who-is-affected sentence; a one-screen index mapping each compile error or symptom to its fix; per break a Before/After pair and a source/binary label; a separate list of changes that do not fail the build (behaviour, logging, artifact coordinates). The same text serves the README section and the GitHub release body.

## 5. Pitfalls and regrets

1. **An unannotated data class with a non-public constructor is a latent build failure.** It warns today and becomes an error at language version 2.5 or with `-progressive`, which is exactly when the 2.2 pin is raised ([kmp-build-and-kotlin-compat.md](kmp-build-and-kotlin-compat.md) pitfall 4).
2. **`@ExposedCopyVisibility` is not a promise to consumers.** The compiler flags their `copy` calls regardless; the annotation only protects binaries. KDoc cannot be attached to the generated `copy`, so the class KDoc has to say that `copy` does not clamp channels and that `withAlpha` and `Color.of` are the safe routes.
3. **The dump follows Kotlin visibility, not the JVM's.** `Color.<init>` is `public` in the class file after the change; Java code can still call it. State in the notes that it is unsupported rather than that it is removed.
4. **The dump is blind to several breaks:** `sealed` to open, opt-in gating, KDoc contracts, behaviour (WARN logging, `NaN` equality), and inline-function bodies. A clean dump diff does not prove those; it proves only the signature set.
5. **Experimental tooling churn.** The built-in tool's DSL changed between 2.2 and 2.4; BCV is in maintenance mode. Pin the Kotlin Gradle plugin exactly and re-read the plugin's DSL on every bump. The tool's own text format is shared, so a fallback to BCV needs no re-baselining (to be confirmed by the checkpoint in F6.3 step 2).
6. **Renaming a file renames its JVM facade.** Moving a file to `commonMain` is neutral; renaming `Vectors.kt` or `CenteredBox.kt` moves `VectorsKt`/`CenteredBoxKt` and breaks every compiled caller.
7. **Common code has no default `kotlin.jvm.*` import.** `@file:JvmName` and `@file:JvmMultifileClass` need explicit imports, as in Okio's `Okio.kt`.
8. **`inline` plus a logger.** A public `inline` function that logs forces a `@PublishedApi` logger into the ABI and a logging library into the semver surface.
9. **Exhaustive `when` over `TwoDoubles` stops compiling.** A consumer `when (x) { is Point -> ...; is Dimensions -> ... }` with no `else` was exhaustive over the sealed class (statements and expressions alike) and needs an `else` once `TwoDoubles` is open. This is part of the "no longer sealed" break and does not show in a dump.
10. **Guideline conflicts to acknowledge.** The Kotlin guidelines say to "follow a deprecation cycle" instead of removing declarations, and to avoid data classes in public APIs. 3.0.0 does neither by design (clean breaks; `Color` stays a data class). Both are defensible in a major version; the notes should say the breaks are clean.
11. **A dump diff can be satisfied by the wrong change.** Adding a source-compatible overload to hide a break would pass review of the dump; the ledger compares against intent, not against zero diff.

## 6. Recommendation for this repo

**Mechanics**

1. **`Color`.**
   ```kotlin
   @ExposedCopyVisibility
   public data class Color internal constructor(
       public val red: Int, public val green: Int, public val blue: Int, public val alpha: Int = 255,
   ) { ... }
   ```
   Companion constants and factories keep calling the internal constructor; `withAlpha` keeps calling `copy`. Rewrite the class KDoc: the public constructor no longer exists, `Color.of` clamps, `fromPackedInt`/`fromHex`/`fromNormalized` decode, `copy` does not clamp. Reject `@ConsistentCopyVisibility` for 3.0.0 only because removing `copy` is a break outside the listed set; it is the better end state, and the maintainer may choose it knowingly (one more row in the ledger, no downstream `copy` call on `Color` found). Reject the plain class and the value class (F1.3).
2. **`divideBy`** keeps its name; KDoc `@return` says that a discarded result performs no division. No suffix and no checker annotation.
3. **`evaluateList`:** `public fun <T> evaluateList(list: Iterable<T>, validator: (T) -> Boolean): Boolean`, not inline, logging unchanged, in `commonMain`'s `Misc.kt`.
4. **`Misc.kt` (common) and `MiscJvm.kt` (JVM)** both start with `@file:JvmMultifileClass` and `@file:JvmName("MiscKt")` plus the two `kotlin.jvm` imports. `read`, `asURL` and `Logger.time` live in `MiscJvm.kt`; everything else in `Misc.kt`. No other file is renamed.
5. **`com.spartanlabs.logging`:** delete `Logger.kt` and `MessageBuilder.kt` (four classes leave the dump). No replacement.
6. **Marker:**
   ```kotlin
   @RequiresOptIn(level = RequiresOptIn.Level.ERROR, message = "Subclassing TwoDoubles is Experimental and may change in a minor release.")
   @Retention(AnnotationRetention.BINARY)
   @Target() // usable only as an argument of @OptIn / @SubclassOptInRequired
   @MustBeDocumented
   public annotation class ExperimentalForInheritanceGeneralToolsApi   // name is the maintainer's call
   ```
   with `@SubclassOptInRequired(ExperimentalForInheritanceGeneralToolsApi::class)` on `TwoDoubles` and a KDoc paragraph on both that says it may change in a minor and that the first consumer to build against it triggers graduation to Supported Extension or Stable Core ([immutable-geometry-model.md](immutable-geometry-model.md) section 3.10).
7. **Tooling:** `kotlin("multiplatform") 2.4.21` as in [kmp-build-and-kotlin-compat.md](kmp-build-and-kotlin-compat.md); `kotlin { @OptIn(ExperimentalAbiValidation::class) abiValidation() ; explicitApi() }`. Prefer the built-in tool over BCV because the build already pins KGP exactly, it needs no extra plugin, the same files are produced by both, and SpartanGraphics uses it. Use BCV `0.18.2` (or KGP 2.2.0's legacy dump) only to produce the 2.2.0 baseline, in a scratch copy of the tag.
8. **Order of commits:** (a) baseline dump committed; (b) build migration with neutral dump; (c) `explicitApi()` with neutral dump; (d) one commit per break, each with its dump diff; (e) migration notes. The review artefact is the diff of `api/GeneralTools.api` from (b) to (d), checked against the ledger below.

## 8. Gaps

- **Nothing was compiled or run.** The dump predictions in section 6 are hand-derived. A spike on a scratch module settles all of them in one go: build the migrated sources, run `updateKotlinAbi`, and diff against the baseline.
- **The baseline tool.** Neither BCV `0.18.2` nor KGP 2.2.0's legacy dump was run against `kotlin("jvm")` 2.2.0 on Gradle 9.0.0. KGP 2.2.x is outside its documented Gradle range there; BCV's README states only Gradle 6.1.1+ and Kotlin 1.6.20+. Whether KGP 2.4.21's JVM dump is textually identical to BCV's output was not verified; the neutral checkpoint (F6.3 step 2) tests it. If they differ only in formatting, a format-only commit absorbs it.
- **`sealed` to open in a JVM dump.** Not established which constructor or modifier lines change (Kotlin sealed constructors default to `protected`; the JVM class is abstract either way). It is treated as invisible to the dump and covered by a compile check.
- **Consumer-side `copy` warning at the consumer's own compiler.** Read from the 2.4.21 checker; the 2.2.0 declaration checker was read, the 2.2.0 usage checker was not. MyGameTools builds with Kotlin 2.2.0 and does not call `Color.copy`, so this is not blocking.
- **`@SubclassOptInRequired` in the same module** (library subclasses `Point`/`Dimensions` needing `@OptIn`) and the `@Target()` marker in common code at `languageVersion` 2.2: precedent (kotlinx.serialization, kotlinx.coroutines) is for their own compiler versions; not compiled here. Same spike as [immutable-geometry-model.md](immutable-geometry-model.md) *Gaps* item 2.
- **The mangled `divideBy-<hash>` name** and whether the covariant `Result` override changes it are not computed; the hash is an md5 of the signature per `InlineClassAbi`.
- **`@file:JvmMultifileClass` with K2 KMP at language version 2.2 under KGP 2.4.21** is supported by precedent (Okio builds with KGP 2.2.21) but not run with this configuration.
- **`explicitApi()` counts** are my reading of each file, not compiler output; they are accurate to a handful. Running `explicitApiWarning()` once produces the exact list.
- **Maintainer calls this report cannot make:** `@ExposedCopyVisibility` (in-set, this report's choice) versus `@ConsistentCopyVisibility` (idiomatic end state, one break beyond the set); marker level (`ERROR` here) and name; BCV versus the built-in tool for the long term (the built-in one is Experimental and BCV is in maintenance mode).
- **Not looked at:** Dokka output of the `@Target()` marker; how the built-in tool renders `@PublishedApi internal` in klib dumps (the JVM rule is source-confirmed, the klib one is assumed identical); IDE inspections that flag an unused `Result`.
