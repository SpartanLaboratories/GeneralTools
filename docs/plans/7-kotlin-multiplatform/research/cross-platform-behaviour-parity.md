# Cross-platform behaviour parity of the pure tests on `jvm`, `js` and `wasmJs`

- **Issue:** [SpartanLaboratories/GeneralTools#7](https://github.com/SpartanLaboratories/GeneralTools/issues/7).
- **Date read:** 2026-10-16. Repo baseline: branch `feat/issue-7-kotlin-multiplatform`, tests as of `master` @ `17d30bc` (185 `@Test` methods).
- **Pinned sources:** JetBrains/kotlin tag `v2.4.21` (commit `9180ce6a7a7d3627f88b424717583f28ddca052d`), the same Kotlin version as the Kotlin Gradle plugin in [kmp-build-and-kotlin-compat.md](kmp-build-and-kotlin-compat.md). Library code is compiled with `languageVersion` and `apiVersion` 2.2, so it may use stdlib API only up to `@SinceKotlin("2.2")`.
- **Method limits:** no Kotlin code was compiled or run. Behaviour of `js` and `wasmJs` comes from the stdlib and compiler source at `v2.4.21`, official docs, and two read-only probes of the underlying primitives (JDK 23.0.2 `java Probe.java`, Node v24.19.0 `node probe.js`). What is therefore inferred rather than observed is listed in *Gaps*, each with the smallest check that settles it.

## 1. Question

Does every test that moves to `commonTest` (the pure part of the current suite: `ColorTest`, the nine geometry component tests, `PointTest`, `SquareTest`, `TwoDoublesTest`, the stray class `Point`, and the platform-neutral part of `MiscTest`) hold unchanged on `jvm` (bytecode 17), `js` and `wasmJs` (both on Node), and which common-code replacements serve the JVM-only calls (`String.format`, `javaClass`, `java.lang.Math.pow`, `java.util.function.Predicate`, `String.capitalize`, `Thread.sleep`)?

An answer must meet these requirements:

- `Color` and the geometry types behave the same on all three targets; existing test expectations hold unchanged, except that `capitalizeEveryWord` stops dropping commas that are part of its input.
- 3.0.0's intended breaks (internal `Color` constructor, open `TwoDoubles`, immutable `Point`/`Dimensions`, `divideBy` returning a `Result`, `evaluateList` taking `(T) -> Boolean`, removal of `com.spartanlabs.logging`) change some tests by design; those are classified separately from parity failures.
- Replacements prefer the standard library, then hand-rolled code, then a new dependency, and must compile with `apiVersion` 2.2.

## 2. Bottom line

- **One assertion in the whole suite cannot hold unchanged on all three targets: `PointTest` "`toString` formats x and y".** `Point(1.0, 2.0).toString()` is `"1.0, 2.0"` on `jvm` and `wasmJs` but `"1, 2"` on `js`, because Kotlin/JS prints a `Double` with JavaScript's `Number.toString`, which has no `.0` (the stdlib's own test excludes JS for exactly this). It passes on JS only if `TwoDoubles.toString` changes on that target. It is the only string assertion in the suite that embeds a `Double` or `Float`. Options and the recommendation are in section 3.1 and section 6.
- **Everything else holds.** Of the 176 tests that go to `commonTest`, 163 hold unchanged on all three targets, 12 change by design (the in-place mutators of `Point`/`Dimensions`), and the 1 above is the exception. The NaN-propagating slab code is safe: JS `minOf`/`maxOf` delegate to `Math.min`/`Math.max` and the Wasm implementations explicitly return NaN, so the grazing-ray test still ends in a clean miss. All `Float` assertions in `ColorTest` use values that are exact in both 32-bit and 64-bit arithmetic or carry a `1e-4` tolerance. The 127.5 ties round up on all three targets.
- **The common replacements are all stdlib-only:** `HexFormat`/`Byte.toHexString` (stable since Kotlin 2.2.0, so allowed at `apiVersion` 2.2) or `Int.toString(16).padStart(2, '0').uppercase()` for `toHex`; `this::class` for `equals`/`hashCode`; dropping the `java.lang.Math.pow` import (the `kotlin.math.pow` import is already there); a `(T) -> Boolean` for `evaluateList`; `replaceFirstChar { if (it.isLowerCase()) it.titlecase() else it.toString() }` joined with `joinToString(" ")` for `capitalizeEveryWord`; a no-op lambda for the `profile` test.
- **Library behaviour that is not covered by any test but differs between targets** (section 3.3): `Color.lerp` with a non-dyadic `Float` fraction differs by one unit in a channel on JS in about 0.01% of probed cases, because a Kotlin/JS `Float` is a double; `trimIfLongerThan` with a negative length throws on `jvm`/`wasmJs` and silently returns `""` on `js`; `Double.hashCode`, `Float` string forms and `KClass` hash values differ per target and must not be relied on. None changes a test result; each has an option and a recommendation.
- **A pre-existing defect becomes visible:** `TwoDoubles.equals` treats `0.0` and `-0.0` as equal but `hashCode` differs on `jvm` and `wasmJs` (equal objects, unequal hashes), and `NaN` coordinates make an object unequal to itself. It is outside the tests' coverage and is reported in section 5.

## 3. Findings

Evidence tiers: **consensus** = multiple independent credible sources or the language/library's own documentation; **practice** = what mature libraries visibly do; **opinion** = one source; **source-read** = read from stdlib/compiler source at `v2.4.21` but not executed on the target.

### 3.1 `Double.toString` on JS, Wasm and the JVM (`TwoDoubles.toString`, behaviour 1)

**Finding (consensus + source-read, Kotlin 2.4.21):** the three targets print the same `Double` differently, and the Kotlin documentation does not promise otherwise.

- The official doc for `Double.toString` says the format "is unstable and may change in a future release" and guarantees only a round trip through `String.toDouble` ([Double.toString](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin/-double/to-string.html)).
- JS: `Double.toString` is not replaced by the compiler (`MethodsOfAnyCallsTransformer` only rewrites `toString` on arrays, `Any`, dynamic and `String` receivers), so it is JavaScript's `Number.prototype.toString`. The stdlib's own test excludes JS from `(0.0).toString() == "0.0"` and `(-0.0).toString() == "-0.0"` in `FpNumberToStringTest.doubleTest`, and another stdlib test says the exact string "is platform-dependent" (`FpNumberToStringTest.kt74441`). A merged third-party fix reports the same: [vico #1625](https://github.com/patrykandpatrick/vico/pull/1625) ("On Kotlin/JS, `Double.toString()` returns `10` rather than `10.0`").
- Wasm: `Double.toString` is `dtoa(this, isSinglePrecision = false)` in `Number2String.kt`, a Grisu2 port from AssemblyScript whose `prettify` step uses JavaScript's layout thresholds (plain decimal from 1e-6 up to 1e21, otherwise `e` notation with an explicit sign), but always keeps one fractional digit for integral values (`"1.0"`, `"-0.0"`).
- JVM: `Double.toString` uses `E` notation at or above `1.0E7` and below `1.0E-3`, always with a fractional digit. The digit generator changed in JDK 19 ([JDK-4511638](https://bugs.openjdk.org/browse/JDK-4511638), "Double.toString(double) sometimes produces incorrect results", fix version 19), so even "the JVM's output" is not one reference on bytecode-17 consumers running JDK 17.

Measured on the JVM (JDK 23.0.2) and in Node 24.19.0 (JS = `String(x)`); the Wasm column is derived from the `prettify` rules in `Number2String.kt` (not executed):

|---|---|---|---|

| `0.5`, `-1.5` | `0.5`, `-1.5` | `0.5`, `-1.5` | `0.5`, `-1.5` |
| `100.0` | `100.0` | `100` | `100.0` |

Every `Double` or `Float` embedded in a string assertion, searched across `src/test/kotlin/**`: only `PointTest."toString formats x and y"` (`assertEquals("1.0, 2.0", Point(1.0, 2.0).toString())`). The other string assertions embed hex strings, URLs, words, and map values. Production code interpolates `Point`/`Segment`/`Square` into log messages and into `Result` failure messages; no test asserts on those.

**What exact JVM reproduction would take.** A common formatter would take the platform's `toString()` (any of the three shapes: `1`, `1.0`, `1e+21`, `1.0E21`), extract sign, digit string and decimal exponent, and re-emit the JVM layout (plain decimal for `1e-3 <= |x| < 1e7` with at least one fractional digit; otherwise `d.dddE<n>` with no `+`). It is idempotent on JVM output, so JVM behaviour is unchanged by construction and a JVM golden-string test can prove it. Even then the digit string is the platform's: JS follows ECMAScript's shortest-round-trip rule, JDK 19+ is shortest, JDK 17 is not always, Wasm's Grisu2 is not guaranteed shortest. Exact equality is therefore achievable for the notation, not for every digit string of every value.

**Is a partial match defensible?** Yes, for a diagnostic string whose documented format is unstable on the reference platform. The partial match that costs three lines (render integral-looking output with `.0` and keep the sign of `-0.0`) equals the JVM output exactly for `NaN`, `±Infinity`, `±0` and every value with `1e-3 <= |x| < 1e7`, and differs only in notation outside that range (value still round-trips).

**Options for the one failing assertion** (the test passes on JS only if library behaviour changes there):

| B. Internal common normaliser that appends `.0` to integer-looking output and fixes `-0.0` | unchanged (it never alters a string containing `.`, `E`, `N` or `I`) | `js` output only; `wasmJs` is already `"1.0"` | ~5 lines, no `expect`/`actual` | exact match on `1e-3 <= abs < 1e7`; `js` and `wasmJs` agree for all values below 1e21 |
| C. Internal common formatter that reproduces the JVM layout from any platform's digits | unchanged (idempotent) | `js` and `wasmJs` notation for `>= 1e7` and `< 1e-3` | ~30 lines plus golden-string tests | exact notation; digit strings still platform-generated |

### 3.2 NaN and the slab code (`minOf`/`maxOf`, behaviour 2)

**Finding (source-read, `v2.4.21`):** NaN propagates through `minOf`/`maxOf(Double, Double)` on all three targets; the NaN-sensitive tests pass.

- Common KDoc: "If either value is `NaN`, returns `NaN`."
- JVM: `Math.min`/`Math.max`. JS: `JsMath.min(a, b)` / `JsMath.max(a, b)`; ECMAScript's `Math.min`/`Math.max` return NaN if any argument is NaN (confirmed in Node: `Math.min(NaN, 1)` and `Math.max(1, NaN)` both give `NaN`; `Math.max(-Infinity, NaN)` gives `NaN`).
- Wasm `minOf` is `when { a.isNaN() -> a; b.isNaN() -> b; else -> if (a.compareTo(b) <= 0) a else b }`. Wasm `maxOf` is `if (a.compareTo(b) >= 0) a else b` and relies on `Double.compareTo` being a total order with NaN greatest, which holds because it falls back to `toBits()` comparison and Wasm's `Double.toBits()` canonicalises NaN (`if (isNaN()) Double.NaN.toRawBits() else toRawBits()`). A NaN produced by `0.0 * Infinity` with the sign bit set would otherwise sort below positive numbers and be dropped; the canonicalisation closes that.
- The sign of zero is handled the same way as on the JVM (`min(-0.0, 0.0)` is `-0.0` in Java and in JS; Wasm uses the same total order).

Walk-through of the only NaN-dependent test, `RayBoxIntersectionTest."origin on a face plane travelling along that face is a deterministic miss"` (ray origin `(0, 1)`, direction `(1, 0)`, box `(-1,-1)..(1,1)`): `invDy = +Infinity`; `ty1 = (-1 - 1) * Inf = -Inf`; `ty2 = (1 - 1) * Inf = NaN`; `minOf(ty1, ty2)` and `maxOf(ty1, ty2)` are `NaN` on all targets; `tmin` and `tmax` become `NaN`; `tmax >= maxOf(tmin, 0.0)` is `false` (the operands are statically `Double`, so the comparison is IEEE on every target); the result is `Result.success(null)`. The Node probe reproduces the intermediate values (`[-Infinity, NaN, NaN, NaN]`). `SegmentBoxIntersectionTest` has no case that produces NaN: its parallel-and-outside segment yields `-Infinity` bounds, not NaN, and its on-face case short-circuits through `contains`.

### 3.3 `Float` semantics (`Color`, behaviour 3) and `roundToInt` (behaviour 4)

**Finding (consensus + source-read):** on `js` a `Float` is a JavaScript number with double precision; on `wasmJs` it is a real 32-bit float; the `ColorTest` assertions are insensitive to the difference.

- JS: the docs map `Float` and `Double` both to `Number` ([Kotlin/JS interop](https://kotlinlang.org/docs/js-to-kotlin-interop.html)). In the compiler, `Float.toDouble()` and `Double.toFloat()` are identity casts (`NumberConversionCallsTransformer`: `add(type, OperatorNameConventions.TO_FLOAT, ::useDispatchReceiver)`), there is no `Math.fround`, and a float literal is emitted as the decimal double of its shortest string (`toDoubleConst(f) = ... f.toString().toDouble()`, so `0.06f` becomes the double `0.06`). `Float.toBits()` documents that "in Kotlin/JS [Float] range is wider than "single format" bit layout can represent". A `FloatArray` is a `Float32Array`, so values stored in the array returned by `normalized()` are rounded to 32 bits on store.
- Wasm: `Float.toDouble()` is `wasm_f64_promote_f32(this)` and `Double.toFloat()` is `wasm_f32_demote_f64(this)`; arithmetic is `f32`.
- Rounding: `roundToInt` is documented "Ties are rounded towards positive infinity" and tested for `2.5 -> 3`, `-2.5 -> -2`. JVM `Math.round`, JS `Math.round` (ECMAScript rounds half toward +Infinity) and Wasm `floor(this + 0.5)` agree on every tie. NaN throws `IllegalArgumentException` on all three (the library's guards keep NaN out).

Per `ColorTest` assertion, every `Float` computation:

- `normalized()`: `assertContentEquals(floatArrayOf(1f, 0f, 0f, 1f), Color(255, 0, 0, 255).normalized())` has values that are exact in any precision, with positive zero (`0 / 255f` is `+0.0`; `assertContentEquals` distinguishes `-0.0`). The partial-channel test (`128 / 255f` against `0.50196f`, tolerance `1e-4f`) is a tolerance check. Holds on all three. (A single division in double precision followed by a store into `Float32Array` equals the correctly rounded float division, because 53 >= 2 * 24 + 2, so even the array contents are identical across targets.)
- `luminance()`: `assertEquals(0.0f, Color.BLACK.luminance())` is `+0.0` everywhere; the white and red checks use `1e-4f`; the alpha check compares two evaluations of the same expression. The returned value differs in its last digits between `jvm`/`wasmJs` (float arithmetic) and `js` (double arithmetic); no test is sensitive to it.
- `lerp(target, fraction: Float)`: every test uses `0f`, `1f`, `0.5f`, `2f`, `-1f`, `NaN` or an infinity. All are exactly representable, and the products (`255 * 0.5f = 127.5`) are exact in 32 and 64 bits; `127.5` rounds to `128` on all targets; the alpha test's `0 + 255 * 0.5f` likewise.
- `fromNormalized`: `0.5f * 255 = 127.5 -> 128`, the clamped cases and the non-finite cases (guarded by `takeIf { isFinite }`) are exact.
- `lightened`/`darkened`/`grayscale` are `Double` arithmetic (identical IEEE results on all targets; JS and Wasm forbid fused multiply-add, and so does HotSpot). Ties tested: `255 * 0.5 = 127.5` and `255 * (1.0 - 0.5) = 127.5`, both `128`. `lightened()` default: `255 * 0.35 = 89.25 -> 89`.

**Library-behaviour divergence outside the tests (not a test failure):**

- **`lerp` on JS with non-dyadic fractions.** The JVM and Wasm round the product to float32 before `roundToInt`; JS does not. Probe (JDK 23 arithmetic; JS modelled as double arithmetic with the literal widened as the compiler does): over all `start, end` in `0..255` and `fraction = k / 100f` for `k = 0..100` (6,619,136 cases), `jvm` and JS differ by one in 676 cases (0.010%) when the fraction is a literal such as `0.21f` (`Color(0,0,0).lerp(Color(150,..), 0.21f)`: red is `31` on the JVM and Wasm and `32` on JS, because `150 * 0.21f` rounds to the float just below 31.5 in float32 but equals exactly 31.5 in doubles), and in 51,743 cases (0.78%) when the fraction's float32 value is carried into doubles unchanged. `wasmJs` matches the JVM in all cases (the Wasm `floor(x + 0.5f)` model differs from `Math.round(float)` in 0 of 6,619,136).
- **Wasm `roundToInt` is `floor(x + 0.5)`**, which differs from JVM and JS for exactly one double (`0.49999999999999994` gives `1` instead of `0`) and for `0.49999997f`. Probe over `lightened`/`darkened` for all 256 channel values and 1,002 fractions, and `grayscale` for all 16,777,216 colours (17,290,240 samples): zero differences. No test or realistic input is affected; it is an stdlib characteristic to know about.

### 3.4 `Int` bit operations (`toPackedInt`, `fromPackedInt`, behaviour 5)

**Finding (consensus):** identical on all targets. The docs state "Kotlin preserves overflow semantics for `kotlin.Int`, `kotlin.Byte`, `kotlin.Short`, `kotlin.Char` and `kotlin.Long`" ([Kotlin/JS interop](https://kotlinlang.org/docs/js-to-kotlin-interop.html)); `Int` `shl`/`shr`/`and`/`or` compile to 32-bit JS operators or to Wasm `i32` operations. Node confirms the two cases that matter: `255 << 24 === -16777216` and `(-1 >> 24) & 0xFF === 255`. `toPackedInt of opaque white is -1`, `fromPackedInt(-1)`, and the ARGB placement test therefore hold.

### 3.5 `String.toInt(16)` and its exception (`Color.fromHex`, behaviour 6)

**Finding (source-read, `v2.4.21`):** holds on all three targets. On JS and Wasm `String.toInt(radix)` is `toIntOrNull(radix) ?: numberFormatError(this)`, and `NumberFormatException` is declared `public actual open class NumberFormatException : IllegalArgumentException` on JS and Wasm (and in common via `expect`). `fromHex("#GGGGGG")` therefore throws an `IllegalArgumentException` subtype everywhere (the `G` digit maps to `-1` in `digitOf` for radix 16 and the parse returns null). `fromHex("#FFFF")` throws the explicit `IllegalArgumentException` (length 4). The `digitOf` tables also accept the same non-ASCII digit classes on JS and Wasm that `Integer.parseInt` accepts (full-width Latin letters and `Character.digit`-style digits). Differences that remain are cosmetic: the exception message ("For input string: ..." on the JVM, "Invalid number format: '...'" on JS and Wasm), and none is asserted.

### 3.6 Replacement for `String.format("#%02X%02X%02X", ...)` (behaviour 7)

**Finding (consensus + source-read):** two stdlib-only options, both valid at `apiVersion` 2.2.

- `HexFormat` and the `toHexString` extensions are `@SinceKotlin("2.2")` (annotated `@WasExperimental(ExperimentalStdlibApi::class)`), and Kotlin 2.2.0's release notes say "In Kotlin 2.2.0, the `Base64` API and `HexFormat` API are now Stable." `Byte.toHexString(HexFormat.UpperCase)` always returns exactly two upper-case digits (`UpperCase` is `Default` with `upperCase = true`; `Default` removes no leading zeros and adds no prefix). `ByteArray.toHexString(HexFormat.UpperCase)` formats `byteArrayOf(red.toByte(), green.toByte(), blue.toByte())` as `"FF5733"` directly, and with the alpha byte first as the `AARRGGBB` form. All three targets run the same common Kotlin code.
- `Int.toString(16).padStart(2, '0').uppercase()` is common API since Kotlin 1.2 (`Int.toString(radix)`) and works unchanged on all targets (JS `Number.toString(16)`, a Kotlin loop on Wasm).
- Both equal `%02X` for `0..255`. They differ from `%02X` only for out-of-range channels (`%02X` of `300` is `12C`, of `-5` is `FFFFFFFB`): `HexFormat` on a `Byte` wraps (`300 -> 2C`), and `toString(16)` yields `12C` and `-5`. The `Color` KDoc declares `0..255` as the contract, and after 3.0.0 only a public `copy` can produce an out-of-range channel (decided with the constructor's visibility, outside this file); no test formats an out-of-range colour.

### 3.7 `this::class` in `equals`/`hashCode` (behaviour 8)

**Finding (source-read, `v2.4.21`):** `KClass` equality distinguishes concrete classes on all three targets, and `KClass.hashCode` differs between `Point` and `Dimensions`; hash values themselves differ per target and carry no cross-target meaning.

| target | `KClass.equals` | `KClass.hashCode` | `qualifiedName` |
|---|---|---|---|
| `jvm` | `ClassReference.equals`: `javaObjectType == other.javaObjectType` | `javaObjectType.hashCode()`, i.e. `Class` identity hash (differs run to run) | available |
| `js` | `KClassImpl.equals`: `jClass == other.jClass && simpleName == other.simpleName` | `simpleName?.hashCode() ?: 0` | `null` always |
| `wasmJs` | `KClassImpl.equals`: `wasm_ref_eq(rtti, other.rtti)` (type identity) | `getQualifiedName(rtti).hashCode()` | available by default since Kotlin 2.3.0 ("In Kotlin 2.3.0, the `KClass.qualifiedName` property is enabled by default on Kotlin/Wasm targets", [What's new in Kotlin 2.3.0](https://kotlinlang.org/docs/whatsnew23.html)); the Wasm `KClass` KDoc at `v2.4.21` still carries the older "not supported by default" sentence |

- `TwoDoublesHashCodeTest."Point and Dimensions with the same values hash differently"` asserts `31 * (31 * H(class) + h1) + h2` differs for the two classes; since 31 is odd that holds exactly when the two class hashes differ. JS: `"Point".hashCode() = 77292912` against `"Dimensions".hashCode() = -1887167507` (`getStringHashCode` in `js/runtime/coreRuntime.kt` is the same 31-polynomial as the JVM's); Wasm: the hash of the qualified name (`com.spartanlabs.geometry.Point` and `...Dimensions`; the JVM's 31-polynomial would give `-366470282` and `-575260249`, and the Wasm `String.hashCode` algorithm itself was not read, see *Gaps*); JVM: two identity hashes (collision chance about 5e-10). All are expected to hold.
- **Do not use `KClass.qualifiedName` in library code:** it is always `null` on JS (on Wasm it works by default since Kotlin 2.3.0). `simpleName` is supported everywhere and is null only for anonymous classes (the existing `divideBy` log call uses it and keeps working).
- **Open `TwoDoubles`:** `if (other == null || other::class != this::class) return false` keeps "same concrete class" on all targets. On JS two distinct anonymous or local subclasses still differ because `jClass` is compared first; on Wasm identity is the runtime type; on the JVM it is the `Class`. Two consequences: (1) `::class` on the JVM allocates a `ClassReference` per call (`ReflectionFactory.getOrCreateKotlinClass` returns `new ClassReference(javaClass)`) where `javaClass` was free, so if `equals` is hot, an `internal expect fun sameClass(a: Any, b: Any): Boolean` whose JVM actual is `a.javaClass === b.javaClass` is the one place where `expect`/`actual` is justified, but only after a measurement says so; (2) subclasses defined by consumers inherit this `equals` and `hashCode` and get the class fold for free.
- **`Double.hashCode` per target:** JVM and Wasm both use `toBits().hashCode()` (`hash(1.0) = 1072693248`, `hash(0.0) = 0`, `hash(-0.0) = -2147483648`, NaN canonical `2146959360`). JS uses `getNumberHashCode`: an integral value hashes to its `Int` (`1.0 -> 1`, and `-0.0 -> 0`), others to `high * 31 + low`. Equal values give equal hashes on every target, which is what the tests need; the numbers are not comparable across targets.

### 3.8 `capitalizeEveryWord` (behaviour 9)

**Finding (source-read, `v2.4.21`):** `String.capitalize()` is deprecated at WARNING level only: the annotation is `@DeprecatedSinceKotlin(warningSince = "1.5")` with no `errorSince`, on both JVM and JS (`StringsJVM.kt`, `stringsCode.kt`). It still compiles at `apiVersion` 2.2 (warning). The stdlib's own `ReplaceWith` for the JVM overload is `replaceFirstChar { if (it.isLowerCase()) it.titlecase(Locale.getDefault()) else it.toString() }`; the locale-free common form is `replaceFirstChar { if (it.isLowerCase()) it.titlecase() else it.toString() }` (`Char.titlecase()`, `Char.isLowerCase()` and `String.replaceFirstChar` are common API since 1.5).

Behaviour of the current implementation and of the replacement `split(' ').joinToString(" ") { it.replaceFirstChar { c -> if (c.isLowerCase()) c.titlecase() else c.toString() } }`:

- **Identical** for input with no commas: `list.toString()` joins with `", "` and the old code removes every `,`, leaving exactly one space per separator, so `"a  b"` (two spaces), a leading or trailing space, and `""` all give the same result as `joinToString(" ")` (empty string splits into `[""]`, giving `""`). Only a space splits words; tabs and newlines do not, in both.
- **The one intended difference:** the old code removes every comma in the data (`"hello, world"` gave `"Hello world"`); the new code keeps it (`"Hello, World"`), which is the new test.
- **Locale:** the old call used the JVM default locale (`capitalize()` is `capitalize(Locale.getDefault())`); `Char.titlecase()` is "Unicode mapping rules of the invariant locale". Results differ only for default locales with special rules (Turkish, Azeri, Lithuanian: `i`). This makes the result deterministic and equal across targets.
- **Title case versus upper case:** the old JVM code titlecased (`ǆ -> ǅ`, not `Ǆ`) and kept uppercase letters as they are; `if (c.isLowerCase()) c.titlecase() else c.toString()` reproduces both. A bare `c.titlecase()` would also titlecase an uppercase `Ǆ` to `ǅ`. One-to-many mappings (`ß`, `ﬀ`) expand to several characters in both versions.
- **Unicode tables** for `isLowerCase`/`titlecase` come from the JDK on `jvm` and from the Kotlin stdlib's tables on `js`/`wasmJs`; a character added in a newer Unicode version than the running JDK's can differ. The test string `"hello world foo"` is not affected.

### 3.9 `kotlin.math` parity (`pow`, `sqrt`, `abs`; behaviour 10)

**Finding (source-read + probe):** `pow(x, 2.0)` is exact (`x * x`) on every target in practice; no test depends on last-bit behaviour of anything else.

- JVM: `Math.pow`. JS: `Math.pow`. Wasm: `kotlin.math.fdlibm.__ieee754_pow` ported from fdlibm, which contains `if (hy == 0x40000000) return x * x /* y is  2 */`. `sqrt` is correctly rounded on every target (Wasm `f64.sqrt`, JS `Math.sqrt`, JVM `Math.sqrt`); `abs` is exact.
- Probes: `Math.pow(x, 2.0) == x * x` for 20,000,000 random doubles (random bit patterns, NaN and infinities excluded) and 20,000,000 uniform values in (-1000, 1000), in both JDK 23 and Node 24: zero differences.
- Exact-equality assertions on arithmetic results, all on values that are exact in binary: `assertEquals(5.0, distance.getOrThrow())` (`sqrt(9 + 16)`), `assertEquals(Point(7.0, 9.0), r.pointAt(2.0))`, `Segment.pointAt(0.5)`, `projectedOnto` on axis `(1, 0)`, the `CenteredBox`/`Square` conversions, `lerp` (section 3.3). Everything else uses a `1e-9` tolerance.
- No FMA contraction on any target (the spec forbids it for JS and Wasm), so `x * x + y * y` is identical everywhere.
- If last-bit stability of `distanceFrom` ever matters, `dx * dx + dy * dy` removes the dependence on `pow` and matches `Point.length`; this is an option, not a requirement.

### 3.10 `measureTime`, `TimeSource.Monotonic` and the `profile` test (behaviour 11)

**Finding (source-read):** works on both non-JVM targets; the `profile` test needs no sleep.

- `measureTime` is `@SinceKotlin("1.9") @WasExperimental(ExperimentalTime::class)`, so it is stable and the `@OptIn(ExperimentalTime::class)` in `Misc.kt` is no longer required. `TimeSource.Monotonic` on JS reads `process.hrtime` under Node (falling back to `performance`, then `Date.now`); on `wasmJs` it reads `performance.now()` through a JS import (falling back to `Date.now`).
- The test only checks the prefix `"sample action took"` and the suffix `"ms"`, so a no-op action (`profile("sample action") { }`) or a short pure loop serves. A common-code sleep would need `kotlinx-coroutines` (`delay`), a new dependency for no gain.

### 3.11 `KClass` in `onException` (behaviour 12)

**Finding (source-read):** holds. `ex::class in exceptions` is `Array.contains`, which uses `KClass.equals` (section 3.7). `IllegalStateException`, `IllegalArgumentException` and `NumberFormatException` are Kotlin classes on JS and Wasm (declared in `js/src/kotlin/exceptions.kt` and `wasm/src/kotlin/Exceptions.kt`), and `runCatching` rethrows the same instance, so `IllegalStateException::class` equals `ex::class` for a thrown `IllegalStateException`, and `NumberFormatException::class` does not. The function is `inline` and public in common code and references only public API.

### 3.12 Companion initialisation order on Wasm (behaviour 13)

**Finding (consensus, Kotlin 2.4.20 release notes):** not relevant to this code. The change is: "Kotlin/Wasm now initializes superclass companion objects before subclass companion objects, matching the JVM behavior" ([What's new in Kotlin 2.4.20](https://kotlinlang.org/docs/whatsnew2420.html)). `Color` and `CenteredBox` are final data classes without a superclass beyond `Any` (`CenteredBox` implements an interface; companions are not inherited through interfaces), `TwoDoubles` has no companion, and `Color`'s companion constants are immutable `Color` values with no dependency on another companion.

### 3.13 Other JVM-specific behaviour in the code that moves (behaviour 14)

Read in full: `generaltools/Color.kt`, `generaltools/Misc.kt`, and all of `geometry/*.kt`. Beyond the listed JVM calls:

- **`kotlin.assert` is JVM-only:** the stray test class `Point` calls `assert(point1 == point2 && point1 != point3)`; `assert(Boolean)` is public only in `jvm/src/kotlin/util/AssertionsJVM.kt` (`internal actual` on Wasm, absent on JS). It must become `assertTrue`. (On the JVM `assert` also only runs under `-ea`; Gradle's test task enables assertions, but `assertTrue` removes that dependence.)
- **`String.substring` bounds:** `trimIfLongerThan` is `if (this.length > length) substring(0, length) else this`. For a negative `length`, JVM throws `StringIndexOutOfBoundsException` and Wasm throws an `IndexOutOfBoundsException` (via `subSequence`), but JS is `asDynamic().substring(startIndex, endIndex)`, which clamps and returns `""`. Not tested; an explicit `require`/`IndexOutOfBoundsException` check would align the targets (and would keep the JVM exception type if it throws `IndexOutOfBoundsException`).
- **`Double ==` versus boxed equality:** all hot comparisons in the geometry code are on statically typed `Double` (IEEE: `NaN` unequal to itself, `0.0 == -0.0`), the same on all targets. Test assertions through `assertEquals(Double, Double)` with no tolerance box the values and use `equals` (`0.0` unequal to `-0.0`; JS implements this in `equals(obj1, obj2)`). No asserted value is `-0.0`.
- **`Result`** (including `Result<Double?>`), `data object`, `sealed interface`, `const val EPSILON` and `infix` members are common Kotlin with no per-target difference. `TwoDoubles.divideBy`'s log call `this::class.simpleName` works on all targets.
- **Interface default method** `AxisAlignedBox.contains`: pure Kotlin semantics on JS/Wasm; the JVM bytecode shape is a build-configuration matter outside this file.
- **kotlin.test API used by the suite** (`assertEquals` with `absoluteTolerance` for `Double` and `Float`, `assertContentEquals(FloatArray, FloatArray)`, `assertIs`, `assertNull`, `assertNotNull`, `assertFailsWith`) is common since 1.5 or earlier. If test sources share the 2.2 `apiVersion`, avoid the new `@SinceKotlin("2.4")` `lazyMessage` overloads in `Assertions.kt`.
- **Test infrastructure, not behaviour:** every test imports `org.slf4j.LoggerFactory` and (in the component tests) `org.junit.jupiter.api.Tag`; neither exists in common code. They are handled in [kotlin-logging-adoption.md](kotlin-logging-adoption.md) and [kmp-test-levels-and-names.md](kmp-test-levels-and-names.md) and are not counted as parity failures here.

## 5. Pitfalls and regrets

- **`Double.toString` is the classic KMP trap.** The pattern in every project above is the same: either the test is told which platform differs, or the library stops depending on the platform string. Parsing the platform string back (option C) works but is the most code to own.
- **JS `Float` is not a `float`.** `Float` results (`luminance`, `lerp`) are bit-different on JS. A fix that would make JS match without changing the JVM needs float32 rounding that common Kotlin cannot request except through tricks (`Float.fromBits(x.toRawBits())`, `FloatArray` stores); a fix that computes in `Double` everywhere changes JVM and Wasm results in the same 0.01% to 0.8% of probed cases.
- **Wasm `roundToInt` is `floor(x + 0.5)`** (one double and one float differ from JVM/JS). Harmless here; relevant if `roundToInt` is ever applied to a value that can be exactly one ulp below `0.5`.
- **Do not use `KClass.qualifiedName`** (always null on JS) or `javaClass` in common code.
- **`kotlin.assert`** compiles only on the JVM. Test files written for the JVM routinely contain it.
- **Pre-existing defect surfaced by the hash tests (JVM and Wasm):** `TwoDoubles.equals` compares with `==` on `Double` (IEEE), so `Point(0.0, 0.0) == Point(-0.0, 0.0)` is true, but `hashCode` uses `Double.hashCode`, which on `jvm` and `wasmJs` hashes `0.0` to `0` and `-0.0` to `-2147483648`. Equal objects with unequal hashes break `HashMap` lookups. Separately, a `NaN` coordinate makes an object unequal to itself (`first == other.first` is false for NaN). On JS the zero case is consistent by accident (`getNumberHashCode(-0.0)` is `0`). No test covers it. A cheap fix is to fold `first + 0.0` and `second + 0.0` into the hash (turning `-0.0` into `0.0`); whether `NaN` should compare equal to itself is a contract decision. This is a defect in a Spartan Labs library and is worth a GitHub issue.

## 6. Recommendation for this repo

1. **`TwoDoubles.toString`: normalise in common code (option B), keep the test as written.** Add one internal helper used by `toString` that leaves any string containing `.`, an exponent, or a non-digit untouched and otherwise appends `.0`, plus the sign of negative zero:

   ```kotlin
   internal fun Double.toDisplayString(): String {
       val s = toString()
       return if (s.all { it.isDigit() || it == '-' }) {
           if (s == "0" && 1.0 / this < 0) "-0.0" else "$s.0"
       } else s
   }
   ```

   On the JVM `toString()` of every `Double` contains `.`, `E`, `N` or `I`, so the helper never changes JVM output; on Wasm integral values already contain `.`; on JS it supplies the missing `.0`. The result equals the JVM output exactly for `NaN`, `±Infinity`, `±0` and `1e-3 <= |x| < 1e7`; outside that range notation stays platform-defined, and the KDoc says so. Reasoning: the existing expectation then holds unchanged on all three targets, the JVM contract is untouched, nothing platform-specific is needed, and the code is five lines. Add `commonTest` cases for the helper on `-0.0`, a negative integral value, `NaN` and `Infinity`; do not assert the notation of values at or above `1e7` or below `1e-3`, which stays platform-defined. Option C is the upgrade path if exact notation is ever required; option A is the fallback if the helper is rejected, and it uses the `expect val currentPlatform` pattern from kotlinx.serialization.
2. **Replacements:** `toHex` with `ByteArray.toHexString(HexFormat.UpperCase)` over `byteArrayOf(...)` (stdlib-only, stable at `apiVersion` 2.2; `Int.toString(16).padStart(2, '0').uppercase()` is the equivalent fallback); `equals` with `if (other == null || other::class != this::class) return false` and `hashCode` folding `this::class.hashCode()`; delete `import java.lang.Math.pow`; `evaluateList(list: Iterable<T>, validator: (T) -> Boolean)`; `capitalizeEveryWord` as `split(' ').joinToString(" ") { it.replaceFirstChar { c -> if (c.isLowerCase()) c.titlecase() else c.toString() } }`; `profile` test with a no-op action; the stray `Point` test's `assert` becomes `assertTrue`. The `@OptIn(ExperimentalTime::class)` on `profile` can go. Keep `toInt(16)` for `fromHex`.
3. **Do not change `lerp`, `luminance` or `roundToInt` usage.** Test fractions are exactly representable, so the suite holds; document in `lerp`'s KDoc that results for non-dyadic fractions may differ by one unit between targets (the JS `Float` is a double), and keep any new `lerp` test to dyadic fractions. Changing arithmetic to `Double` would alter JVM output today in the probed 0.01% to 0.8% of cases, which a parity change should not do silently.
4. **Optional, low-cost:** align `trimIfLongerThan` for negative lengths (throw `IndexOutOfBoundsException` for `length < 0` so JS matches `jvm` and `wasmJs`); swap `dx.pow(2.0)` for `dx * dx` only if a last-bit guarantee is wanted (today both give the same bits).
5. **Reject** replacing the `toString` contract with fixed-decimal formatting (it changes JVM output), and reject adding a dependency for number formatting (the helper above is smaller than the dependency's integration).

## 8. Gaps

- **Nothing was run on Kotlin/JS or Kotlin/Wasm.** Every statement about `js` and `wasmJs` is from stdlib and compiler source at `v2.4.21` plus primitive probes (JDK 23 / Node 24), not from executing compiled Kotlin. The smallest checks that would settle the inferred items, each a one-assertion probe in `commonTest` run on all three targets:
  1. `assertEquals("1.0", 1.0.toString())`, `"0.0"`/`"-0.0"`, `"1.0E7"` (expected to fail on JS, and the last on Wasm) to confirm the table in 3.1, in particular the Wasm column (derived from the `prettify` rules; Grisu2 digit strings for non-trivial values such as `0.1 + 0.2` are unconfirmed).
  2. `assertEquals(31, Color(0, 0, 0).lerp(Color(150, 0, 0), 0.21f).red)` to confirm the JS `lerp` divergence in 3.3 (the 676-case figure models JS as double arithmetic with the literal widened as `toDoubleConst` does).
  3. `assertTrue(rayIntersectsBox(Ray(Point(0.0, 1.0), Point(1.0, 0.0)), box).getOrThrow() == null)` on Wasm, the one NaN case, to confirm the walk-through in 3.2 against the real Wasm code path (the existing test already is that check once it runs).
- **JDK 17 behaviour was not observed.** The probes ran on JDK 23; the statement that JDK 17's `Double.toString` can print different digits rests on the JDK-4511638 record (fix version 19), not on a JDK 17 run.
- **The Wasm `String.hashCode` algorithm** (used by `KClass.hashCode` on `wasmJs`) was not read; the `Point` versus `Dimensions` hash inequality there is expected from distinct names, not proven.
- **The hash equality/contract defect (section 5) was shown by reading `TwoDoubles` and by `Double.hashCode` values measured on the JVM;** the JVM-side `Point(0.0, 0.0) == Point(-0.0, 0.0)` was not executed as Kotlin.
- **`Color`'s constructor visibility and `copy` visibility** are decided in the language-mechanics question; whether an out-of-range channel is reachable (3.6) depends on it.
- **The outcome of the geometry-model question** decides whether `PointTest."copy constructor copies x and y"` and `SquareTest."mutating a square's location updates its properties"` stay (a) or become (b); this file assumes they stay.
- **JVM `::class` allocation cost in `equals`** is stated from the source of `ReflectionFactory` (one `ClassReference` per call); whether HotSpot's escape analysis removes it on the geometry hot paths was not measured.
- **Test names and per-level selection, slf4j and JUnit `@Tag` use in the tests** are not assessed here; see [kmp-test-levels-and-names.md](kmp-test-levels-and-names.md) and [kotlin-logging-adoption.md](kotlin-logging-adoption.md).
